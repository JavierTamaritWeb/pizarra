# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Pizarra is a canvas-based wireframing/sketching web app with a hand-drawn aesthetic. Vanilla HTML/JS with **zero runtime dependencies** — no bundler, no framework; `index.html` loads plain `<script>` tags and a plain stylesheet. Styles are authored in **SCSS (BEM)** under `src/scss/` and compiled by **Gulp 5 + dart-sass** into `css/styles.css`, which is **committed** so cloning and opening `index.html` keeps working with nothing installed (see "Styles" below). UI text is in Spanish.

The app was formerly called SketchWire, so that name survives in identifiers that must not change: the `localStorage` keys `sketchwire.autosave`/`sketchwire.prefs` and the clipboard marker `sketchwire/elements` in app.js. **Renaming those would orphan every user's saved canvas and preferences** — leave them alone.

## Running

Open `index.html` directly in a browser, or serve statically:

```bash
python3 -m http.server 8000   # then open http://localhost:8000
```

Style development needs `npm install` once, then: `npm run watch:css` (recompile on save), `npm run build:css` (one-shot), `npm run build` (compile + regenerate `dist/`, the publishable build: index.html and LICENSE verbatim, CSS compressed, JS minified — gitignored), `npm run lint:css` (stylelint). Tests use Node's built-in runner (no dependencies):

```bash
node --test tests/*.test.js          # full suite
node --test tests/exporter.test.js   # single file
```

**The app itself still has zero runtime dependencies** — `index.html` loads plain `<script>` tags and the already-compiled `css/styles.css`. `package.json`/`node_modules` exist only for development: the end-to-end suite and the style pipeline (Gulp/Sass/stylelint); never make the app require them at runtime.

Use the glob (`tests/*.test.js`), not the bare directory: `node --test tests/`
silently skips a file under Node 22.x's directory globbing, so a regression guard
could pass unnoticed by not running at all.

Tests load the global-scope scripts via `node:vm` with canvas/DOM stubs (see `tests/helpers/`). Two vm-realm gotchas: arrays/errors created inside the vm don't share host prototypes, so compare structurally (`[...arr]`, `err.name`) instead of `deepStrictEqual` against host literals or `instanceof`.

**`src/js/app.js` is testable too** (since v1.13.1) via `tests/helpers/load-app.js`, which runs the whole app under `node:vm`: `dom-stub.js` builds the element tree by parsing the real `index.html` (so ids, classes and nesting match the page), and the test drives real gestures — `selectTool`, `drag`, `click`, `key` — then reads the result with `elements()`. There is **no test hook in production code**: observability comes from the autosave, which serializes `state.elements` to localStorage. `flush()` drains the queued `requestAnimationFrame`/`setTimeout` callbacks so each gesture settles deterministically. Two things to know when writing these tests: pointer-move events must carry `buttons: 1` (app.js requires it to treat a move as a drag), and prefer asserting on element coordinates/counts rather than on canvas draw calls. **The harness does not simulate browser default actions** — it caught none of the two bugs found by opening the app in a real browser (a tool shortcut leaking into the modal it opened, and the eraser's reach feeling far too aggressive). It proves logic, not feel: still open the app for anything about focus, defaults or how a gesture reads. See `tests/app-interaction.test.js`. Prefer converting a "manual repro" BUGS.md entry into one of these tests over repeating the steps by hand.

### End-to-end suite (`e2e/`, Playwright)

```bash
npm run e2e:install     # una vez: descarga Chromium (~95 MB)
npm run test:e2e        # suite e2e
npm run test:all        # node:vm + e2e
```

It **complements** the `node:vm` harness, it does not replace it. The split is the point: `tests/` proves logic (coordinates, undo, export, geometry) in milliseconds; `e2e/` proves the things the vm harness cannot see *by construction* — layout, CSS, real focus and browser default actions. That's exactly the gap CLAUDE.md already warned about ("still open the app for anything about focus, defaults or how a gesture reads"), so most `e2e/` specs are BUGS.md entries that used to say *"verificación manual"*. **Decide where a new test goes by that rule**, not by convenience.

`playwright.config.js` serves the app with `python3 -m http.server` on port 8123 (no build, same as production) and runs Chromium only. Three things bite in this app specifically, all absorbed by `e2e/helpers.js` — use the helpers rather than driving the page directly:

- **Nothing is observable synchronously.** `redraw()` is coalesced through `requestAnimationFrame` and the autosave is debounced 500 ms, so a read right after a gesture returns the *previous* state. `settle()` (two rAFs) runs at the end of every gesture helper, and `elements()` then waits for the autosave to agree with the panel's «Elementos» counter. Without `settle()` that agreement is satisfied by the stale pair (0 === 0) and the wait returns instantly with the old scene — a silent false pass, not a failure.
- **The canvas is scaled and the scaling is animated.** `canvasPoint()` maps canvas coords to viewport coords through the canvas's own rendered box, so it absorbs zoom and scroll. But `.canvas-area__sizer` transitions `width`/`height` over 0.2 s: measuring mid-transition sends clicks to the wrong canvas coordinate and reports a half-sized scroll area. Always change zoom with `setZoom()`, which waits for the box to reach its final size.
- **Window size decides the initial zoom**, because of the auto-fit. Use the measured `WIDE` (1920×1200 → 120 %) and `NARROW` (1160×700 → 100 %) constants. `NARROW` is deliberately above 1100 px: below that the panel becomes a hidden drawer and its buttons can't be clicked without opening it first.

Observability follows the same rule as the vm harness: **no test hooks in production code** — the scene is read from the autosave, and everything else from the DOM the user sees.

`PLAN.md` holds the prioritized improvement roadmap (fases 1-3 completed, except §3.2 element-type registry, deliberately skipped as optional). `BUGS.md` is the regression registry: every bug fix gets a symptom/cause/fix entry there plus a **regression guard** — a test in `tests/` for code in one of the `node:vm`-loadable modules (config/sketchy/arc/renderer/exporter/templates), or documented manual repro steps if the fix lives in `app.js` (DOM-only, outside the test harness — see below). Add the entry as part of the fix, not as a follow-up.

## Styles (`src/scss/` → `css/styles.css`)

Since v1.25.0 the stylesheet is compiled: **`css/styles.css` is a generated artifact — edit `src/scss/` and run `npm run build:css`, never the CSS itself** (a guard in `tests/smoke.test.js` checks the banner and the runtime contracts). The artifact stays committed, at that exact path, because `tests/smoke.test.js` anchors `css/styles.css?v=…`, Playwright serves the repo root with no build step, and the README promises clone-and-open. `gulpfile.js` uses the modern `sass.compile()` API directly (no gulp-sass plugin), `style: 'expanded'`, no sourcemaps, no autoprefixer — the output is meant to be deterministic and reviewable. `src/` holds the app source: `src/scss/` (compiled), `src/js/` (loaded as-is — `index.html` points its `<script>` tags at `src/js/*.js`) and `src/img/` (every image in the repo). `index.html` itself stays at the repo root because the vm harness (`load-app.js`), Playwright and clone-and-open all anchor it there.

`npm run build` additionally assembles `dist/`, the publishable build (gitignored): LICENSE verbatim, index.html with its `src/js/` and `src/img/` paths flattened to `js/` and `img/` (the only HTML transformation anywhere), the same SCSS recompiled with `style: 'compressed'`, and each `src/js/*.js` minified with **terser** into `dist/js/` keeping its filename. `site.webmanifest` gets the same `src/img/` → `img/` rewrite, because its icon paths resolve relative to the manifest itself. Terser must never mangle top-level bindings — each `<script>` exposes globals (`TOOLS`, `Sketchy`, …) as top-level `const` that later scripts consume; the default `mangle: true` (without `toplevel`) is what keeps that safe. The `src/js/` files themselves are never transformed in the source tree.

**`dist/` does not regenerate itself, and a stale one is invisible.** It is gitignored, so it can sit at an old version indefinitely while the source moves on — and an app opened from `dist/index.html` then looks and works perfectly, just *as that older version*: a tool added since is simply absent from the sidebar, with nothing on screen to hint why (v2.23.0 lost an afternoon to exactly this, see BUGS.md). `tests/smoke.test.js` now checks that **if** `dist/` exists its `?v=` and topbar badge match `package.json`, and stays quiet when it doesn't. When verifying a change in a browser and the change "isn't there", check **which path the app is being opened from** — repo root, `dist/`, or `file://` — before trusting anything else.

## Images (`src/img/`)

**Every image in the repo lives in `src/img/`** — the icon set, `favicon.ico`, the topbar logo, the source PNG and the README screenshots. There is no `icons/` or `docs/` folder and nothing image-shaped at the repo root. `IMG_SKIP` in `gulpfile.js` is what keeps `dist/img/` down to the runtime pieces: it drops `icon-source-512.png` and anything named `screenshot-*`, which is why the README captures carry that prefix — rename them and they end up shipped.

The whole icon set is derived from `src/img/icon-source-512.png` with ImageMagick — that PNG is the only original, everything else is regenerable. `index.html` references them with **relative** paths (`src/img/…`, not `/src/img/…`) because the README promises clone-and-open over `file://`, where an absolute path resolves to the disk root. The small sizes (16/32/48, and thus the `.ico`) are cropped in ~7% before downscaling and lightly unsharpened: at 32px the source's generous padding left the drawing washed out. `src/img/logo-96.png` (the topbar's `<img class="topbar__logo-icon">`) comes from that same crop at 3× its 32px box. `src/img/icon-maskable-512.png` is the odd one — full-bleed paper background with the artwork at 80%, because Android crops a maskable icon into a circle and the squircle's corners would go with it; the rest keep transparent corners. `tests/smoke.test.js` guards that every icon referenced by the `<head>`, the manifest or the topbar exists and matches its declared `sizes` (a 404 here is silent — the browser just falls back to the default icon). The topbar logo is decorative (`alt=""`, the word «Pizarra» is right next to it) and carries no `border-radius`: the PNG already has its own rounded corners, and clipping it again eats into the drawing.

Rules that keep the compiled output correct — each one broke, or would have broken, something real:

- **`1rem` = 10px.** `html { font-size: 62.5% }` and every UI distance is written in rem (`body` restores the effective 16px with `1.6rem`). Media-query breakpoints stay in **px** on purpose, and so does everything JS sets on the canvas (canvas coordinates don't scale with browser font size; the UI chrome does). e2e asserts *computed* px (72/132), which rem resolves to exactly.
- **Custom properties must stay custom properties** in the output — never Sass `$vars` resolved at compile time: `--sidebar-w` is redefined at runtime inside a media query, and `src/js/config.js` reads `--font-sketch` at startup. The design-token *values* live as Sass vars in `src/scss/abstracts/_variables.scss` and `base/_tokens.scss` interpolates them into `:root` — that's the one place both layers meet.
- **Fonts have one source of truth: `src/scss/abstracts/_fonts.scss`** (`$font-ui`, `$font-sketch`). `_tokens.scss` emits them as custom properties via `meta.inspect()` — plain `#{}` interpolation strips the quotes each family needs. In the browser `SKETCHY_FONT` (config.js) reads `--font-sketch` from computed style, with the old literal as fallback for the `node:vm` harness (no `getComputedStyle` there) — the smoke guard asserts CSS and fallback agree. `FONT_FALLBACK` (exporter.js) derives from it stripping both quote kinds (double quotes would malform the SVG export's XML attributes).

**Since v2.13.0 the handwriting font is self-hosted and selectable, and the app requests no font over the network at all.** Five families live in `fonts/` as woff2 (SIL OFL 1.1, latin subset, licence in `fonts/LICENSE-handwriting-fonts.txt`): Architects Daughter — the default, unchanged — plus Caveat, Patrick Hand, Kalam and Indie Flower. **v2.14.0 added OpenDyslexic as a sixth option** — so the dyslexia-readable choice reaches the drawing and not just the chrome — and **v2.15.0 a seventh, Montserrat Alternates** (geometric). Neither is handwriting, so both end their stack in `sans-serif` rather than `cursive` (if the woff2 failed, another geometric beats a cursive), and the visible label became **«Letra del lienzo»**: it said «manuscrita» while they all were, and two of seven no longer are. Only OpenDyslexic carries `google: false`. The `<head>`'s two `preconnect`s and the Google Fonts `<link>` are gone, so the README's clone-and-open promise now holds offline and over `file://`; before, without a network the canvas silently fell back to the system cursive. Six things to keep in step:

- **`SKETCH_FONTS` (config.js) is the catalogue**, and every entry needs both an `@font-face` in `_font-faces.scss` and its `.woff2` on disk — a missing one doesn't throw, the canvas just draws with the system fallback. The first entry is the default and must say exactly what `$font-sketch`/`--font-sketch`/`SKETCHY_FONT` say. All of that is guarded in `tests/smoke.test.js`, including that `index.html` mentions neither googleapis nor gstatic.
- **`sketchFont()`, never `SKETCHY_FONT`, is what draws.** The constant is computed once at startup, so everything that writes on the canvas (renderer, previews, both exporters) goes through the function or a font change would leave old text behind. `exporter.js`'s `FONT_FALLBACK`/`FONT_CSS` became functions for the same reason.
- **`setSketchFont` also rewrites `--font-sketch`**, because the floating text editor is a real `<textarea>` that takes its family from that custom property — otherwise you would type in one hand and see another the moment you committed.
- **A `<canvas>` does not trigger a webfont download.** `ctx.font` with an unloaded family draws the fallback and never retries, and the only DOM node using the handwriting is that hidden textarea, so nothing requested it. `ensureSketchFontLoaded` asks `document.fonts.load` explicitly and repaints when it arrives — verified in a browser: choosing Kalam moves it from `unloaded` to `loaded` and the measured text width changes.
- **The picker exists twice** (`SKETCH_FONT_SELECTS`: the panel's «Lienzo» section and `#modal-text`, where you are looking while writing), both routed through the single `applySketchFont`. Options are built from the catalogue, never duplicated in the HTML, and each is labelled **in its own family** — in a list of names that is the only thing telling one handwriting from another.
- **Exports still fetch from Google Fonts, deliberately.** A `.svg` or `.html` export is a loose file that travels without the `fonts/` folder, so a relative path would break the moment it left; `FONT_URL()` builds the URL from the active family and offline the file falls back to the same stack. **`google: false` entries return `null`** and both exporters then omit the `<link>`/`@import` entirely — OpenDyslexic is not on Google Fonts, so the URL would have been a silent 404 inside every export. Any future self-made family needs that flag; a smoke guard pins the current list. The UI font is **OpenDyslexic** (chosen for dyslexia readability — a user accessibility choice, don't swap it), **self-hosted** in `fonts/`: four woff2 (Regular/Bold/Italic/BoldItalic) converted with fontTools from the user's official OTFs (classic Bitstream Vera-derived family; license file alongside, regenerated from the fonts' own name table). `@font-face` lives in `src/scss/base/_font-faces.scss` — weights 500/600 in the CSS resolve to 400/700 by CSS font-matching, and `dist/` gets `fonts/` copied verbatim. OpenDyslexic is wider than a typical sans: the sidebar buttons are sized so the longest catalogue word («Redondeado», ~58px at 0.9rem) fits on one line — 6.8rem button, no letter-spacing on the name, `min-height` so multi-line labels grow the button instead of overlapping the icon. Never reintroduce `overflow-wrap: anywhere` there (it splits words at arbitrary characters — «Rectán / gulo») nor a fixed button `height`; an e2e test in `responsive.spec.js` measures all three failure modes in both sidebar widths.
- **The `@use` order in `main.scss` is the cascade** — don't alphabetize. Each BEM block is one partial and carries its own media queries (base rule and its override travel together); `_scrollbar.scss` loads last because the original file ended with it. Order-dependent pairs: `.btn` → `.btn[hidden]`, `.panel` base → drawer media query, `.modal__shape-grid--three .modal__shape` (wins over the *later* `.modal__shape` by specificity — don't "fix" the order).
- **Vendor selectors never share a comma-separated group** (`::-webkit-slider-thumb` / `::-moz-range-thumb`): one unknown selector invalidates the whole group in both browsers. The shared body lives in the `range-thumb` mixin.
- **A comment between nested rules breaks nesting**: dart-sass traps it inside the parent's declaration block. That's why comment-dense partials (`_btn`, `_canvas-area`, `_modal`, `_panel-drawer`) use flat selectors and only comment-free stretches use `&__`/`&--`.
- Breakpoints are named in `src/scss/abstracts/_breakpoints.scss` (1201/1100/420/360) — the only place they may live; e2e and the docs below pin the sidebar one.
- stylelint is configured for the **legacy color notation on purpose** (`rgba(…)`, numeric alpha): the modern-notation autofix would rewrite every color and change the artifact's bytes. Don't "clean" that config without re-verifying the output.
- The v1.25.0 migration kept `.panel__select`'s `var(--text-main)` typo verbatim on purpose; v2.0.0 fixed it to `--text-primary`, and `tests/smoke.test.js` now asserts that **every custom property used in the compiled CSS is defined** — a wrong `var()` name fails nowhere by itself (SCSS, stylelint and the browser all stay silent).

### La interfaz va en MAYÚSCULAS (v2.29.0)

`src/scss/base/_uppercase.scss` pone en mayúsculas toda la interfaz. Se hace con **`text-transform`, nunca cambiando el texto del HTML**, y eso es lo que lo vuelve inocuo: `textContent` sigue diciendo «Cerrar», así que las guardas que leen el DOM (los `<legend>` de los modales, los rótulos del sidebar), las que leen `index.html` y cualquier comparación de cadenas de la app siguen valiendo — y revertirlo es borrar un fichero. Tres cosas que hay que saber:

- **Los controles de formulario NO heredan.** El navegador fija `text-transform: none` a `button`, `select`, `option` e `input` en su propia hoja, así que sin nombrarlos explícitamente se quedaban fuera todos los botones (topbar, «Limpiar todo», el «Cerrar» de cada diálogo) y todos los `<select>`: la mitad de la interfaz. Por eso el partial repite los cuatro contenedores con `button, select, option, label`.
- **Lo que escribe el usuario no es interfaz**: el rótulo de los componentes UI (`.panel__text`, `#ui-modal-label`), el editor flotante del lienzo y los campos numéricos se rescatan con `text-transform: none`. Verlo en mayúsculas mientras el elemento guarda otra cosa es un mando que miente. Una regla directa gana siempre a la herencia, así que da igual dónde caiga en la cascada.
- **Rompió el sidebar y hubo que recalibrarlo.** «RECTÁNGULO», «REDONDEADO», «AROMÁTICAS» y «TREPADORAS» ya no cabían en la columna estrecha del modo de dos columnas y se salían por los lados tocando al botón vecino; el cuerpo bajó a `0.8rem` con `letter-spacing: -0.02em` **sólo en ese modo**. La guarda de `e2e/responsive.spec.js` no lo veía: medía `scrollWidth > clientWidth`, y el rótulo crece a `max-content` con overflow visible, así que su caja nunca "desborda" — ahora compara además el ancho del rótulo con el del **botón**.

## Architecture

Scripts are plain `<script>` tags loaded in dependency order in `index.html` (config → sketchy → freehand → arc → curve-path → shape-rotation → regular-polygon → trapezoid → airbrush → flood → eraser → building → garden → solid → renderer → exporter → templates → app). There are no modules/imports — each file exposes a global (`TOOLS`, `Sketchy`, `Freehand`, `ArcMath`, `CurvePath`, `ShapeRotation`, `RegularPolygon`, `Trapezoid`, `Airbrush`, `Flood`, `Eraser`, `Building`, `Garden`, `Solid`, `Renderer`, `Exporter`, `Templates`) via IIFE, and later scripts rely on earlier globals. If you add a file, add its `<script>` tag in the right position (and, for the test harness, in `ALL_FILES`/`KNOWN_GLOBALS` of `tests/helpers/load.js`).

The app is state-driven immediate-mode rendering: a single `state.elements` array of plain objects is the source of truth, and any change triggers a full canvas redraw (`redraw()` in app.js). Elements are serializable plain objects (this is what JSON export/import round-trips), so never store functions or DOM refs on them. They are also treated as immutable: operations replace the element object (`moveElement` returns a copy) rather than mutating it, which lets undo snapshots be shallow copies (`state.elements.slice()`) — preserve that discipline when adding features.

- `src/js/config.js` — global constants: `TOOLS` ids, `TOOL_GROUPS` (drives sidebar build), `COLORS`, `CANVAS_W/H` (1200×800), `UI_DEFAULTS` (fallback sizes for UI components placed with a tiny drag). **`COLORS` is laid out, not just listed**: `.panel__color-grid` is `repeat(6, 1fr)`, so each run of six in the array is one visible row, and since v2.19.0 the 36 colours go tinta/neutros (dark→light, opening with the default `#1a1a2e`), then the vivos and the pasteles each sweeping the rainbow by ascending HSL hue, darkest first within one hue. A guard in `tests/config-templates.test.js` computes the hue and fails if a colour goes in out of order, if the total stops being a multiple of six, or if a vivo lands among the pasteles — and any e2e that clicks a swatch must address it by `[data-color="…"]`, never by index.
- `src/js/sketchy.js` — low-level "wobbly" hand-drawn primitives (line, rect, roundedRect, ellipse, arrow) using `Math.random()` jitter.
- `src/js/arc.js` — pure circular-arc math (`ArcMath`): fits a single cubic Bézier to an arc of a given sagitta over a chord (≤ 180°). A `curveArrow` with `arc: true` is a normal cubic whose controls were computed this way, so renderer/exporters/hit-test need no arc-specific code. The `TOOLS.ARC` sidebar tool ("Semicírculo") is creation-mode only — it is **not** an element type; it creates `curveArrow` elements that are always exact 180° semicircles (drag = diameter). Editing keeps the 180° invariant: `+/−` and the ctrl-handle drag change the radius via `resizeArc` (app.js), and endpoint drags preserve the shape through `transformControlsToChord`.
- `src/js/curve-path.js` — pure shared geometry for `curveArrow`, including chained curves. Historical single curves keep `x1/y1/cx/cy[/cx2/cy2]/x2/y2`; a chain also carries `segments`, an ordered, continuous array of quadratic/cubic Bézier objects, while top-level `x1/y1/x2/y2` mirror only the overall endpoints for connector anchoring. Use `CurvePath` for rendering, bounds, sampling, moving, scaling, reversing and endpoint/join editing so those mirrors never drift.
- `src/js/shape-rotation.js` — pure discrete rotation rules. `rotateElement(el, dir)` takes a direction (1 clockwise, the historical default and what `Shift+R` uses; -1 counter-clockwise, added in v2.23.0 for the `←`/`→` shortcut). **The two directions must stay exact inverses** — rotating and un-rotating has to give back the same object, `rotation` field *absent* rather than a stored 0, or a round trip would serialize differently from what was rotated (guarded for all nine types). `ShapeRotation.rotateElement` swaps a rectangle's `w/h` around its unchanged center for each 90° turn, and normalizes the `rotation` field of triangles/pentagons/hexagons/stars after 90°/36°/30° turns. A star's step is its polygon's, not `360/2n`: half a step lands on the same silhouette rotated onto itself. Unsupported types are returned unchanged.
- `src/js/regular-polygon.js` — pure geometry for `triangle`, `pentagon`, `hexagon` **and the two stars**: side counts, vertices, center-radius creation and real-silhouette containment. These elements use the standard `x/y/w/h` shape schema but must keep `w === h`; app resize enforces the square and import validation rejects deformed polygons.

  **The stars live here, not in a module of their own, and that is the whole design.** `star5`/`star6` **are** element types (unlike `arc`, Emoji or the Edificios/Jardín tools), and their silhouette is just one more polygon — concave, with **twice as many vertices as points** (10 and 12), alternating outer and inner radius. Sharing `vertices()` is what makes them inherit, without a line of their own, the hit-test, the eraser's real-silhouette reach, fill, «Bordes ocultos», the discrete rotation, the mandatory square box and both vector exporters. Four things to keep:

  - **The inner radius is canonical, not a taste knob**: `innerRatio(n) = cos(2π/n) / cos(π/n)` (0.381966 for 5, 0.577350 for 6) is the one where **extending a point's side lands exactly on another point**, so the outline is made of whole straight lines instead of a flower of straight petals. That is what gives the classic pentagram and Star of David; any other ratio draws a fatter or scrawnier star. Guarded by *"El radio interior es el canónico: el lado de una punta apunta a otra punta"*.
  - **The box stays the circumscribed circle's**, so a star's real bbox doesn't fill its square on the sides. Accepted deliberately: it's what keeps rotation, scaling and `w === h` behaving exactly like every other regular polygon.
  - **Even index = outer radius**, so a star is born point-up like the polygons are born vertex-up (`startAngle = -π/2`).
  - **Every type list that names the polygons must name the stars too** — `REGULAR_POLYGON_TYPES`/`SHAPE_TOOLS` (app.js), `OUTLINE_TYPES` (eraser.js), `OVERLAP_SHAPE_TYPES` (renderer.js), `VECTOR_TYPES` and the SVG `<polygon>` case (exporter.js). Missing one fails silently and differently in each: the eraser would use the bounding box, the export would drop the shape, «Bordes ocultos» would ignore it. They are pinned by *"Renderer, borrador y solapamiento tratan la estrella como una forma más"* and *"Exporter valida, exporta y reimporta las estrellas"*.

  They carry **no keyboard shortcut** — the 26 letters and 10 digits are taken, and `f q d s` are curve-arrow actions checked before `TOOL_KEYS` — same as Balcón, «Select» and the Aerógrafo; the exact keyless list is pinned in `tests/config-templates.test.js`.
- `src/js/trapezoid.js` — pure geometry and quarter-turn rotation of the isosceles `trapezoid` element (standard `x/y/w/h` schema, free proportions).
- `src/js/building.js` — pure geometry (`Building`) for the **Edificios** section (see below). `Building.elements(tool, p1, p2, opts)` returns an array of plain **existing-type** elements (`rect`/`line`/`circle`/`curveArrow`), so renderer/exporter/`isValidElement`/bounds need no building-specific code. - `src/js/airbrush.js` — pure geometry (`Airbrush`) for the **Aerógrafo**'s cloud of dots. Unlike `arc`/`building`/`garden`, `airbrush` **is** an element type (`type:'airbrush'`, in `TOOLS`, in the «Dibujo» group, **no shortcut** — no plain key is left). The element stores the **axis** (`points`, decimated at 2 px like the pencil) plus `radius` (nozzle), `density`, `lineWidth` (grain) and `seed`; the dots are regenerated here every time they're needed — canvas, all five exports, the modal thumbnail and the drag preview — so the JSON stays small and the five outputs cannot diverge. Seven rules, each of which broke or would have broken something real:
  - **The randomness is a FUNCTION, not a generator.** `_rnd(seed, seg, dot, channel)` is a stateless hash. `mulberry32` (sketchy.js) is a sequential stream, and that is exactly the *boiling* problem: change the number of dots in one span and the whole sequence shifts, so the cloud re-rolls on every frame of a resize — and on every point added while drawing. With a per-dot hash, growing the stroke only **adds**, and scaling moves the survivors affinely (guarded by two tests, each verified against its own mutation).
  - **`t` comes out of the hash, never from `i/n`.** That is what makes the surviving dots keep their position when the dot count of their span changes. The **deterministic dithering** (`_rnd(...,7) < fraction`) is what lets 2 px spans not force ≥1 dot each and blow up the real density of thin strokes.
  - **The radial spread is 2-D isotropic** (`rho = R·u^SPREAD`, uniform angle), not a perpendicular offset. A 1-D `R·rand**k` is singular on the axis for any `k>1` — it draws a hard bright line down the middle, the defect that makes a fake airbrush look like a highlighter — and leaves **square caps**. The 2-D version gives round caps for free (the union of discs along the polyline is a stadium; a click with no drag is a round puff) and makes **`radius` a hard bound**: no ink beyond R of the axis, which is what lets bounds, the area clip and the eraser's reach be exact.
  - **The cap is a target, not a cut.** `MAX_DOTS` degrades the *rate* through the factor `k`; a `break` would leave the end of the stroke blank. `estimate()` returns `capped` so the modal can say so instead of lying.
  - **`getElementBounds` returns the BAND** (`Airbrush.visibleBox`), the axis inflated by `radius` and intersected with `clip`. With the axis box the selection frame cut the cloud in half and the box hit-test lied. `hitTest` measures distance to the polyline for the same reason lines and arrows do.
  - **Resize is uniform**, like regular polygons and groups (`resizeTo` and `applyGeometry` both). The nozzle is one scalar; a box stretched on one axis would need an elliptical nozzle, which the model doesn't have. `radius` scales, **`lineWidth` (grain) doesn't** — its slider has a fixed 1–8 range and a resize that pushed it out of range would leave that control lying about what's drawn.
  - **The look was calibrated in a browser, not derived.** It shipped at grain 3 / density 45 and came out **speckled**, not sprayed: loose dots, no core. From grain 5 up the dense core with the faded edge appears. That is why the defaults are grain 5 / density 70 and `MAX_DOTS` is 6000 — at 3000 a long stroke at high density always hit the cap, so the mancha stopped thickening no matter what the slider said. Guarded in `tests/airbrush.test.js` (the shape properties) and `e2e/airbrush.spec.js` (real pixels).
- `src/js/eraser.js` — pure geometry (`Eraser`) for what an eraser stroke touches: `touches`/`doomedIndices`/`apply`, plus segment-segment distance with a crossing test. Everything that lives outside is injected via `deps` (`boundsOf`, `sampleCurve`, `polygonVertices`, `trapezoidVertices`) so the module stays DOM-free and testable; app.js supplies them in `eraserDeps()`. **Since v1.14.0 the eraser deletes elements instead of masking them** — the old `type:'eraser'` element was a `destination-out` mask fixed in canvas space, so moving the drawing slid it out from under the mask and the "erased" content came back (and still travelled inside exported JSON). The reach rule is **what you can see, not the bounding box**: for `OUTLINE_TYPES` shapes only the contour counts (box edges, sampled ellipse, or real polygon/trapezoid vertices) unless `el.fill` is set, in which case the interior is ink too — the interior of the **silhouette** (point-in-polygon over the same outline vertices), not of the bounding box: the bbox corner of a filled circle is ~15px away from any ink and must not erase it; text, images and UI components still use the box, because there the box *is* the drawing. Using the box for everything — the obvious "same as `hitTest`" choice — makes one sweep through the middle of a facade delete the whole wall. A generous box is right for *selecting* and far too aggressive for *erasing*. **Legacy `eraser` elements are still rendered, exported and validated** so older projects look unchanged, and `doomedIndices` skips them — deleting a mask would reveal exactly what it hides. Only the tool stopped creating them.
  **Since v1.22.0, `line`/`arrow`/`pencil` are recorded, not deleted, by `Eraser.erase(elements, pts, r, deps)`** (used by app.js instead of `doomedIndices`+filter): a touched line/arrow is resampled every `LINE_SAMPLE_STEP` (4px) and a touched pencil's own `points` are walked directly; `_survivingRuns` classifies each point as erased/kept and bisects the exact crossing at every transition, so what remains is whatever falls outside the circle, split into as many pieces as needed — this is what makes erasing through the middle of a line, or through where two strokes cross, only take the bit under the pointer instead of the whole element. An `arrow` piece only keeps its type (and head) if it contains the original tip (`x2,y2`) by reference — a run built from an interpolated crossing point never equals it — so a fragment cut away from the tip becomes a plain headless `line` rather than inventing a new arrowhead at the cut; a `heads:'both'` arrow keeps that flag only on a piece that still holds *both* original endpoints, which in practice means the split didn't really touch it. **Since v2.33.0 the same treatment reaches `curveArrow`, the `airbrush` and the outline of an unfilled shape** — before, grazing any of the three deleted it whole, which the user reported as "the eraser works with Pencil/Line/Arrow but not with the airbrush, the curved arrows or the shapes". Five rules hold that extension together:

- **A cut piece comes out as `pencil`** (`_asPencil`), built from scratch and never with `{...el}`: a `rotation` inherited by a pencil is **rejected** by `isValidElement` on import, and `w`/`h`/`fill` would be serialized garbage. `dash` is dropped too — the renderer doesn't apply it to a pencil, so copying it would draw solid while claiming dashed. `buildingGroupId` *is* kept: the fragment is still a piece of the same building/garden/solid. A curve's heads and label go with the cut, same reasoning as arrow→line.
- **A shape's outline is a closed RING, and its seam must be sewn back**: the ring is closed by repeating its first point, split, and the two runs sharing that seam are rejoined. Without it, erasing anywhere on a rectangle also broke it at the seam, into two pieces where the eraser never passed.
- **The ring and the reach must be the SAME outline** — `_shapeOutline` is shared by `touches` and `_splitOutline`, or the eraser would report touching one thing and cut another. The `roundedRect` grew a real rounded outline for this (`_roundedOutline`, at the renderer's 12 px radius); with the box outline its corners were cut square.
- **Everything is densified to `LINE_SAMPLE_STEP` before splitting** (`_densify`, keeping the original vertices *by reference* so the intact-check still works). A rectangle's outline is four points: erasing the middle of a side changes the classification of neither of its endpoints, so nothing was cut at all.
- **A FILLED shape still goes whole**: its drawing is a surface, and no element type can represent a bitten surface. The airbrush is the one that splits its **axis**, with the same `r + radius` margin as `touches` — that "full nozzle" is geometry, not caution: the surviving axis keeps spraying up to `radius` into the gap, so cutting at `r + R` leaves a clear gap of exactly `r`. With half a nozzle the measured residue in the gap was 7 % of the ink, i.e. a faint smear right where you just erased.

**Since v2.34.0 the UI section is erased by RASTER (`deps.rasterErase`, app.js)** — `text` (Texto and Emoji), `image`, `imagePlaceholder`, `button`, `input`, `nav`, `card`. There is no geometry to split there (a word is glyphs, a component is outline + label + tint, an image is a raster) and no element type can express "a button missing a corner", so the element is rendered offscreen exactly as `Renderer.renderElement` draws it, the stroke is punched out with `destination-out`, and what remains becomes an `image`. **The look is identical by construction** — it is the same drawing — at the price of no longer being editable as text or as a component. It's the same demotion ladder as arrow→line and curve→pencil, one rung further down. The user was offered the alternatives (text cut by letters + components whole; or precise reach only) and chose this. Six things it rests on:

- **It lives in app.js, not eraser.js**, because it needs a canvas and eraser.js is pure geometry. Without the dep — the `node:vm` harness, the exporters — the eraser falls back to whole-element delete, which is why *these* types can only be guarded in `e2e/eraser.spec.js`.
- **Comparing the ink before and after the punch is what gives exact reach for free**: if not a single pixel changed, the element is returned **by reference** and nothing happens. Crossing the empty middle of a card no longer deletes it, and there is no phantom undo step.
- **The preview cannot pay a `toDataURL` per frame** — and its decode is async, so the element would blink through the whole gesture. In preview mode the piece carries the live canvas in `bitmap`, which `Renderer._image` draws before looking at `src`. It never reaches `state.elements` (elements hold plain data, never DOM refs); the committed piece carries `src` instead. Same geometry both ways, so the preview matches the result exactly.
- **A half-decoded `image` renders as its dashed placeholder**, and rasterizing that would replace the photo with the placeholder. `Renderer.imageReady(src)` (which also warms the cache) gates it: not ready → return the element untouched.
- **The result is cropped to the remaining ink.** The raster is padded (Sketchy's wobble, the dashed frame, and above all the text shadow, which scales with the font size), so without cropping the new image would carry a wide empty margin and its selection box would lie.
- **A bitten PHOTO re-serializes as lossy WebP, never PNG** (v2.35.0): `toDataURL('image/png')` on photographic content multiplied its weight ×5-7, and two bitten photos blew localStorage's quota — every later autosave then failed inside a silent `catch` and work drawn afterwards was lost on reload. The choice keys on the *source* (`src` JPEG/WebP → WebP with the hole's alpha; line art — text, components — stays PNG, where it is smaller and crisper), with a prefix check because a browser without WebP support returns PNG silently; `IMAGE_SRC` (exporter.js) accepts `data:image/webp`. And the quota failure is no longer mute: `#autosave-warn` in the topbar lights while the save doesn't fit and clears itself when it fits again (`saveAutosaveNow` reflects the last attempt's real outcome).

**The whole per-frame cost lives in `eraserSession` (v2.35.0), born on the drag's first frame and thrown away on release** — nothing survives between passes, which is itself load-bearing: a WeakMap of pre-punch ink counts that outlived the pass returned stale counts after a canvas-font change, and a graze that erased *nothing* replaced the component with an image (auditoría v2.35.0). The session has two halves:

- **Geometric memos (`deps.session`, a Map keyed by element)**: the stroke only grows and an erased sample never un-erases, so `_survivingRuns` classifies each frame only against the NEW segments, `touches` retests only the stroke's new tail (with one point of overlap), and a stroke-bbox reject skips far elements before any sampling — sampled points are cached in the memo too, because the intact-by-reference checks compare run endpoints to them. Guarded by an equivalence test (incremental result ≡ full recompute) — the number (15.8 → 0.4 ms/frame; a 40-frame drag now costs what one frame used to) is a consequence, the equivalence is the correctness.
- **Raster previews (`eraserSession.raster`)**: one padded canvas per element, rendered once, punched incrementally (`destination-out` accumulates; each new segment stroked round-capped — the union equals the whole round-joined polyline). No pixel counts, no crop, no `toDataURL` in preview: the piece carries the live canvas in `bitmap` covering the whole padded box (transparent margins draw nothing). The commit (`rasterErase`, once per pass on release) computes fresh «antes»/«después» stats and crops, exactly as before.

`_erasedAt` rejects by segment bounding box before computing any distance — with the session on top, that inner clip only pays for the new tail. **Since v2.2.0 the split classifies with the same ink margin as `touches` (`r + lineWidth/2`)** — with bare `r` there was a band (between the axis and the stroke's edge) that "touched" without erasing anything visible yet still rebuilt the element; a graze that erases no sample now returns the element intact **by reference** (no phantom undo step, no silent de-anchoring), and a piece that keeps its original arrow endpoint keeps that endpoint's anchor (a piece demoted to `line` drops anchors — `resolveAnchors` ignores lines). The eraser's own size is `state.eraserSize`, edited **only** in `#modal-eraser` — `applyEraserSize()` is the single point that keeps the slider, the preview canvas and `state.eraserSize` in sync. Until v2.21.0 it had a second mando: the panel's stroke slider, *repurposed* (retitled "Tamaño del borrador", min/max swapped for `ERASER_SIZE_MIN/MAX`). **That whole slider is gone** — a control whose meaning changed with the active tool is exactly what the panel stopped doing; see "A tool's own settings…" below. **Selecting the Eraser tool opens `#modal-eraser` immediately**, same as Planta/Puerta/Balcón open their catalogue (`openEraserSizeModal()`, called from `selectTool`) — pressing the tool again reopens it later without leaving it (**since v2.21.0 that is the only way in from the panel side: «Trazo» has no ⚙**, see below). Unlike those catalogue modals, closing it does **not** revert to the tool active before: Eraser is already usable with its current size, there's nothing to "cancel" into. It is deliberately *not* added to `opensVariantModal`, for that same reason — same as Emoji.
- `src/js/garden.js` — pure geometry (`Garden`) for the **Jardín** section (see below), with plan and elevation renderers for vegetation. Two element types have no sidebar button: **`polygon`** — a free polygon defined by `points`, with its own fill and an optional contour (`stroke: false` draws only the fill). ### Adding a new element type

Requires touching several files in sync. The list below is the complete one — it was written after adding `polygon` (v2.25.0), because the short version this section used to carry omitted three things that are **not** optional today, and each of them fails silently:

1. **`TOOLS`** (config.js), plus a `TOOL_GROUPS` entry **only if it gets a sidebar button** — `image` and `polygon` deliberately have none. Never add it to `CREATION_ONLY_TOOLS` (exporter.js): that is the list of tools that are *not* element types, and putting a real type there drops it from `ELEMENT_TYPES` so nothing of it survives an export→import (the trap the AIRBRUSH comment warns about).
2. **A render case in `Renderer.renderElement`.** PNG/JPG come free from there.
3. **Creation logic** in app.js `onMouseUp` (and `UI_DEFAULTS` if it's a UI component) — unless another module emits it, as `Solid` does with `polygon`.
4. **`getElementBounds`** (app.js) if it isn't x/y/w/h-shaped. Skipping this is not a cosmetic bug: the fallback returns `{x: undefined, …}` and takes down selection, the marquee, `selectionBounds`, `applyGeometry` and the eraser's `boundsOf` at once.
5. **`VECTOR_TYPES` + a `case` in `_svgElement`** (exporter.js). Being in `VECTOR_TYPES` covers **both** SVG and HTML (the type goes inside the embedded `<svg>`), so the HTML `switch` needs nothing.
6. **A branch in `isValidElement`**, placed *before* the generic final `return`, which demands x/y/w/h > 0 and would otherwise reject the element on import. Copy the `pencil`/`airbrush` pattern for point arrays.
7. **`OUTLINE_TYPES` (eraser.js) + `eraserDeps()` (app.js)**, or the eraser works by bounding box — the "one sweep through a facade deletes the whole wall" defect that `OUTLINE_TYPES` exists to prevent.
8. **Decide about `OVERLAP_SHAPE_TYPES`** (renderer.js) explicitly. `polygon` stays out on purpose: `_box(el)` there assumes x/y/w/h and would silently yield `NaN`, and a solid's faces are precisely the ones that must read solid rather than dashed.

`moveElement`, `scaleElement`, `resizeTo` and `applyGeometry` need **nothing** for a type defined by a `points` array — their `m.points` branch is already generic. `tests/helpers/` needs nothing either unless you add a whole new module file.

### Panel controls: dual semantics

Panel controls follow an Excalidraw-style dual semantic: **with a selection they edit the selected elements** (immutable copies + one undo step per gesture); **without a selection they set the creation default** (`state.lineWidth`, `state.doubleHead`, `state.fillShapes`, …). `redrawNow` is the single sync point that pushes the right value back into each control (single selection → element's value; no selection → default; multi-selection → left untouched). Any future panel control inherits this question — follow the same pattern (see the stroke slider, the "Doble punta"/"Rellenar formas" checkboxes and the fill color picker in `wireControls`). **Since v2.9.0 the stroke colour picker follows it too** — which meant nothing already drawn could ever be recoloured; `showColor()` updates the swatches and the picker without touching `state.color`, so `redrawNow` can display the selection's colour without overwriting the creation default. **Since v2.10.0 the font-size slider was the last to join** (`applyFontSize`, same gesture-snapshot undo as `applyStrokeWidth`): with a `text` selected it resizes it live, without touching `state.fontSize`.

`#panel-sec-element` ("Posición y tamaño") is the one section that is pure element editing: X/Y/width/height plus the element's own text (`value` on a `text`, `label` on the UI components — `LABEL_FIELD`). It reads through `getElementBounds` and writes through `scaleElement` + `moveElement`, the same pair the handles and the drag use, so it works for **every** type (freehand strokes and multi-selections included) without a case per type and cannot drift from what dragging does. Four things it must keep:

- **It sits FIRST in the panel**, above «Trazo». It was added at the bottom and that alone made it useless: selecting something put the fields below Lienzo, Solapamiento and Zoom, off-screen on a normal window, and the feature read as "you can't edit anything". When a section only appears because something is selected, it is the most relevant thing on screen.
- **Typing a size must not permit what dragging a handle forbids.** A regular polygon needs `w === h` and `isValidElement` **rejects** deformed ones, so free width/height would produce a project that no longer imports; a group scales uniformly for the same reason (its pieces carry that invariant). `applyGeometry` mirrors `resizeTo`/`resizeGroupTo`: the side you just typed wins and the other follows.
- Scale before translate — the factor is relative to the *original* box.
- `syncGeometryControls` never overwrites the field that currently has focus, or typing "300" would be rewritten to "3" mid-keystroke.

Since v2.10.0 the X/Y/Ancho/Alto quartet also exists inside each of the four settings modals (`GEO_PREFIXES` = `el`, `stroke-modal`, `shape-modal`, `text-modal`, `ui-modal`): one `syncGeometryControls`/`applyGeometry(prefix)` body serves all five sets, so a measure typed in a modal obeys the exact same invariants as the panel. The modal blocks (`#*-modal-geo`) appear only with a selection, and their wrapper `<div>` is deliberately **classless** so the user-agent's `[hidden]` rule works without adding entries to the `_panel.scss` grouped rule. The wiring passes the prefix through a closure — passing `applyGeometry` directly as a handler would feed it the event as `prefix`.

Four hard-won rules inside `applyGeometry` (auditoría v2.10.1 — each has a BUGS.md entry and a guard; breaking any of them re-opens a real bug):

- **"Changed" is judged against what the field DISPLAYED** (`Math.round`), never against the exact box — otherwise every fractional box (any diagonal polygon drag; with the 120% auto-fit zoom, nearly everything) makes the untouched width "win" over the height the user just typed. When a field didn't change, the *exact* value is used, not the rounded one.
- **`Number('') === 0`**: an emptied (or garbage-typed) `type=number` field must count as "unchanged", or emptying Ancho collapses the element to 1px.
- **The no-op guard checks the *effect*** (`dx/dy/sx/sy`), not box equality: typing a height on a horizontal line (where `scaleElement` forces `sy = 1`) must not stack a phantom undo step, and the field must resync to the truth.
- **`geoFieldsFor` discards stale changes**: in a browser, clicking element B fires `mousedown` (selection changes) *before* the field's `blur`→`change`, so a width typed for A would land on B. The rAF resync always runs after the change, so the recorded selection identity catches it (e2e-guarded — the vm harness can't see this event order).

Reading and writing go through `selectionBounds()` — the combined box of ANY selection. `selectionGroupBounds()` stays group-only on purpose (it decides the single box *with handles*), but typing measures never needed the selection to be a building; multi-selections scale uniformly either way. And handles are drawn **only when the active tool is Mover** (`handlesOn` in `redrawNow`): with a kept selection and a creation tool, canvas gestures create — drawing scale handles there promised a resize that `onMouseDown` (whose handle hit-test lives in the SELECT branch) would never deliver.

### The panel is contextual (v2.9.0)

The panel's `<section>`s are shown or hidden by `syncPanelSections()`, called from `redrawNow` — the same single sync point. Sections: `#panel-sec-stroke` (always), `#panel-sec-fill` (a fillable tool **or** a fillable in the selection), `#panel-sec-text` (Texto/Emoji or a `text` selected), `#panel-sec-build` (`BUILDING_TOOLS`), `#panel-sec-garden` (`GARDEN_TOOLS`), `#panel-sec-canvas` and `#panel-sec-selection` (always). Two rows inside Trazo are contextual too: `#row-dash` and `#row-double-head`. **v2.21.0 emptied `#panel-sec-stroke` of everything that changed meaning with the tool**: the ⚙ that retargeted to five modals and the **stroke-width slider** (`#stroke-slider`/`#stroke-val`/`#stroke-label`), which with the Eraser became its size — retitled and re-ranged. What is left there is the colour palette and the two line modifiers, under a plain «Trazo» heading. The width now lives only in the five settings modals, where `#modal-text` gained its own (`#text-modal-stroke`) so a selected text isn't left without one. Each remaining section carries **its own ⚙**, except that one and `#panel-sec-canvas` (no modal holds its controls) — see "A tool's own settings…" below for the rule and for why only `#btn-element-settings` still needs a `hidden`. Before this, drawing with the pencil still showed "Plantas", "Cubierta del alzado" and "Ancho del camino" — 28 controls, of which ~10 applied. Below 1100px the panel is a drawer, so every extra control is paid in scroll.

Three things this rests on, each of which has already broken something:

- **It keys on the tool AND the selection, never the tool alone.** Fill, stroke and text controls have dual semantics, so with a rectangle selected `#panel-sec-fill` must be there even if the active tool is the pencil — otherwise selecting a shape stops letting you edit it, which is worse than the long panel. Guarded by *"las secciones reaparecen con la selección, no solo con la herramienta"*.
- **`hidden` does not hide anything that declares `display`.** `.panel__section`, `.panel__check`, `.panel__field` and `.panel__gear` all do, and that beats the user-agent's `[hidden]{display:none}` — the same trap that made `.btn[hidden]` necessary. They share one grouped rule in `_panel.scss`; **add any new `.panel__*` you plan to hide from JS to that group.** It has bitten four times, including the ⚙ from the day it was written (visible with every tool, opening the eraser modal from the pencil). The vm harness cannot see it — `hidden` there is a JS property, not CSS — so `tests/smoke.test.js` asserts all four compiled rules and `e2e/panel.spec.js` asserts real visibility. **Since v2.21.0 `.panel__gear[hidden]` is what hides `#btn-element-settings`, the only gear JS still hides** — don't delete that rule on noticing that the «Trazo» gear it was written for no longer exists.
- **Nothing was renamed or deleted.** `dom-stub.js` fabricates an empty `<div>` for an unknown id, so a renamed control fails as a confusing value diff instead of a missing element; and the Edificios/Camino twins are pinned by three guards. The reorganization only moves nodes.

`#modal-stroke` and `#modal-shape` are the drawing and shape tools' own settings, twinned with the panel through `syncStrokeControls()` / `syncShapeControls()` and opened from `selectTool` like every other configurable tool — see the rule below. `#modal-shape` also owns the **rotation** of the shapes that store it as an angle (`ROTATABLE_TOOLS` = the regular polygons, the two stars and the trapezoid; rect/roundedRect serialize a quarter-turn into their `w`/`h` and `isValidElement` **rejects** a `rotation` on them). `state.shapeRotation` is the creation default, snapped to the active type's `ShapeRotation.step` — 36° is not a valid hexagon orientation, and a trapezoid off a quarter-turn fails import validation. `creationRotation()` is the single source for both the drag preview and the committed element, and editing a selection goes through `rotateTo()`, which applies whole `ShapeRotation.rotateElement` steps rather than writing the angle directly — the trapezoid also swaps `w`/`h` on each quarter, so a raw write would leave its box out of line with its silhouette. Both sync functions write **both** sides (panel and modal): the dual-semantics handlers were extracted into named `apply*` functions (`applyDash`, `applyDoubleHead`, `applyFill`, `applyFillTransparent`, `applyFillOpacity`, `applyFillColor`, `applyStrokeWidth`) so the two control sets share one body, the way `wireBuildPair` does for the Edificios twins.

### A tool's own settings must open from the tool, not only from the panel

A control that is reachable only from the side panel is, in practice, unreachable: the panel sits far from the sidebar where the user actually clicked, it can be a hidden drawer below 1100px width, and nothing about clicking a tool button hints that an unrelated-looking control changed meaning somewhere else on screen. **v1.22.0 shipped the eraser's size control as a small ⚙ button inside the panel's stroke-slider section — technically wired correctly, invisible in practice.** The user clicked the "Borrador" tool expecting the size modal to show up right there, the way every other configurable tool (Emoji, Planta, Puerta, Ventana, Tejado, Balcón, and the eight Jardín tools) already opens its own modal from `selectTool` the moment it's picked — and reported it as broken.

The fix, and the rule going forward: **if a tool has a setting worth surfacing, wire it into `selectTool(id)` so picking the tool opens it**, following the existing `if (id === TOOLS.X) $('modal-X').showModal();` pattern (see `openEraserSizeModal()`). A panel control (twin slider, gear button, whatever) can still exist as a faster way to *reopen* or *live-tweak* it without leaving the tool, exactly like Fachada's twin panel fields — but it must never be the *only* way in, **and it must not change meaning with the active tool**: the panel's stroke slider did (it became the eraser's size, retitled and re-ranged) and that is why v2.21.0 removed it outright rather than moving it. Note one real difference from the catalogue tools: Emoji/Planta/Balcón etc. require a choice before the tool is usable, so cancelling their modal restores the previous tool (`opensVariantModal`, `state.toolBeforeModal`). The Eraser needs no such choice — it already erases at whatever size it has — so its modal is deliberately *not* registered in `opensVariantModal`, and closing it just leaves you on the Eraser, ready to draw (same reasoning as Emoji, which shares this trait).

**`#modal-stroke` and `#modal-shape` (v2.9.0) extend the same rule to the drawing and shape tools.** `STROKE_TOOLS` (Lápiz, Línea, Flecha, Flecha curva, Semicírculo) open the first from `selectTool`; `SHAPE_TOOLS` (the ten of Formas) open the second, which carries the whole **Relleno** block on top of the stroke — that panel section exists only for them. Both work exactly like the Eraser's size modal and, like it, are *not* in `opensVariantModal`: closing leaves you on the tool, ready to draw. Their live previews draw the real thing (a line vs an arrow; a pentagon vs a circle) with the current settings, so «Doble punta» is dimmed on a line and a filled pentagon looks filled before you drag. **Since v2.21.0 a panel ⚙ belongs to its section and always opens the settings of *that* section** — `#btn-element-settings`, `#btn-fill-settings`, `#btn-text-settings`, `#btn-build-settings`, `#btn-garden-settings`, `#btn-selection-settings`. Before that there was a single one, **in the «Trazo» heading**, that `syncPanelSections` **retargeted to five different modals** by `state.tool` and showed or hid with a six-branch condition: the same button, in the same place, opened five different dialogs and there was no way to tell which without pressing it. **«Trazo» is now the one section with settings and no ⚙, deliberately** — it was that button's house, and giving it one back is reopening the problem. Its three destinations are reached where they belong: pressing the tool in the sidebar (the primary way, which also works with the panel closed or drawered) and, with something selected, `#btn-element-settings`. «Lienzo» has none either, for the simpler reason that no modal holds its controls. What survives of the context-dependence is deliberately small and never changes a destination: «Texto» has two (`#modal-emoji` when the Emoji is active and nothing is selected, since that is where the slider's twin lives), and only `#btn-element-settings` still gets a `hidden` — it follows the **type of what is selected** (`TYPE_SETTINGS_MODAL`, the inverse of `MODAL_EDIT_TYPE`) and `settingsModalForSelection()` returns `null` when the types disagree, same rule as `commonOf`: don't invent a value they don't share. Everything else inherits its section's visibility. All of them call `open*Modal()` directly, so opening settings from the panel can never change tool or empty the selection; **«Edificios» and «Jardín» are the one exception and go through `selectTool` on purpose**, because a catalogue is rebuilt when it opens (its icons are painted with the live geometry, colour and stroke) and that rebuild lives inside `selectTool`. Two consequences worth remembering: `renderStrokePreview`/`renderShapePreview` now read the selected element's type before the tool's (those modals can be opened with any tool active, so a selected pentagon was previewing as a rectangle), and the guard that matters most is the textual one in `tests/smoke.test.js` — `dom-stub.js` fabricates an empty `<div>` for an unknown id, so a gear wired in app.js but missing from `index.html` passes every vm test and simply isn't there in the browser; that same guard pins which two sections must stay ⚙-less. **`#modal-stroke` was built the other way round first — not opening on selection, only the ⚙ plus a re-entry click — on the reasoning that the pencil is the most-used tool and a modal on every change would be in the way. The user rejected that: the promise "picking a tool shows its settings" is the whole point of the rule, and an exception for the most-used tool is where it matters most.** Don't reintroduce the exception.

**`#modal-text` and `#modal-ui` (v2.10.0) complete the rule for the UI group** — Mover and «Select» (v2.11.0) are now the only tools with no settings modal (the guards' "tool that opens nothing" baseline uses Mover). Texto opens the first (font-size twin of `#font-slider`, colour, preview); Botón/Input/Imagen/Navbar/Tarjeta share the second (`UI_MODAL_TOOLS`), retitled per tool by `syncUiControls()`, whose preview draws the real component via `Renderer.renderElement` scaled to fit (the nav is 600×50). Its **Rótulo** field goes through `applyLabel` — the same body as the panel's `#el-label` — and is dual: with a selection it edits the element's `label`; without, it writes `state.uiLabels[tool]`, the creation default the UI branch of `onMouseUp` stamps on new components (empty = renderer default; `imagePlaceholder` has no label and its row hides). `uiLabels` persists in prefs (known keys, strings, trimmed to 120 chars — they end up in `label`, which travels in exported JSON). Neither modal is in `opensVariantModal`.

**Pulsar la herramienta del elemento seleccionado lo edita (v2.10.0).** `selectTool` used to clear the selection unconditionally, so the settings modals could only ever configure creation defaults. Now `MODAL_EDIT_TYPE` maps each settings-modal tool to the **exact** element type it edits (pencil/line/arrow/curveArrow — the Semicírculo maps to `curveArrow`, which is what it creates —, the ten shapes, `text`, the five UI types), and the selection survives when it contains at least one element of that type; the modal then opens showing the selection's values, and the existing dual semantics do the editing — geometry included. Exact-type on purpose: "press the tool of the selected element to edit it" fits in one sentence, and pressing Rectángulo with a circle selected deselects like it always did. Starting any creation gesture on the canvas (`onMouseDown`, right after the SELECT branch) drops the kept selection — otherwise the panel would keep editing the old selection while you draw something new. Catalogues, the Eraser and Emoji still clear.

**The two Edición tools never clear it at all (`SELECTION_TOOLS`, v2.12.0).** Mover and «Select» are the tools that work *on* the selection — one moves, resizes and duplicates it, the other builds it — so neither empties it when picked, in either direction. They aren't in `MODAL_EDIT_TYPE` (they have no settings modal), so they were falling into the unconditional `setSelection([])` inherited from pre-2.10.0, and that broke the natural division of labour the moment «Select» existed: frame several objects with «Select», press Mover to move them, and the drag moved only the one under the pointer because the selection was gone. Guarded by *"seleccionar varios con «Select» y pulsar Mover los mueve TODOS a la vez"* — plus its reverse and a third guard pinning that creation tools still clear, so the fix can't drift back into "never clear".

**The UI components' renderer defaults are Spanish since v2.10.0** («Botón», «Escribe aquí...», «Título», nav «Inicio/Nosotros/Contacto») — they were English in an app whose UI was always Spanish. They are duplicated in exporter.js (SVG and HTML branches) and pinned by `tests/sketchy-renderer.test.js` and `tests/exporter.test.js`: change them in both places or the exports lie.

Two consequences of nearly every tool now opening something:

- **Returning to the "previous tool" after cancelling a catalogue would chain a second modal** on top of the one just closed. `selectTool(id, { silent: true })` selects without opening, and `wireBuildModalCancel` uses it: a previous *catalogue* still falls back to `TOOLS.SELECT` (reopening it would put you back to picking a variant, which is not what cancelling asked for), but a previous tool that only opens *settings* is restored silently. Dumping every case on Mover would be the easy path and the worse one. Guarded by *"cancelar un catálogo recupera la herramienta sin encadenar modales"*.
- **`e2e/helpers.js`'s `selectTool()` closes the five settings modals** (`SETTINGS_MODALS`: eraser, stroke, shape, text, ui) after picking a tool, because a `<dialog showModal>` makes the canvas inert and every drawing spec would otherwise time out. Catalogues are deliberately *not* in that list — those specs need to pick a variant. Specs that assert the *opening* click the sidebar button directly instead (`e2e/panel.spec.js`).

### «Select» (solo selección, v2.11.0)

`TOOLS.PICK` («Select», grupo Edición, entre Mover y Borrador) es una herramienta de **solo selección**: el clic selecciona con exactamente la misma semántica que Mover (grupo completo vía `groupIndicesOf`, Alt aísla la pieza, doble clic desciende, Shift hace toggle vía el helper compartido `shiftToggleAt`, y «Los clics acumulan selección» añade/retira), y el arrastre dibuja **siempre** marquesina — incluso naciendo encima de un elemento, el gesto que con Mover lo movería y que era imposible de hacer en un lienzo denso. Nada se desplaza jamás con ella. Cuatro decisiones que hay que conservar:

- **El gesto entero se resuelve en el bloque de marquee de `onMouseUp`** (vía `state.pickDown`): hasta soltar no se sabe si fue clic o marco, así que el `mousedown` no toca la selección — un clic necesita la selección vieja intacta para poder acumular o retirar, y un marco la sustituye él mismo con `setSelection`. Con Mover ese camino no se pisa: su clic se resuelve en `mousedown` y su marquesina solo nace en el vacío.
- **No dibuja handles** — `handlesOn` en `redrawNow` sigue siendo `state.tool === TOOLS.SELECT` a propósito: un handle promete un resize que el hit-test de PICK nunca haría (regla v2.10.1: no dibujar promesas que el mousedown no cumple).
- **El doble clic desciende a la pieza pero NO abre editores** ni resetea curvaturas: es una herramienta que no modifica nada. La rama `picking` del handler dblclick corta antes de los editores de texto.
- **Sin atajo** (las 26 letras y los 10 dígitos están cogidos — misma situación que Balcón). **Desde la v2.17.0 sí tiene modal de ajustes**, `#modal-select`, que se abre al elegirla como el de cualquier herramienta configurable: contiene «Los clics acumulan selección», que dejó el panel. **Lo abren las DOS herramientas de Edición** (`SELECTION_TOOLS`, v2.18.0 — la 2.17.0 lo reservó a «Select» y dejaba a Mover dependiendo del ⚙): la casilla gobierna el clic de ambas, así que ambas la enseñan. Lo reabre el **⚙ de «Elementos»** (`#btn-selection-settings`, v2.21.0 — antes era el de «Trazo», que solo estaba con las dos de Edición), y desde ahí se alcanza con **cualquier** herramienta puesta: la casilla gobierna el clic, no el dibujo. Consecuencia obligatoria: **las cuatro activaciones automáticas de Mover pasan `silent`** — pegar una imagen, pegar elementos, Ctrl+A y el retorno de un catálogo cancelado (`wireBuildModalCancel`). Ahí nadie ha pulsado la herramienta, y un `<dialog showModal>` dejaría inerte el lienzo justo después de pegar o de seleccionarlo todo; el del catálogo, además, encadenaría un modal encima del que se acaba de cerrar. Guardado por *"Ctrl+A y pegar no abren el modal de selección"* y *"cancelar un catálogo que cae en Mover no encadena el modal de selección"* (esta última verificada fallando al quitarle el `silent`). `#modal-select` no está en `opensVariantModal` (cerrarlo deja la herramienta puesta) y sí en `SETTINGS_MODALS` de `e2e/helpers.js` — sin eso, todo spec que use «Select» se cuelga con el lienzo inerte. **Cada modal cablea su propio botón «Cerrar»** en `setupModals`: olvidarlo no rompe ningún test del arnés vm (allí se cierra llamando a `close()`) y deja la app bloqueada en el navegador, así que la guarda vm cierra por el **botón**, no por la API. El cursor es `default` (`.canvas-area__canvas--pick`, CSS puro que el arnés vm no ve — guardado en `tests/smoke.test.js`), y desde la v2.36.0 el de **Mover** es `pointer`, la mano que señala con el índice —el gesto de su propio icono ☝️—, no las cuatro flechas de `move`: el `move` prometía desplazamiento incluso sobre el lienzo vacío, donde esa herramienta empieza una marquesina. Se usa el cursor nativo y no una imagen del emoji porque es nítido a cualquier densidad de pantalla y su punto activo cae donde debe; guardado en `tests/smoke.test.js` por el mismo motivo que el de «Select». El orden exacto del grupo Edición (`select`, `pick`, `eraser`) y su condición de única herramienta sin tecla del grupo están fijados en `tests/config-templates.test.js`; el comportamiento, en `tests/app-interaction.test.js` y `e2e/select-tool.spec.js`.

### Aerógrafo (v2.22.0)

La herramienta que aplica **tono** en vez de trazo. La geometría vive en
`src/js/airbrush.js` (reglas arriba); lo que hay que saber del resto de la app:

- **`CREATION_ONLY_TOOLS` (exporter.js) NO se toca.** Es el reflejo automático al
  añadir una herramienta y aquí sería justo el error: `airbrush` **sí** es un tipo
  de elemento, así que meterlo en esa lista lo sacaría de `ELEMENT_TYPES` y
  ninguna mancha sobreviviría a un export→import. Guardado por un round-trip.
- **Dos caminos de pintado, y el motivo de que sean dos.** En **sólido**, una sola
  ruta con N `arc()` y **un único `fill()`** (idéntico con círculos opacos: la
  unión, y mucho más rápido). En **translúcido**, `globalAlpha` + `fill()` **por
  gota**, porque ahí la acumulación de alfa *es* el efecto. Cada `arc()` necesita
  su `moveTo(x+r, y)` delante o la ruta sale cosida con rectas. En SVG lo mismo:
  `<g fill="…" fill-opacity="…">` con un `<circle>` por gota — **`fill-opacity`,
  jamás `opacity`**, que aplanaría el grupo antes de componer y mataría la
  acumulación (la divergencia lienzo↔export más fácil de colar). Agrupar además
  parte por la mitad el peso del `.svg`. Las tres cosas tienen guarda.
- **La ausencia del campo es el aspecto por defecto**, como con `bold`/`shadow`
  del texto: `opacity` solo se guarda si es < 1 (el mando al 100 % lo **borra**, y
  `isValidElement` rechaza `opacity: 1` igual que rechaza `dash: false`), y `clip`
  solo si hay área. Una mancha corriente serializa exactamente lo mismo que
  serializaría sin esta funcionalidad.
- **El área es un rectángulo, y su marco es overlay puro** (precedente:
  `drawPathAngle`): se limpia cada fotograma, no es elemento, no cuenta en
  «Elementos», no entra en undo, autoguardado ni exportación. El elemento sí
  guarda una **copia** (`{...state.airbrushArea}`, nunca la referencia: los
  elementos son planos y compartirla haría que mover una mancha moviera el área
  de la herramienta), y `moveElement`/`scaleElement` la llevan con él.
- **Armar el área CIERRA el modal**, y no es comodidad: un `<dialog showModal>`
  deja inerte todo lo de detrás, así que pedir un arrastre en el lienzo sin
  cerrarlo deja al usuario mirando una app que no responde — el síntoma exacto de
  la v2.16.2. Lo mismo vale para `#modal-airbrush` en `SETTINGS_MODALS` de
  `e2e/helpers.js`. Un arrastre por debajo de `MIN_AREA` **no cambia nada y sigue
  armado**: un clic torpe no debe perder el modo ni pintar una mancha que nadie
  pidió. Marcar el área **no lleva `saveUndo`** — es un ajuste de herramienta,
  como `state.eraserSize`.
- **Una mancha cuyas gotas caen todas fuera del área no se crea** (`isEmpty` en
  `onMouseUp`): sería un elemento invisible que cuenta en «Elementos» y viaja en
  el JSON.
- **El seed se fija en el `mousedown`** (`state.airbrushSeed`), no al soltar: la
  previsualización dibuja la nube de verdad con `Renderer.renderElement`, y con un
  seed nuevo por fotograma herviría. `drawPiecesPreview` **no** se toca: es de
  Edificios/Jardín.
- **El puntero es el círculo de la boquilla** (`cursor: none` + arco en
  `paintOverlay`, igual que el Borrador), y rodea la superficie **exacta**: las
  gotas se recortan en tamaño —`r = min(r, R - rho)`— para que la tinta acabe
  justo en `radius`. Se recorta el TAMAÑO y no la posición del centro a
  propósito: acotar el centro a `R - grano` daría el mismo borde, pero como el
  grano no escala con el dibujo la banda efectiva dejaría de ser proporcional y
  **las gotas se recolocarían al redimensionar** (lo probé: rompe la guarda del
  escalado afín). `onMouseMove` actualiza `lastPos` también en reposo para esta
  herramienta, como para el borrador, o el círculo se queda clavado.
- **La paleta vive en dos sitios** (`COLOR_GRIDS`): el panel y estos ajustes.
  `updateColorActive` consulta por **clase**, no por id, así que resalta el
  color activo en las dos sin saber que hay dos — pero cualquier test o spec que
  busque una muestra por `data-color` tiene que **acotar la rejilla**
  (`#color-grid .panel__color-swatch[...]`), o encuentra dos y falla en modo
  estricto. Ya mordió a `e2e/panel.spec.js` al añadir la segunda.
- **Los cuatro deslizadores no pueden ir por `applyStrokeWidth`** aunque el grano
  acabe en `lineWidth`: sin selección esa función escribe `state.lineWidth`, que
  es el grosor de los trazos, no el grano del espray. Comparten un cuerpo propio
  (`applyAirbrush`) con el mismo contrato de siempre: snapshot al primer `input`,
  commit en `change` **y** `pointerup`/`pointercancel`, `savePrefs` en el commit.

### Sólidos 3D (v2.24.0)

The **3D** sidebar group draws the ten «Formas» silhouettes in volume: **Prisma**, **Pirámide**, **Tronco** and **Esfera**, 31 figures in all. Like Edificios and Jardín, **every 3D tool is creation-mode only — none is an element type**, so `CREATION_ONLY_TOOLS` in exporter.js must include `...SOLID_TOOLS` or `type:'prisma'` becomes a phantom element on import.

**The whole design rests on one fact**: in cavalier projection the back cap is the front face *translated*, not deformed. So the front face is emitted as **the real 2D element of its section**, and inherits for free the fill with all its modes, the Sketchy wobble, hit-test and silhouette erasing, «Bordes ocultos», the `w === h` invariant and all five exports — **zero new code in renderer, exporter, eraser or bounds**. Everything else is `line`/`curveArrow`, the only types that accept `dash: true` (`renderer.js:621,629,650`); that is exactly why the back cap **cannot** be a shape element — some of its edges are hidden and some aren't, and a shape can't be dashed piecewise.

Rules that took work to get right:

- **Face visibility is the SIGN OF THE PROJECTED QUADRILATERAL'S AREA**, not `n·d`. `caraVisible(i) ⟺ sign(shoelace(Vᵢ, Vᵢ₊₁, V'ᵢ₊₁, V'ᵢ)) === −σ`, with `σ` the sign of the front profile's own shoelace (so it never depends on which way a module returns its vertices). It is equivalent to `n·d` for a prism but works **unchanged** for the frustum and the pyramid, where the lateral face is tilted and its 3D normal is no longer `(e_y, −e_x, 0)`; with the apex the "quadrilateral" degenerates into the right triangle and the shoelace still gets it. A back-cap edge inherits its lateral face's visibility; a connector is visible if **either** adjacent face is. Verified against the canonical cube and guarded by a test that dies if the rule is stubbed to `true`.
- **A tie (`area ≈ 0`) counts as VISIBLE.** It happens for real — a hexagon at 30° has an edge parallel to `d`, and its back copy lands exactly on top of the front one. Solid over collinear solid reads as a slightly thicker stroke and the wobble hides it; dashed over solid reads as a broken line.
- **`_occlude` is a required second pass, not a nicety.** After the face rule, any piece that still passes *behind* the front face is marked dashed (never deleted — it is hidden, and dashed is how this app draws hidden). It is needed because "front-facing" stops implying "visible" twice over: on the **concave** sections the back star lands inside the front star's notches at any usable depth (they only separate at `|d| ≳ 2R`), and with **`k < 1`** the cap shrinks toward the centre so the convex-prism proof no longer applies. It uses `RegularPolygon.contains`/`Trapezoid.contains`, shrinks the test shape by a 2 px margin (or a silhouette edge would test as "inside" by rounding) and samples interior points only, never the endpoints — a connector *starts* on the contour. Known limit: a partially-inside edge is classified whole.
- **Never `arc: true` on a 3D piece.** `app.js:2020` and `app.js:3337` re-normalize any element carrying that flag to an exact semicircle the moment an endpoint or the curvature handle is dragged, so a sphere's equator would snap to a semicircle on first touch. Elliptical arcs are emitted as a **chained cubic `curveArrow`**, split into ≤90° spans (α = 4/3·tan(Δt/4); one cubic per half-ellipse has 2.7 % radial error and visibly flattens the ends). `CurvePath.isValidSegments` demands **strict equality** at the joins, so the join point is computed once and reused by variable.
- **The round sections have closed forms**, no search loops: the cylinder's tangency is `T± = C ± (−rx²·dy, ry²·dx)/N` and its visible half is always `[t₊−π, t₊]` with `t₊ = atan2(ry·dx, −rx·dy)` — no branch. Cone and truncated cone are **the same routine**, tangents from the homothety's fixed point `H = C + d/(1−k)`, so `k = 0` (apex) is not a special case. The **cone has nothing hidden** and that is correct: its base is entirely visible because the body is behind it.
- **Degeneracy is clamped, never looped.** `ρ = hypot(dx/rx, dy/ry)`; below 1 the cone/frustum has *no* tangents (`√(ρ²−1)` is `NaN`), so `d` is scaled out to `ρ = 1.15`. The polygonal path has the analogous floor via `_rayBoundary`: **if the apex projects inside the base, every face is back-facing and the whole figure comes out dashed** — correct and unreadable at once.
- **`DEPTH_SCALE` is a calibration constant, not a fudge**, in the same spirit as the airbrush's grain 5 / density 70: looking down a solid's own axis collapses a pyramid's silhouette onto its base, so a pyramid needs about twice the depth a prism does to read at all. One slider still scales all three.
- **The sphere's equator is deliberately NOT sheared.** The strict cavalier equator is a sheared ellipse, which the app has no primitive for and which reads as a drawing mistake rather than as perspective; a sphere is rotation-invariant, so the equator's plane is free and the axis-aligned one is chosen.
- **Emission order is `[hidden, visible, connectors, FRONT]`**, so turning the fill on can never spoil the drawing: the front face covers whatever passes behind it.

**Giro, trazo y relleno (v2.25.0).** Cuatro añadidos que comparten una regla: los ajustes de una herramienta se alcanzan desde la herramienta.

- **`solidRotation` gira la SECCIÓN**, cuantizado con `ShapeRotation.step` al paso válido de su tipo, y se pasa tanto a `_profile` como a la cara frontal — si sólo llegara a la cara, las aristas seguirían naciendo de los vértices sin girar y el sólido se rompería. `Solid.isRotatableSection` deja fuera `rect`/`roundedRect`/`circle`: ahí girar es intercambiar `w`/`h` y `isValidElement` **rechaza** un `rotation` en esos tipos, así que su fila del modal se oculta en vez de prometer algo inerte. `_occlude` recibe la misma rotación, o mediría el recorte contra otra silueta.
- **`Shift+R` y `←`/`→` giran una figura compuesta entera** (`rotateAround`, app.js). Dos regímenes: si TODO lo seleccionado sabe girar sobre sí mismo, cada elemento gira su paso alrededor de su centro (el comportamiento de siempre); si hay algo que no —líneas, curvas, texto, caras—, gira el conjunto un cuarto de vuelta alrededor de su centro común. **El cuarto de vuelta no es estético: es el único ángulo que todos los tipos saben representar**, porque una caja no guarda ángulo. Las flechas se cobran el nudge horizontal del grupo, con el mismo consuelo de siempre (↑/↓, ratón y campos X/Y). Los extremos de nivel superior de una cadena se **copian** de los segmentos, nunca se recalculan, o `CurvePath.isValidSegments` los vería discrepar por un ULP.
- **Las caras laterales vistas se emiten como `polygon` con `stroke: false`.** Sin contorno porque las aristas se dibujan aparte, una a una, y cada una decide por su cuenta si va discontinua; con contorno saldrían dobles y las ocultas se volverían sólidas. Sólo las **vistas**: las de detrás quedarían tapadas en opaco y en translúcido sólo ensuciarían el tono.
- **El orden de emisión ES el resultado**: `[ocultas, caras, FRENTE, vistas]`. Las aristas vistas van **después** de la cara frontal — en una caja caen fuera de ella y el orden no se notaría, pero el ecuador de la esfera va por dentro y con el relleno delante desaparecía.
- **La esfera se queda fuera de `_occlude`**, y es el único caso: su ecuador es una línea sobre la superficie, no una arista de detrás.
- **Un sólido relleno lleva SIEMPRE `fillColor` explícito** (`o.fillColor || o.color`, en `_face` y `_frontEl`). Sin el campo, `Renderer.fillStyle` cae en el tinte clásico `color + '20'` —12 % de opacidad— que es retrocompatibilidad de las **formas planas**: ahí un proyecto viejo tiene que dibujarse igual. Un sólido es de la v2.24.0 y no tiene nada anterior que conservar, así que ese tinte sólo conseguía que el modo «sólido» saliera tres veces menos cubriente que el translúcido (40 % de fábrica) — el fallo de la v2.25.4. El color estampado es el que el selector del modal ya está enseñando (`hex6(fillColor || color)`), de modo que el mando y el dibujo dicen lo mismo. Sin relleno se conserva el `fillColor` elegido pero no se inventa uno derivado del trazo, o vaciar y volver a rellenar perdería el color.
- **Los mandos de trazo y relleno de los cuatro modales pasan por los `apply*` compartidos** (`applyStrokeWidth`, `applyColor`, `applyFill*`), así que heredan la semántica dual y el paso único de undo por gesto. `syncSolidControls` los vuelca leyendo la misma fuente que `syncShapeControls`, y se llama desde ahí **sólo si hay un modal 3D abierto**: con un `<dialog showModal>` delante el lienzo está inerte, así que repintar cuatro miniaturas no compite con nada, y cerrado no cuesta.

**De pie (`solidApex: 'upright'`, v2.27.0; el Tronco desde la v2.28.0).** El único sitio del módulo donde la cara frontal **no existe**: la sección se tumba sobre el suelo —su Y pasa a ser profundidad— y la figura se levanta sobre el plano del papel, así que todo son `line`/`curveArrow` y caras `polygon`. Lo ofrecen los dos remates de `Solid.UPRIGHT_TOOLS` (Pirámide y Tronco, mando «Eje» en «Proyección», estado compartido como la sección). **Es un solo cuerpo con el mismo factor de tapa `k` que `_extrude`**: la pirámide es `k = 0` —todos los puntos de la tapa colapsan en el ápice y las caras degeneran en los triángulos correctos—, y el prisma saldría de `k = 1`; se deja fuera junto con la esfera porque ahí el mando no cambiaría nada que valga la pena. **La tapa y la base son horizontales y sólo se ve una de las dos**, y no la decide el criterio de caras sino desde dónde se mira (`d.y < 0` ⇒ desde arriba ⇒ se ve la tapa): sus aristas van sólidas enteras, y con relleno hay que pintar esa cara **la última** o el tronco queda con un agujero por el que se ve el papel justo donde debería estar su cara de arriba. Seis cosas que sostienen el modo:

- **La ausencia del campo es el modo de siempre.** `solidApex: 'depth'` produce byte a byte lo que producía antes de que el modo existiera, y `_upright` sólo se alcanza desde la Pirámide — guardado comparando las dos salidas.
- **Sin cara frontal no hay de dónde reconstruir el gesto**, y regenerar es lo que permite rellenar o recolorear después (v2.25.2). Por eso `solidMeta` guarda aquí `apex`/`section`/`rotation`/`gesture`, **la única excepción** a "sólo lo que no se deduce" — y, como los puntos de inserción de `gardenMeta`, hay que llevarlo con la figura al **mover, escalar y girar**, o rellenarla la devolvería a donde se dibujó. Los cuatro campos entran juntos o no entran (`isValidElement`), para que no llegue un meta a medias que regenere cualquier cosa. **Desde la v2.30.0 llevan dos acompañantes opcionales, sólo de pie y con la ausencia como default**: `turns` (1–3) acumula los cuartos de vuelta pendientes de la figura — `_upright` sólo sabe construir figuras erguidas, así que `rotateAround` NO gira el gesto (ningún par gesto-girado/fuga representa una figura tumbada; girarlo hacía que regenerar la sustituyera por otra figura) sino que incrementa `turns`, y `regenerateSolid` reconstruye erguido, re-aplica esos giros alrededor del centro y recoloca sobre el centro en pantalla —, y `fillColor` conserva el color de relleno con el relleno apagado, porque de pie no queda ninguna cara que lo guarde. Y al regenerar, la rotación va **exacta** (`solidRotationExact`, sin la cuantización de `_rotationFor`, que es del mando): tras un cuarto de vuelta un pentágono está legítimamente a 90°, que no es múltiplo de su paso, y re-cuantizarlo lo saltaba a 108°.
- **El relleno lo dice una CARA, nunca una arista.** `regenerateSolid` lee `fill`/`fillColor` de la cara frontal si la hay y, si no, de cualquier `polygon`: preguntárselo a una línea daría siempre "sin relleno" y marcar la casilla no volvería a crear las caras nunca.
- **La punta sube hasta el borde alto del arrastre**, no una altura medida desde la base: así lo que arrastras es lo que ocupa. Con lo segundo, la fuga se sumaba por arriba y una pirámide dibujada a media pantalla se salía del lienzo.
- **La fuga usa la escala del prisma** (`DEPTH_SCALE` dobla la de la pirámide porque en el modo de siempre se la mira por su eje y se derrumba sobre su base); aquí la base se ve de lado y con esa escala saldría el doble de honda que ancha. Y tiene DOS suelos propios, no uno: el de longitud (con el escorzo y la profundidad al mínimo la base tumbada colapsa en una línea) y, desde la v2.30.0, uno para la componente **vertical** de la fuga — con el ángulo a 0°, 180° o 360° la base colapsaba igual aunque la longitud fuera de sobra, y la herramienta no dibujaba nada.
- **Una cara lateral es el cuadrilátero de `_faceVisible` con los dos últimos vértices colapsados en el ápice**, así que sirve el mismo criterio del signo del área — pero con el signo de referencia **cambiado**: en `_extrude` lo pone la cara frontal, que mira al observador, y aquí lo pone la base, que mira al suelo. Con `sigma` a secas la figura sale con las aristas de detrás sólidas y las de delante a trazos (el fallo de la v2.27.0). Una arista de la base hereda la visibilidad de su cara y una lateral se ve si se ve alguna de sus dos. La dirección de visión no se elige: la induce la propia proyección —un desplazamiento invisible cumple `δX = −dx·δZ`, `δY = dy·δZ`—, así que con la fuga por defecto se mira desde `(+X, +Y, −Z)` y lo que se ve es la cara de delante y la de la **derecha**.
- **En la redonda, la superficie vista se emite como UNA cara**, no una por muestra: el barrido arranca en un tramo oculto para que el corte del índice 0 no la parta en dos polígonos, que comparten borde y en translúcido lo dibujan doble.
- **La base redonda se muestrea (`UPRIGHT_ROUND_STEPS`) sólo para localizar la frontera** y se emite como **dos arcos**, no como 64 segmentos. El parámetro del arco es el **opuesto** del índice del muestreo (`ang(i) = −2πi/n`): `proj` invierte el seno al tumbar la sección, y con el signo sin cambiar los dos arcos salen intercambiados y el cono enseña justo la mitad que debería tapar.

**Editar un sólido ya dibujado (v2.25.2).** Un sólido no tiene un tipo de elemento propio, así que no cabe en `MODAL_EDIT_TYPE` (que empareja herramienta con tipo exacto). Su condición es otra: `selectTool` conserva la selección cuando `selectedSolid()` la reconoce como **una figura 3D completa** — todas las piezas del mismo `buildingGroupId`, todas con `solidMeta`, y **todas** seleccionadas (regenerar con media figura dejaría la otra media huérfana).

- **`regenerateSolid(cambios)`** vuelve a crear la figura con un ajuste distinto. Hace falta porque **las caras laterales son elementos y sólo se emiten al crear**: un sólido dibujado en hueco no las tiene, así que marcar el relleno después sólo pintaba la cara frontal y «el color de los lados» no tenía a qué aplicarse. Es el mismo recurso que `regenerateGardenGroup`.
- **El arrastre equivalente se reconstruye desde la CARA FRONTAL, no desde datos guardados**: ella da la sección (su `type`), la caja y el giro, y viaja con la figura, así que regenerar conserva dónde está y cuánto mide aunque la hayan movido, escalado o girado. Los polígonos regulares nacen del centro, de modo que se reconstruye ese gesto (`p2 = centro + (w/2, 0)`) y no la caja, o saldrían del doble de tamaño.
- **`solidMeta` guarda sólo lo que no se deduce**: el remate y la proyección (`{version, tool, depth, angle, foreshorten, taper}`). Por eso, al contrario que los puntos de inserción de `gardenMeta`, no hay que actualizarlo al mover ni al escalar. La única excepción es el **ángulo de fuga**, que sí gira con la figura: lo ajusta `rotateAround`, o rellenar un sólido girado lo devolvería a su orientación original.
- **Los deslizadores regeneran en `change`, nunca en `input`**: uno por tic del arrastre apilaría decenas de pasos de deshacer y expulsaría el historial de 50.
- **`syncSolidControls` lee con `commonOf`, no del único elemento seleccionado.** Un sólido son SIEMPRE varias piezas, así que con la lectura de uno solo caía a los defaults — y como corre en cada repintado, **desmarcaba la casilla de relleno justo después de marcarla**. Mismo fallo que `syncStrokeControls` en la v2.16.3, y misma solución.

Integration notes:

- **`drawPiecesPreview` needed two extensions** (app.js), and both are exactly the failure its own comment warns about — silent, and invisible to the vm harness. It now (1) sets `setLineDash` **per piece and in both branches** (inheriting `paintOverlay`'s global dash made every edge dashed in the preview and only half of them after release; fixing it also corrected a pre-existing incoherence in the Edificios/Jardín previews) and (2) delegates anything that isn't a line/rect/circle/curve to `Renderer.renderElement` — the front face is a `pentagon`/`star6`/…, so it simply wasn't drawn. It passes a **fixed seed** when the piece has none, or Sketchy falls back to `Math.random` and the wobble boils every frame. Guarded by `e2e/solids.spec.js`, verified failing against both mutations.
- **The three extrusion tools share `state.solidSection`** through `VARIANT_MODALS` (picking pentagon in Prisma leaves it picked in Pirámide); they differ only in catalogue, because the *name* of a section depends on the finish («Cubo» / «Pirámide cuadrangular» / «Tronco cuadrangular»). The **Esfera is not in the table** — there is no section to pick — so its modal is settings-only and opens like the Eraser's, and it needs its own «Cerrar» wiring in `setupModals`.
- **The icon box must be big** (`box: {x: 96, y: 76}`) even though the icon is 56 px: `roundedRect` carries a fixed 12 px corner radius, so a 30 px face came out fully round and its icon was indistinguishable from the cylinder's. Fitting by real bounds restores the size afterwards.
- **`syncSolidControls`/`renderSolidPreview` serve all four modals from one body** over a prefix table, the `GEO_PREFIXES` pattern; the slider ranges come from `Solid.*` and `tests/smoke.test.js` pins them against the HTML.

### Los modales de ajustes: ancho y paletas (v2.26.0)

Los **quince diálogos con miniatura** (`.modal__build`) llevan `modal--settings`, y esa clase es lo único que decide su ancho: `76rem` a partir de `$sidebar-2col` (1201px, el mismo breakpoint que pone la sidebar a dos columnas), con `.modal__build-fields` a dos columnas. Por debajo siguen en los `46rem` del modal corriente. Tres cosas que no se deducen del CSS:

- **La clase va en el `<dialog>`, y olvidarla no rompe nada visible**: el modal nuevo simplemente se queda estrecho con una columna larguísima. `tests/smoke.test.js` cuenta los `.modal__build` del HTML y exige el mismo número de `modal--settings`; `e2e/modal-palette.spec.js` mide el ancho real a los dos lados del breakpoint. Las fichas botánicas quedan fuera a propósito: tienen su propio ancho (`.modal--plant`, 72rem).
- **`align-items: start` en la rejilla de dos columnas no es cosmético.** Sin él cada celda se estira al alto de su fila, y un deslizador que comparte fila con una paleta aparece separado de su propio rótulo por seis filas de muestras.
- **Dentro de un modal la paleta fija sus columnas a `2.8rem`** (`.modal__palette .panel__color-grid`), no `1fr`. En el panel, que es estrecho, `1fr` deja las muestras justas; en un modal ancho las reparte por todo el ancho y la paleta deja de leerse como un bloque de color. Las **seis** columnas se conservan: cada tanda de seis de `COLORS` es una fila visible (ver `COLORS` arriba).

**Los modales de ajustes van por bloques (`modal--settings` + `.modal__group`, v2.26.1–2.26.2)** — los cuatro 3D, más trazo (Línea · Color), forma (Trazo · Relleno · Orientación), texto (Letra · Trazo · Sombra), componente (Contenido · Trazo), aerógrafo (Boquilla · Pintura · Dónde pinta), fachada (Edificio · Cubierta · Huecos) y muro (Muro · Verja de coronación · Entrada); «Posición y tamaño» es un bloque más. **Borrador, verja, cancela y camino se quedan sin bloques a propósito**: con uno o dos mandos, un único recuadro con título no organiza nada, sólo repite el título del diálogo. Los títulos exactos de cada modal están pinnedos en una tabla de `e2e/modal-palette.spec.js` — un recuento no habría visto un título equivocado. Dos reglas más: **un bloque no puede repetir su título en un campo de dentro** (por eso la cubierta de la fachada dice «Tipo» y el selector libre del trazo «Personalizado»), y **si el único mando de un bloque se oculta, se oculta el bloque entero** — `#shape-modal-rotation-row` pasó del `<label>` al `<fieldset>`, o quedaba un recuadro con título y nada dentro. Como `.modal__group` declara `display`, eso **exige** la regla `.modal__group[hidden]` (la trampa que documenta `_panel.scss`), guardada por un spec propio.

**Y en los cuatro modales 3D en concreto**: «Proyección» (a ancho completo, con sus deslizadores a dos columnas), «Trazo» y «Relleno», uno junto al otro. Son `<fieldset>` con `<legend>` de verdad — la agrupación tiene que llegar también a un lector de pantalla — y el **reset del fieldset es obligatorio**: su `min-width: min-content` nativo impide encoger dentro de una celda de grid y el bloque desborda la columna. El `<legend>` necesita `float: left; width: 100%` para salir de su flujo especial y participar en la rejilla. En cada bloque **el selector de color vive dentro de su `.modal__palette`**, no suelto: cuando iba aparte, rotulado «Otro color», los campos a dos columnas lo dejaban lejos de la paleta a la que pertenece. Guardado por *"los modales 3D agrupan sus mandos en Proyección, Trazo y Relleno"*, que además mide que ningún bloque desborde el diálogo.

**Las paletas son dos familias distintas, y esa separación es el punto.** `COLOR_GRIDS` (10 rejillas: el panel, el aerógrafo, los cuatro 3D y los cuatro de ajustes) pinta muestras `.panel__color-swatch` que aplican el **color del trazo**; `FILL_COLOR_GRIDS` (`#modal-shape` y los cuatro 3D) pinta `.panel__fill-swatch` que aplican el **relleno**. Comparten aspecto y no clase porque el resaltado del activo va **por clase, no por id** — `updateColorActive` marcaría las del relleno con el color del trazo. Cada familia tiene su función (`updateColorActive` / `updateFillColorActive`), y las llaman los mismos puntos de sincronía que ya volcaban los selectores nativos: `syncShapeControls` y `syncSolidControls`. Un clic en una muestra de relleno pasa por `applyFillColor` y **cierra su gesto en el acto** (`fillSwatchApply`), porque una muestra no arrastra por tonos intermedios: un clic, un paso de deshacer. Cualquier test o spec que busque una muestra por `data-color` tiene que **acotar la rejilla** (`#shape-modal-fill-grid .panel__fill-swatch[...]`) o encontrará varias y fallará en modo estricto.

### Emoji

`TOOLS.EMOJI` is creation-mode only, like `TOOLS.ARC` — **not an element type**. Picking the tool opens the `#modal-emoji` catalogue (built from `EMOJI_GROUPS` in config.js) — respecting `selectTool`'s `silent` flag, or cancelling a Building/Garden catalogue with Emoji as the previous tool would chain this one on top (auditoría v2.10.1) — and `placeEmoji()` stamps the chosen character as an ordinary `text` element centred on the click, at `state.emojiSize` — its own setting since v2.10.0 (the `#emoji-modal-size` slider in the catalogue, `EMOJI_MIN_SIZE`–`EMOJI_MAX_SIZE` = 32–96, persisted in prefs), no longer tied to `state.fontSize`: growing an emoji must not shrink the next text. With Emoji active and no selection, the panel's «Texto» section **retargets** to it (`#font-label` says «Emoji», the slider drives `state.emojiSize` through `applyEmojiSize`, min 32) — this is the last surviving instance of that pattern, and it is worth knowing that its twin, the stroke slider retargeted to the eraser's size, was **removed** in v2.21.0 for exactly the reason a retargeting control is suspect; before that retarget the section was a dead control for the Emoji, and pre-2.10.0 the slider *did* govern it. Both font sliders reach `EMOJI_MAX_SIZE` (96) so a selected big emoji doesn't overflow them. Because it is just a `text` element, rendering, hit-testing, resize, undo, autosave and all five export formats work with no emoji-specific code — keep it that way rather than introducing an `emoji` type. The catalogue is injected with `textContent`, never `innerHTML`.

### Edificios (sección)

The **Edificios** sidebar group draws a building's exterior. Like `TOOLS.ARC`/`TOOLS.EMOJI`, **every building tool is creation-mode only — none is an element type**; each drag produces plain `rect`/`line`/`circle`/`curveArrow` elements (via `src/js/building.js`), so render/export/undo/JSON/bounds work with no building-specific code. The one required sync point is `CREATION_ONLY_TOOLS` in exporter.js: it must include `...BUILDING_TOOLS` so `isValidElement` never accepts `type:'planta'`/`'puerta'`/… as a phantom element on JSON import. `paintOverlay` (app.js) draws the drag preview by calling `Building.elements` and stroking each `line`/`rect`/`circle`/`curveArrow` (helper `drawPiecesPreview`, which honours each piece's own `lineWidth`), so the preview always matches what is committed.

Every building tool opens a **shape-picker modal** on selection, mirroring the pattern (like `#modal-emoji`): **Planta** → `#modal-planta` (`PLANTA_SHAPES`, `state.plantaShape`), **Fachada** → `#modal-facade` (`FACADE_TYPES`, `state.facadeShape` = flat/gable/profile), **Tejado** → `#modal-roof` (`ROOF_TYPES`, `state.roofShape`), **Puerta** → `#modal-door` (`DOOR_TYPES`, `state.doorType`), **Ventana** → `#modal-window` (`WINDOW_TYPES`, `state.windowType`), **Balcón** → `#modal-balcony` (`BALCONY_TYPES`, `state.balconyType`), **Muro** → `#modal-wall` (`WALL_VIEWS`, `state.wallView`), **Verjas** → `#modal-fence` (`FENCE_VIEWS`, `state.fenceView`) and **Cancela** → `#modal-gate` (`GATE_VIEWS`, `state.gateView`). The first five are built by hand-written `build*Catalog`/`update*Active` pairs with inline-SVG icons (`plantaIcon`/`doorIcon`/`windowIcon`) — the arch uses an SVG path `A` command with **`sweep-flag=1`** to bulge up (y-down coords) — and their `update*Active` queries are scoped to their own catalogue (`$('planta-catalog').querySelectorAll(...)`) so the shared `.modal__shape` styling doesn't cross-toggle. **Balcón, Muro, Verjas and Cancela instead go through the generic `VARIANT_MODALS` table**, so their icons are the real geometry. Every catalogue is built with `createElement`/`createElementNS`/`textContent`, never `innerHTML`. The chosen state is passed into `Building.elements` as creation defaults; all nine tools persist their variant and applicable settings in prefs, validated against `BALCONY_TYPES`, `WALL_VIEWS`, `FORGE_TYPES`, `FENCE_VIEWS`, `GATE_TYPES` or `GATE_VIEWS`. Regression guards live in `tests/building.test.js`, `tests/app-interaction.test.js`, `e2e/fence.spec.js` and `e2e/gate.spec.js`.

**Balcón** draws a railing over a cantilevered slab in elevation, like Puerta and Ventana (8 types: barrotes/francés/forja/balaustrada/corrido/acristalado/terraza/mirador). Three things to know:

- **It is the only building tool whose default box depends on the variant**, because a mirador is tall and a balcón corrido is a strip, whereas a door measures the same whatever its type. `DEFAULTS` in building.js therefore gained a generic `variantKey`+`byVariant` resolution (the same idea garden.js uses for all its tools); only the balcony declares them. Guarded by *"el clic sin arrastrar da la caja propia de cada tipo de balcón"*.
- **The catalogue icon is drawn with a null drag on purpose** (`box: {x:0, y:0}` in `VARIANT_MODALS`), so `byVariant` picks each icon's box and the icon shows the type's natural proportion — which is what tells half the catalogue apart at that size. The garden entries keep their fixed 100×84 box.
- **It has no keyboard shortcut**, and neither do Muro, Verjas or Cancela: all 26 letters and 10 digits are taken, and `f`/`q`/`d`/`s` belong to curve-arrow actions checked before `TOOL_KEYS`. Pinned by *"el sidebar de Edificios y BUILDING_TOOLS son la misma lista"* in `tests/config-templates.test.js`, which also fixes the exact keyless list (`['balcon', 'muro', 'verja', 'cancela']`).

**Muro** draws a perimeter wall in either **plan view** (a footprint strip seen from above, like the sibling `#modal-plot` idea in Jardín) or **elevation view** (a face seen from the front, like Balcón). It combines a `VARIANT_MODALS` catalogue (2 entries, `WALL_VIEWS`, keyed by `wallView`) with settings orthogonal to that view: material (stone/concrete/**brick**), wall height (1/2 m), optional wrought-iron top railing with its own design and height, and one of **18 gate styles** plus «Sin puerta» and gate height. The precedent for this hybrid is **Camino** in Jardín (§ below), not a new pattern: `#modal-wall` gets a live thumbnail (`renderWallPreview`) and its own sync point (`syncWallControls`, called from `selectTool` right where `GARDEN_PATH` calls `syncPathControls`). **All settings stay enabled and visible in both views** — v2.3.1 fixed the opposite: dimming height and railing while the view was `plan` put them out of reach, because clicking a view commits and closes the modal. Treat that as the rule: in a hybrid catalogue+settings modal, a setting reachable only in the other variant is a dead end. Hence `_wallRailingPlan` (the handrail seen from above) and the plan footprint growing with declared height. **The height is the drawing's scale, not just its default box**: `_wallPxPerM` (`b.h` ÷ metres) drives course height, block width, concrete lifts and railing height, so «2 m» is visible at *any* drag size. Stone is irregular masonry from deterministic `_noise`; brick uses regular courses with alternating perpends; concrete stays visually plain apart from construction lifts. Because the default box depends on view and height, building.js derives `wallSizeKey` itself (`'plan1'`/`'plan2'`/`'h1'`/`'h2'`). The **entrance is a cancela, not a hole with bars**: two capped piers, leaves, defensive finials and a wall body split at the passage. The gate's own height is `o.wallGateHeight`, in metres on the `_wallPxPerM` scale (`#wall-gate-height`, clamped to `WALL_GATE_H_MIN/MAX`). `_wallGateRange` returns free span, pier width and the complete passage span that texture, railing and wall body must avoid.

The gate selector now contains **18 entries** from the shared `GATE_TYPES`: straight-bar `single`/`double`; nine concave styles (`concave`, `concaveSwan`, `concavePanel`, `concaveOrnate`, `concaveFan`, `concaveLyre`, `concaveDiamond`, `concaveRings`, `concavePalmette`); four monumental convex styles (`convexPanel`, `convexFan`, `convexMedallion`, `convexBlind`); and three urban portals (`solidTransom`, `openBars`, `openScrolls`). They remain ordinary `<option>`s in `#wall-gate-type`, because gate style is orthogonal to the plan/elevation catalogue. **The top railing's height and style are settings too** (`wallRailingHeight`/`wallRailingType`); the height is clamped to `WALL_RAIL_H_MIN/MAX`. The tool opens on `elevation` + `concave`; `wallDesignVersion` prevents historical default prefs (`plan` + `none`) from silently hiding that redesign.

**Verjas** and **Cancela** are autonomous siblings of Muro. Both use a hybrid modal: `FENCE_VIEWS`/`GATE_VIEWS` choose plan or elevation, while a `<select>`, a 0–350 cm slider and a live preview choose the model and physical height. `syncFenceControls`/`renderFencePreview` and `syncGateControls`/`renderGatePreview` are their single sync points. Verjas draws the 13 `FORGE_TYPES`; every design has a defensive finial and `_forgeFinial` gives each blade a distinct classical profile. Cancela draws all 18 `GATE_TYPES` without wall fabric by building its own opening and reusing `_wallGatePlan`/`_wallGateElevation`. Their independent prefs are `fenceView`/`fenceType`/`fenceHeightCm` and `gateView`/`gateType`/`gateHeightCm`; the exported module limits (`FENCE_H_MIN_CM/MAX`, `GATE_H_MIN_CM/MAX`) must match the HTML sliders and are pinned by `tests/smoke.test.js`.

`#modal-facade` is the one that carries more than a catalogue among the hand-written five, because Fachada is the only one of those with parameters. It holds a **live thumbnail** (`#facade-preview`) plus twins of the panel's four building fields (`#facade-floors`/`#facade-bays`/`#facade-roof-type`/`#facade-roof-pitch`), so a view can be chosen without hunting for the panel. Four rules keep it honest:

- **One opts builder.** `buildOpts()` is the single source for every `Building.elements` call — drag preview, commit, and thumbnail. Never inline a fresh opts object; a field added to one and not the others makes preview ≠ result.
- **Hole types belong here too.** `#facade-door-type`/`#facade-window-type` are filled by `fillVariantSelect()` from `DOOR_TYPES`/`WINDOW_TYPES` and write the same `state.doorType`/`windowType` as the Puerta/Ventana tool modals (calling their `update*Active` so both paths agree). Without them the facade flow could not reach the very types it draws — the Puerta/Ventana tools change the active tool.
- **One sync point.** `syncBuildControls()` pushes `state` into *both* control sets, refreshes the thumbnail and runs `updateFacadeFieldsEnabled()`. Every handler (panel *and* modal) calls it. Assigning `.value` fires no events, so the twins can't loop. The twin `<select>` options and slider range must stay identical — guarded by *"los controles gemelos de Edificios (panel y modal) ofrecen lo mismo"* in `smoke.test.js`.
- **The thumbnail reuses the real painter.** `renderFacadePreview(shape?)` calls `Building.elements` + `drawPiecesPreview` (the same pair the drag overlay uses) and fits the result by its own bounds — cornice, eaves and rasante fall outside the drag box. It paints `state.canvasBg` as paper first: the modal is dark and the drawing ink is not. Passing `shape` previews a view without selecting it (hover/focus).
- **Names promise nothing about the roof.** `FACADE_TYPES` entries carry a plain-language `name` plus the architect's term as `hint`; the Alzado icon draws the *active* `state.roofType` (`FACADE_ROOF_PTS`). Neither text may name a roof shape — `_gable` takes it from `state.roofType`, so "Alzado (2 aguas)" was a lie whenever hip/mansard was set. Guarded by *"el catálogo de Fachada no promete una cubierta concreta en el nombre"*.

`updateFacadeFieldsEnabled()` dims the settings the chosen view ignores (flat has no roof at all; profile always draws its own trapezoidal one, `_profile` never reads `roofType`). Clicking a view still commits and closes, as in the other four modals — only the parameters live-apply.

The **panel** has an "Edificios" section (`#build-floors`/`#build-bays`/`#build-roof-pitch`/`#build-roof-type` → `state.buildFloors`/`buildBays`/`roofPitch`/`roofType`) wired in `wireControls`. These are **creation defaults only** — building tools are creation-only, there is no "building" element to edit, so they do NOT follow the dual panel semantic (like the stroke-colour picker) and persist in prefs — as do the variants and settings of the nine building tools, so the whole section survives a reload or none of it does. Each of the four also exists as a twin inside `#modal-facade`; both sets are wired in pairs (`wireBuildPair`) against the same `state` and reconciled by `syncBuildControls()` (see above), so adding a fifth setting means adding it in **both** places or not at all.

Each building is created as a **group**: the `onMouseUp` building branch stamps a shared `buildingGroupId` (`newId()`) on every piece when a drag yields ≥2 elements. `groupIndicesOf(idx)` expands a hit to the whole group so a plain click selects the building as a unit (move/duplicate/delete already iterate `state.selection`); **double-click on a piece of the selected group descends to it** (the one-pointer way in, since v2.2.0 — the dblclick handler checks `selection.length > 1 && selection.includes(idx)` before falling through to the text editors), and **Alt+click** is the accelerator. The one-hand rule covers modifier+*click* chords too, not just modifier+drag: Alt+click as the *only* way in was an audit defect. Same pattern for disjoint multi-selection: the panel checkbox **«Los clics acumulan selección»** (`state.multiSelect`, not persisted — same as «Ajustar a cuadrícula») makes a click *add* the group and a **click without drag** on something already selected *remove* it (recorded as `state.pendingUnselect` in `onMouseDown` — also in the combined-frame branch, which captures those clicks — and consumed in `onMouseUp` only if `didDrag` stayed false, so dragging the selection keeps working); Shift+click stays as the accelerator.

Because a building is *always* a multi-selection, it interacts with the "drag the selection from anywhere inside its combined frame" convenience in `onMouseDown`: that frame covers the whole facade. **`hitTest` must run before that branch, and the branch must yield when the point lands on an element outside the selection** — otherwise anything drawn on top of a building becomes unreachable (click selects nothing new, drag moves the building, Delete deletes the building). Guarded by `tests/app-interaction.test.js`; the third test there pins the convenience itself, so don't "fix" a regression by removing it. `insertClones` reassigns a fresh `buildingGroupId` per cloned building (a copy is an independent group), and `selectionGroupBounds` draws one combined selection box. `isValidElement` (exporter.js) validates `buildingGroupId` as an `ID_RE` string so it survives the JSON round-trip.

Group **resize** works as a unit (v2.7.1). It was deliberately skipped when groups arrived, on the reasoning that resize could stay single-element — but once Edificios and Jardín made *most* of what you draw a group, that exception swallowed the feature: clicking anything you had just drawn gave a multi-selection, and multi-selections drew no handles, so in practice resizing had disappeared from the app. `selectionGroupBounds()` now draws its combined box **with** handles, and `resizeGroupTo` scales every piece through the same `scaleElement` used for one element. Three things to keep:

- **The handle hit-test must run before the combined-frame drag branch** in `onMouseDown`. The handles sit exactly on the corners of the frame you drag the group from, so with the other order grabbing a corner would move the group and there would be no way to scale it. Guarded by *"arrastrar por dentro del marco sigue moviendo el grupo, no escalándolo"*.
- **The group scale is UNIFORM**, unlike the free two-axis stretch a lone element allows. A group carries arbitrary pieces, and a free stretch would break invariants that belong to them: regular polygons require `w === h` and `isValidElement` **rejects** deformed ones on import, so a free scale could produce a project that no longer opens. Guarded by *"el resize de grupo conserva la proporción y no invalida las piezas"* — which also asserts the group actually grew, or it would pass vacuously by nothing happening at all.
- **`scaleElement` maps each element's own coordinates** (`mapX(el.x)`, `el.w * sx`) rather than snapping to the destination box. For a single element the two are identical, because `from` *is* that element's bounds; for a group member, assigning `to.x`/`to.w` directly would pile every piece onto the group's origin.

**Since v2.12.0 those handles belong to ANY multi-selection**, not only to a `buildingGroupId` group: `onMouseDown` and `redrawNow` take the box from `selectionBounds()` whenever `selection.length > 1`, and `resizeGroupTo` — already generic over `r.group`/`r.originals` — does the rest. Scaling "whatever is selected" never needed the selection to be a building, and typing measures had allowed it since v2.10.1, so the mouse was the odd one out. Two details that are deliberate: the scale stays **uniform** for the same invariant reason as groups (a hand-picked selection can contain regular polygons too), and a loose multi-selection keeps its **per-element highlights in addition to** the combined box — the box alone can't say *which* elements are selected, since it also covers gaps and neighbours. A building group still draws only the combined box: its pieces number in the dozens and it is manipulated as one thing.

**Panel controls show the selection's common value (v2.12.0).** The dual-semantics block in `redrawNow` used to sync only for a *single* selection, leaving every control stale with several — the panel showed the black and 2px of the creation defaults while three red 7px shapes were selected, even though touching a control did change all three. `commonOf(els, get)` returns the value all elements agree on, or `undefined` when they differ, and each control is computed over the elements it **affects** (arrows for «Doble punta», `FILLABLE_TYPES` for the fill block, texts for the font size) rather than over the whole selection. When there's no common value the control is left untouched: showing the first element's value would claim the others match it. Guarded by *"el panel enseña el valor común de la selección, y no lo inventa si discrepan"*.

**The rule binds `syncStrokeControls`/`syncShapeControls`/`syncTextControls` too, not just `redrawNow`** — they are the *twin* sync points, and two of them write into panel ids (`#check-dash`, `#check-double-head`). `syncStrokeControls` was the one that didn't obey it: with a multi-selection its `single` is `null`, so it fell to the creation defaults and wrote them into those two panel checkboxes, overwriting on every frame what `redrawNow` had just computed with `commonOf`. Having `#modal-stroke` open was enough for the false value to always win, because `syncPanelSections` re-calls the function at the end of each repaint — so three dashed double-headed arrows announced themselves as plain, and ticking the box stacked a phantom undo step (auditoría v2.16.3). Guarded by *"con varios seleccionados el panel enseña su valor común, no los defaults"*.

### Jardín (sección)

The **Jardín** sidebar group has eight **creation-only** tools (`GARDEN_TOOLS`) covering 68 variants. Plot, decor and paths are plan-only; the 50 tree/shrub/flower/herb/climber species support plan and elevation. Every drag still produces plain existing-type elements via `src/js/garden.js`. `CREATION_ONLY_TOOLS` in exporter.js must include `...GARDEN_TOOLS`, or a tool id becomes a phantom element. Grouping **reuses `buildingGroupId`**. Plant groups also repeat a strict, versioned `gardenMeta` record on every piece (tool, variant, insertion points, original color/line width and all botanical controls): `moveElement` shifts those insertion points, cloning preserves them under a new group id, and exporter validation whitelists every field/range so imported metadata is safe to regenerate.

Four things differ from Edificios and are deliberate:

- **One generic catalogue builder, not one per tool.** `VARIANT_MODALS` is a table of `{tool, modal, root, cls, data, catalog, key, gen, opts, box, plant?}` entries — the eight garden ones plus Balcón, Muro, Verjas and Cancela — driving `buildVariantCatalog(cfg)` / `updateVariantActive(cfg)` and the `selectTool`/`setupModals` hooks. `plant:true` installs the shared preview/view/stage/scale/color/label controls. `gen`/`opts`/`box` let non-garden tools join; `opensVariantModal(tool)` is the one predicate both hooks use. New catalogues should be added through this table.
- **Icons are the real geometry, not hand-drawn SVG.** `variantIcon(cfg, variantId)` paints a `<canvas>` with `cfg.gen().elements` + `drawPiecesPreview`, fitted by real bounds. The 68 icons therefore cannot drift from creation geometry. Plant modals also use `renderPlantPreview` on a larger canvas and expose live botanical dimensions. A plant icon's box comes from `plantIconBox()`: the species' **botanical proportion**, scaled so the longer side is `ICON_MIN_SPAN` (64 px). It must not be the raw click-sized box — at 20 px/m a 0.25 m *Acis valentina* came out 5 px wide, where every `Math.max(1.2, …)` floor in the geometry (there to keep petals from vanishing) takes over, the details collide, and fitting-to-bounds blows that smudge up to fill the tile. Two species then shared one icon; the caléndula, the tomillo and the boca de dragón had carried that smudge since v2.7.0. Guarded by *"los iconos de plantas usan la caja botánica, no un rectángulo genérico"*.
- **`drawPiecesPreview` (ex-`drawBuildingPreview`) must handle every type a creation tool can emit.** What's missing doesn't throw — it just isn't drawn, and preview stops matching the result. It had a latent bug on exactly this: chained `curveArrow`s have no top-level `cx`/`cy`, so `quadraticCurveTo(undefined, …)` was a silent no-op. It now walks `CurvePath.segments` and delegates `text` to `Renderer.renderElement` rather than re-implementing font/anchor/line-height.
- **Shortcuts are `8 9 h x z`** — the only five plain keys that were left, so **Caminos, Aromáticas and Trepadoras have none** (`key` is optional in `TOOL_GROUPS`), and any further garden tool arrives keyless too. `f`, `q`, `d` and `s` are already taken by curve-arrow actions that are checked *before* `TOOL_KEYS` and only when a `curveArrow` is selected; since every garden piece contains curves, reusing one would fail intermittently and silently. Pinned by `RESERVED_PLAIN_KEYS` in `tests/config-templates.test.js`, which also pins the *exact* keyless list, so a tool can neither lose its key in a refactor nor gain one that collides.
- **Two pitfalls in the `LOBES` tables** (`_blob`'s radius multipliers): a table that alternates high/low over few points has low-order symmetry and reads as a polygon — 8 points alternating gave a rhombus, not a clump. Over many points the same alternation is a *feature*: `carob` uses 14 for a scalloped crown. And two variants of the same tool must not differ only in their table, or they become indistinguishable at icon size (that was "Frondoso" vs "Olivo"); give them different structure instead. Guarded by *"dentro de un catálogo, dos variantes nunca se dibujan igual"* in `tests/garden.test.js`, whose signature is the element-type multiset **plus the overall aspect ratio** — proportion is a legitimate way to differ (Rectangular vs Cuadrada carry the exact same pieces), so a new variant must change one or the other.
- **Caminos is its own tool, and its two axes are four variants — not two panel checkboxes.** The camino comes in serpenteante/recto × liso/empedrado. They live as four catalogue entries because in this section the variant is what picks the default box and names the label; a checkbox would have neither. And they got their own sidebar button (`TOOLS.GARDEN_PATH` / `PATH_TYPES` / `#modal-path`) rather than staying in Decoración, where four near-identical strips filled half the catalogue and buried the rest. Guarded by *"los caminos viven en su propia herramienta, no en Decoración"*. `_pathTool` derives both axes from the explicit `PATH_VARIANTS` table (never by sniffing the id string) and computes the wave **once**, in `_at`, because the cobbles have to ride the exact same curve as the edges — a second copy of that sine is a guarantee they eventually drift apart. **By default, the drag is read as a box, and both the route and the thickness come out of it**: the long side is the route, the short side the thickness — so moving the mouse perpendicular while dragging fattens the path. That is the *only* way to get both from one gesture without a modifier key or a second step, and it is why a plain drag comes out horizontal or vertical. An any-angle version shipped briefly in 1.19.0 and was reverted in 1.21.0 because it took over the drag vector itself and, with it, the mouse-driven thickness the user preferred. **v1.23.0 reintroduced free angles as an opt-in, and v1.24.0 made that opt-in reachable with one hand.** The primary control is a **sticky setting**, `state.pathAnyAngle` — a checkbox that exists twice (`#path-any-angle` in the Camino catalogue, `#check-path-any-angle` in the panel), persisted in prefs. **A held modifier could not be the only way in: Shift+drag needs two hands, and the user this was built for has the use of one.** Treat that as a standing constraint, not a one-off fix — any future gesture whose only form is modifier+drag is a defect. `state.pathFreeAngle` (the Shift transient, mirroring `state.curveFlip`'s three touch points — `onMouseDown`, `onMouseMove`, and the drag-commit tail) survives as an *optional* accelerator, and `gardenOpts()` ORs the two. `elements()` picks `_pathAxisFree` over `_pathAxis` when `o.freeAngle` is set — same signature, same consumers (`_pathTool`/`_pathBox` don't change at all) — but `ux`/`uy` come straight from the raw drag vector and the width comes *exclusively* from `o.pathWidth`, exactly like a box-mode click or straight drag, because there is no short side left to read one from. **Unlike `curveFlip`, the angle flags are threaded into `gardenOpts()`** — the catalogue icons read it too, to keep the one-opts-builder discipline — so the Shift transient must be reset to `false` explicitly at the end of every `GARDEN_PATH` commit (the shared `onMouseUp` tail) rather than left for the next `mousedown` to clear; `curveFlip` never needs that because nothing icon-related reads it. The sticky flag can't be reset that way (it's meant to persist), so the Camino row of `VARIANT_MODALS` carries its own `opts: () => ({ ...gardenOpts(), freeAngle: false })`: **the icons are there to tell the four *trazados* apart (serpenteante/recto × liso/empedrado), not to show the angle**, and at 56 px a diagonal drawn at the panel's width — up to 120 px over a 95 px route — is a blob, the same reasoning that gave the row its fixed `box` in v1.20.0. What *does* show the live angle and width is `renderPathPreview()`, the `#path-preview` thumbnail beside them, built on the `renderFacadePreview` pattern (real geometry through `drawPiecesPreview`, fitted by real bounds, `state.canvasBg` as paper, reusing the `.modal__preview`/`.modal__build` CSS so the ≤420 px stacking comes for free). Its sample drag is deliberately **short-side-free** — dead straight, or a clean diagonal when the setting is on — because that is exactly the case where the width comes from the slider in *both* modes, so the thumbnail can never promise a thickness the drag then overrides. `syncPathControls()` is the single sync point for both twin pairs plus the thumbnail, same contract as `syncBuildControls()`. Finally, `drawPathAngle()` rotulates the live angle beside the pointer during the drag (protractor convention: 0° right, positive up, hence the negated `atan2` — canvas y grows downward). It is **overlay-only** — cleared with the rest of `paintOverlay` every frame, never an element, never in undo/autosave/export — and deliberately silent in box mode, where the path can only come out at 0° or 90° and the number would be noise. The cobble-flattening ratio (`rx`/`ry` in `_pathTool`) is a continuous function of `ax.ux`/`ax.uy` rather than a horizontal/vertical `if`, so a diagonal path never hits a visible seam at 45° — it reduces to the old fixed 0.82 ratio at the two angles box mode can ever produce, and to an almost-round stone on the diagonal. When the short side is under `MIN_SPAN` (a click, or a dead-straight drag) the width falls back to `o.pathWidth`, the panel setting — that is the setting's whole job. The drag-derived width is deliberately *not* clamped: there the user sees exactly what they draw. `elements()` still branches for `GARDEN_PATH` before the generic box, because its default is a *length*, not a size, and because `_pathBox(ax)` gives the label a box measured on the drawn band rather than on the drag. There is **one geometry, not one per orientation**: everything is computed in path coordinates (`u` = fraction travelled, `v` = offset from the axis) and `_p(u, v)` rotates it onto the canvas. **`v` is measured along the same direction `_wave` takes as its normal**, so `_at` applies unchanged either way and no stray sign can creep in between the edges and the cobbles — a bug that would be invisible in the horizontal case, which is why the guards check both. **The paving grows in rows, not in stone size** (`PATH_ROWS`/`PATH_ROW_H`/`PATH_SPREAD`): with two fixed rows a 90 px path was paved with half-metre boulders and read as a row of balloons. `PATH_STONES` caps the total, since `PATH_COLS` only bounds one row. Cobble size follows the path's *width*, like real paving, so the count grows with its length; `PATH_COLS` is only a flood guard, and past it the empedrado thins out rather than stopping half-way.

The **panel** keeps the global label switch and Camino's angle/width controls. Botanical defaults live in each plant modal and persist globally (`plantView`, `plantStage`, `plantScalePct`, `plantPxPerM`, `plantColorMode`, `gardenLabelMode`). A complete plant-group selection exposes `#btn-edit-garden`; `editSelectedGarden()` restores its metadata, and choosing a species calls `regenerateGardenGroup()` to replace the group at the stored insertion points with one undo snapshot. Cancel must clear `editGardenGroupId` without touching the original. Labels remain ordinary `text` elements inside the group.

**A settings modal's way out must survive the modal growing (v2.16.2).** `.modal__cancel` is `position: sticky; bottom: 0` so the close button stays anchored to the bottom of the dialog while its content scrolls. A `<dialog showModal>` makes everything behind it **inert**, so a close button pushed below the viewport doesn't just look bad — the canvas stops responding and the whole app reads as broken, which is exactly how the user reported it after v2.16.0 added three controls to `#modal-text`. Three details that took two attempts: `bottom` must be **0, never negative** (a negative offset restores the very permission to sit below the edge), a negative bottom margin lifts it and lets the next control peek through the gap, and since a sticky element anchors to its containing block's **content** box, a second blur-less shadow is needed to mask the dialog's 2.8rem of bottom padding. Guarded by `e2e/modal-fit.spec.js` at a deliberately short 1160×560 viewport — at `NARROW`'s 700 the modal fits and the guard would guard nothing; verified it fails when the rule is reverted.

### Text style: bold and shadows (v2.16.0)

`text` elements take three optional fields — `bold` (boolean), `shadow` (a `TEXT_SHADOWS` id) and `shadowColor` (hex) — and **their absence is the classic look**, so older projects render byte-identically. `Renderer.textFont(el)`/`Renderer.applyTextShadow(ctx, el)` are the single resolution point, mirrored by `_svgTextShadow`/`_htmlTextShadow` in exporter.js so the five formats can't drift. Seven things to keep:

- **Removing a style deletes the field, never stores it false.** `applyTextStyle` drops `bold:false` and `shadow:'none'` (plus its orphan `shadowColor`), which is what keeps an unstyled text serializing exactly as it always did instead of bloating every element in the JSON. Guarded by *"quitar el estilo lo BORRA del elemento, no lo guarda en falso"*.
- **Shadow measurements scale with `fontSize`** against `SHADOW_REF_SIZE` (18). A fixed 2px shadow is invisible on a 60px title. The SVG's `stdDeviation` is **half** the canvas blur radius — same number would come out twice as diffuse.
- **The hard shadow's offset is deliberately tiny (1px at the reference size).** With no blur to soften it, a larger gap stops reading as a shadow and starts reading as the word typed twice — which is exactly what 3px did on a 44px title. Verified in a browser comparing 3, 2, 1.5 and 1.
- **`isValidElement` validates all three**, because they end up in exported markup: an invented shadow id would put an arbitrary filter id in the SVG, and a non-hex colour is free text inside a style attribute. The HTML exporter also strips `;<>{}"'` from the colour rather than trusting that everything reached it through import validation.
- **Bold is only real where the family has a 700 cut** (Caveat, Kalam, Montserrat Alternates, OpenDyslexic); the other three are single-weight and the browser synthesizes. Never fake a 700 `@font-face` pointing at the 400 file — the browser accepts it and bold comes out *identical* to regular, which is worse than synthesis. That was Caveat's bug until v2.16.0 and `tests/smoke.test.js` now pins that no declared bold shares its file with the regular.
- **Every continuous control is ONE undo step per gesture, and a colour picker is a continuous control.** The native `<input type="color">` dialog fires an `input` per *tone crossed while dragging*, so a `saveUndo()` per event fills the 50-deep history with intermediate tones and evicts the user's actual work — silently. `applyTextShadowColor` shipped without the pattern in v2.16.0 and had to be fixed in v2.16.3; the fix is the same `snapshot()`-on-first-input + one `pushUndo` on `change` that `applyColor`, `applyFillColor`, `applyStrokeWidth`, `applyFontSize`, `applyFillOpacity` and `applyShapeRotation` already use (and the default is persisted on the commit, not per tone, or the drag hammers `localStorage` too). Guarded for **all three colour pickers at once** by *"ningún picker de color apila más de un paso de undo por gesto"*, plus a 60-tone drag (over the 50 limit) in *"un arrastre por el color de la sombra es UN paso de deshacer, no uno por tono"*.
- **Changing the shadow TYPE must not stamp the colour.** `applyTextShadowType` used to add `shadowColor: state.textShadowColor` to the patch, and the spread beat the element's own — but with a selection the picker writes to the *element*, not to the default, so `state` stayed grey and switching «suave»→«halo» reverted the red just chosen. A text with no `shadowColor` renders with `DEFAULT_SHADOW_COLOR`, which is exactly what the picker shows for it, so stamping nothing is what keeps control and drawing in agreement (and serializes leaner). Creation *does* stamp it, in `textStyleDefaults()`, where the default is what the picker shows. Guarded by *"cambiar el TIPO de sombra conserva el color propio del texto"*.

### Orden Z de la selección (v2.39.0)

Cuatro acciones para recolocar la selección en el apilado — al frente, adelantar, retrasar, al fondo —, la idea de Excalidraw. **El orden del array `state.elements` ES el apilado**, así que `reorderSelection(dir)` (app.js) es lo único nuevo: renderer, exportadores, «Bordes ocultos», la Tinta y el borrador no necesitan ni una línea. Cinco reglas:

- **La selección conserva SIEMPRE su orden relativo** (extraer y reinsertar, nunca ordenar): un edificio es un bloque contiguo y reordenarlo debe dejarlo contiguo y con sus piezas en el mismo orden interno — guardado pieza a pieza con una fachada.
- **'up'/'down' saltan UN vecino no seleccionado entero**, con barridos de intercambio (descendente para subir, ascendente para bajar), así que el bloque cruza al vecino de una vez en lugar de entremezclarse con él.
- **En el tope no pasa nada**: si el resultado es idéntico elemento a elemento, ni undo ni redraw — la regla del no-op de `applyGeometry`. Tras reordenar, `state.selection` se recompone buscando los MISMOS objetos por referencia (elementos inmutables).
- **Los botones son la rejilla `.panel__zorder`** (2×2, en «Elementos», ocultos sin selección) — la clase declara `display: grid`, así que está en la regla agrupada de `[hidden]` de `_panel.scss` (sexta vez que aplica la trampa).
- **Los atajos son `Ctrl/Cmd+↑/↓`** (un paso; con `Shift`, a los extremos), **flechas y no corchetes a propósito**: en el teclado español `[`/`]` exigen AltGr y la regla de una mano manda. El bloque corre antes del giro de `←`/`→` y del NUDGE en el keydown, y filtra `e.repeat` como ellos. Guardado en `tests/app-interaction.test.js` (pasos, extremos, undo sin fantasma, edificio como bloque).

### Guías de alineación al arrastrar (v2.38.0)

Al arrastrar una selección con **Mover**, sus bordes y centros se **imantan** (tolerancia `ALIGN_TOL` = 5 px en espacio lienzo) a los bordes y centros de los elementos no seleccionados, y una guía discontinua cruza el lienzo enseñando con quién quedó alineada — la idea de Excalidraw/tldraw. Todo vive en `alignAdjust()` (app.js), llamado desde la rama de arrastre de `onMouseMove` **antes** de `moveSelectionBy`, así que `clampDelta` sigue teniendo la última palabra en el borde. Cinco cosas que hay que conservar:

- **La guía es overlay puro** (precedente exacto: `drawPathAngle` y el marco del aerógrafo): `state.alignGuideLines` se pinta al principio de `paintOverlay` y se limpia con él cada fotograma — jamás elemento, ni undo, ni autosave, ni export. El `scheduleOverlay()` del mouseup es lo que evita que la última guía quede colgada tras soltar.
- **`free` acumula el delta CRUDO del puntero** (la sesión `state.alignSession`, nacida en el primer fotograma del gesto y muerta al soltar, como `eraserSession`): el imán corrige respecto a esa posición libre, así que al salir de la tolerancia el objeto vuelve con el puntero **sin zona muerta** — la misma razón por la que `dragLast` guarda la posición real y no la recortada.
- **Los candidatos se calculan una vez por gesto**, no por fotograma: los bordes/centros de lo no seleccionado no cambian mientras se arrastra. La excepción que lo haría mentira se excluye: una flecha **anclada** a lo seleccionado viaja con ello (`resolveAnchors`), así que no es candidata — sin eso el imán pegaba a su posición del primer fotograma, una coordenada ya vacía (auditoría v2.39.1).
- **El mando es «Guías de alineación» en `#modal-select`** (`state.alignGuides`, en prefs, **activa de fábrica**), y **Alt la suspende en caliente como acelerador, nunca única vía** (regla de una mano, mismo convenio que el snap a cuadrícula). Al contrario que «Los clics acumulan», sí persiste: es un modo de trabajo. **`free` acumula también en los fotogramas con Alt** — la salida temprana pre-acumulación hacía que al soltar Alt la selección saltara hacia atrás justo lo recorrido suspendido (auditoría v2.39.1).
- **Si el imán acaba de pegar, la cuadrícula NO re-snapea al soltar — pero solo EN SU EJE** (`alignSession.snappedX`/`snappedY` en el bloque de mouseup): gana la guía, que es más específica, y el eje donde no pegó nada sigue siendo de la rejilla — con un flag único, imantar la X dejaba la Y sin imán y sin cuadrícula a la vez (auditoría v2.39.1). Guardado en `tests/app-interaction.test.js` (imantado exacto con la casilla puesta, posición libre con ella quitada, y los tres casos de la auditoría).

### Lápiz con presión simulada (v2.37.0)

El lápiz puede dibujar con **grosor variable según la velocidad del gesto** — rápido = fino, lento = grueso, extremos afilados —, la idea de [perfect-freehand](https://github.com/steveruizok/perfect-freehand) (MIT) reimplementada en `src/js/freehand.js` (global `Freehand`, módulo puro: sin DOM, sin `Math.random`). El campo es **`taper: true` en el `pencil`, y la ausencia es el lápiz clásico** — un proyecto viejo serializa y se dibuja byte a byte igual. Seis cosas que lo sostienen:

- **El contorno se regenera donde se necesita** (renderer, export SVG, previsualización del gesto, muestra del modal) a partir de los mismos `points` de siempre — el JSON no guarda el polígono, igual que el aerógrafo no guarda sus gotas, así que los cuatro dibujos no pueden divergir. `Freehand.outline(points, lineWidth)` es determinista: mismo gesto, mismo polígono.
- **La envolvente respeta el grosor nominal**: el semiancho máximo es `lineWidth/2`, exactamente lo que ya ocupaba el lápiz clásico, y por eso bounds, hit-test y el alcance del borrador (`r + lineWidth/2`) valen sin tocarlos. No subas el tope «para que luzca»: romperías esa cota en tres sitios a la vez.
- **Se dibuja RELLENANDO el polígono, no trazándolo** — en el canvas (`fill()`) y en el SVG (`<path … Z" fill stroke="none"/>`). Un stroke del contorno daría el doble de grosor aparente y divergiría del lienzo. No pasa por Sketchy: el temblor ya viene en los puntos del gesto.
- **El borrador lo trata como a cualquier lápiz** (parte por `points`), y `_asPencil` (eraser.js) **copia `taper`** al fragmento: solo un `pencil` de origen puede llevarlo (`isValidElement` lo ata al tipo y solo en `true`, patrón `ink`), así que un trozo de curva convertido a lápiz nunca lo hereda por accidente.
- **El mando es «Trazo con presión» en `#modal-stroke`**, con la semántica dual de siempre (`applyTaper`: con lápices seleccionados los edita, sin selección fija `state.strokeTaper`, que persiste en prefs). Se **atenúa, no se oculta**, cuando ni la herramienta ni la selección son un lápiz — mismo criterio que el discontinuo. Quitarlo **borra el campo**, nunca guarda `false`.
- **La calibración es de navegador, no derivada** (mismo espíritu que el grano 5/densidad 70 del aerógrafo): `SPEED_SPAN = 4` está puesto para que, con la decimación de 2 px del lápiz, un trazo pausado vaya casi a ancho completo y un latigazo caiga a `MIN_W`. Guardado en `tests/freehand.test.js` (determinismo, cota de la envolvente, contraste lento/rápido, afilado de puntas, validación y SVG) y `tests/app-interaction.test.js` (default + semántica dual).

### Tinta: el bote de pintura (v2.32.0)

`TOOLS.INK` («Dibujo», sin atajo — no queda ninguna tecla plana libre, igual que el Aerógrafo) pinta con un clic, y hace dos cosas según dónde caiga: **dentro de una forma rellenable, le pone el relleno a ella misma**; **fuera, detecta la zona cerrada por los trazos que la rodean y crea una mancha nueva e independiente**. El caso que la originó es el rombo formado por varios trazos cruzados: una región que la app no tenía forma de representar, y a la que por tanto no se podía dar color.

**La mancha es un `polygon`, un tipo que ya existía** (v2.25.0, para las caras de los sólidos), así que renderer, exporter, eraser, bounds, move/scale/rotate y las cinco exportaciones no necesitaron ni una línea. Dos consecuencias obligatorias, y son las dos trampas del alta:

- **`ink` va en `CREATION_ONLY_TOOLS`** (exporter.js). Es el reflejo contrario al del Aerógrafo: aquél SÍ es un tipo y meterlo ahí lo borraría al importar; éste NO lo es, y dejarlo fuera haría que `type:'ink'` entrara como elemento fantasma.
- **`fillColor` siempre explícito**, o `Renderer.fillStyle` cae en el tinte del trazo al 12 % — el fallo exacto de la v2.25.4.

La mancha lleva además **`ink: true`**, y no es decorativo: es lo que hace que **una mancha previa no sea barrera** (si lo fuera, repintarla para cambiarle el color sería imposible) y lo que la distingue de una cara de sólido, que también es un `polygon` sin contorno y sí debe frenar la pintura. `isValidElement` lo valida atado a `polygon` y sólo en `true`, con el criterio de siempre: la ausencia es el valor normal.

**`src/js/flood.js` (`Flood`) es geometría pura**: por su frontera sólo cruzan `Uint8Array`, números y listas de `{x,y}` — nunca un ImageData, un contexto ni un elemento —, y por eso `tests/flood.test.js` la prueba con máscaras escritas a mano, sin stub de canvas. Rasterizar es cosa de app.js. Cinco decisiones que sostienen el resultado:

- **Marching squares para el contorno**, no seguimiento de borde: recorre las *grietas* entre píxeles (borde real a medio píxel, no medio píxel adentro), atraviesa los apéndices de 1 px sin caso especial —abundantísimos tras un flood contra trazos con antialias, y donde Moore se atasca— y devuelve escaleras alineadas con los ejes, que es el input ideal de Douglas-Peucker.
- **DP sobre anillo cerrado**, partido por dos anclas estables; sin ese corte puede colapsar el anillo a un triángulo. Un rombo sale con 4-8 vértices y una curva sigue lisa. Guardado que **subir epsilon nunca añade vértices**, que es lo que hace terminar el bucle del tope de 300.
- **La fisura**: el flood se para en el borde interior del trazo, así que la mancha nacería separada de la línea. Se arregla **dilatando la región antes de extraer el contorno** (`inkRadius = lwFrontera/2 + gap/2 + 1`), nunca desplazando vértices —en un polígono cóncavo eso se autointerseca—. Pasarse es gratis (la mancha va debajo de los trazos); quedarse corto se ve. Medido: con la dilatación quedan 1-3 px de antialias, sin ella 10 px de papel.
- **El escape corta en cuanto un tramo toca el borde del lienzo**, así que una zona abierta se descarta en microsegundos. El borde NO se trata como barrera: si lo fuera, la pintura "cerraría" contra el papel y llenaría el lienzo entero.
- **Si el clic cae sobre un trazo se prueban varios píxeles libres de alrededor**, no el más cercano: el más cercano puede estar al otro lado de la línea, y entonces la pintura se escaparía por una zona que nadie señaló. Se prueban en orden y gana el primero que dé una zona cerrada; sale barato precisamente porque una fuga se detecta al instante.

En app.js: `inkBarrierMask()` rasteriza con **`renderElements` en modo `normal`** (nunca `renderScene`, que estampa el fondo opaco y dejaría todo en barrera, ni `hidden-dashed`, que trocea contornos y abre fugas), **excluye lo que lleva `ink`** y **rasteriza continuo lo discontinuo** (si no, la pintura se escapa por los huecos del propio trazo). La máscara se cachea comparando la escena **por referencia elemento a elemento** — basta porque los elementos son inmutables, y no puede dar un falso «no ha cambiado». La mancha se inserta con `splice` **por debajo** del elemento más bajo al que toca (con `push` taparía los trazos y robaría los clics de su interior), y **repintar la misma zona sustituye la mancha en su sitio** en vez de apilar otra, comparando las cajas de los dos ELEMENTOS —nunca la de la región, que no incluye la dilatación y por eso no reconocería ninguna gemela.

**El color de la Tinta ES el color de relleno de la app**: no estrena ajuste propio, reutiliza `state.fillColor`/`fillTransparent`/`fillOpacity` y sus `apply*`, con la semántica dual y el «un paso de undo por gesto» ya resueltos. Su rejilla va en **`FILL_COLOR_GRIDS`**, no en `COLOR_GRIDS` (el resaltado va por clase, y `updateColorActive` la marcaría con el color del trazo). Ajustes propios: `inkGap` (0-12 px, cierra huecos) e `inkTarget`, ambos en prefs. Tres extras en el modal: cuentagotas —que **cierra el modal al armarse**, porque un `<dialog showModal>` deja inerte el lienzo (el fallo de la v2.16.2), y **Alt+clic queda como atajo opcional, nunca como única vía**—, pintar la selección y sustituir un color en toda la escena; los dos últimos, un solo paso de undo. **`hex6` normaliza a minúsculas** (v2.35.0): la validación de import acepta hex en mayúsculas, y sin normalizar, «Sustituir un color» listaba `#FF0000` y `#ff0000` como dos colores y sustituía la mitad. **Elegir la Tinta conserva la selección si contiene algo rellenable**, o su propio botón «Pintar lo seleccionado» sería inalcanzable.

Limitaciones asumidas y documentadas: una región con islas se pinta entera (`polygon` es un anillo único; `Flood.countHoles` las detecta y el modal avisa); **la mancha no sigue a los trazos** si los mueves — es la contrapartida de ser un elemento independiente; con tolerancia alta y trazo fino puede sangrar 1-3 px al otro lado; y el aerógrafo es poroso por construcción.

### Shape fill

Only `FILLABLE_TYPES` (rect, roundedRect, circle, trapezoid, square, triangle, pentagon, hexagon and the two stars — it spreads `REGULAR_POLYGON_TYPES`, so a new regular polygon joins by existing) take a fill; UI components carry their own as part of their design. Four fields control it: `fill` (boolean, on/off), the optional `fillColor` (hex), the optional `fillTransparent` (boolean), and the optional `fillOpacity` (number from 0 to 1, defaulting to 0.4 when absent). They are deliberately independent — the "Rellenar formas" checkbox toggles `fill` only and never touches the others, so emptying and refilling a shape recovers the same color, mode and opacity. "Relleno translúcido" and the opacity slider have the standard dual panel semantics: with a selection they update selected fillable shapes, using one undo step per slider gesture; without a selection they set creation defaults. Solid mode is represented by the absence of `fillTransparent`, preserving backward compatibility.

`Renderer.fillStyle(el)` is the single place that resolves these fields. Transparent mode converts `fillOpacity` to an 8-bit hex alpha and applies it to `fillColor || color`; otherwise it uses `fillColor || color + '20'`. A translucent shape without `fillOpacity` must remain at the legacy 40% (`0x66`). Therefore **a shape without `fillColor` keeps the classic translucent stroke tint**, and older projects render identically — preserve both fallbacks. SVG and HTML exports mirror this resolution. `isValidElement` validates `fillTransparent` as a boolean, `fillOpacity` as a finite number in `[0, 1]`, and `fillColor` as hex because they affect serialized/exported output.

### Shape overlap mode

`state.overlapMode` is a global scene setting with two valid values: `normal` (default and backward-compatible) and `hidden-dashed`. `Renderer.renderElements(ctx, elements, mode)` must be used for whole-scene rendering so it can compare geometric shapes by z-order. In hidden mode it samples the real outlines of rect, roundedRect, circle/ellipse, square, trapezoid, triangle, pentagon, hexagon and star shapes (`OVERLAP_SHAPE_TYPES`), assigns every covered segment to the highest later shape containing it, draws visible segments solid, and defers hidden segments until after that covering shape's fill. Only hidden segments use `[4 * lineWidth, 4 * lineWidth]`; the upper outline stays solid.

The setting is persisted in prefs, autosave and exported JSON (`settings.overlapMode`). `Exporter.importJSON()` keeps its array return API and exposes the imported mode as the non-enumerable `elements.overlapMode` property. PNG/JPG call the coordinated renderer; SVG and hidden-mode HTML use the same overlap plan. Old autosaves (bare element arrays) and JSON without settings resolve to `normal`.

### `←`/`→` rotate instead of nudging (v2.23.0)

With a selection where **every** element stores its orientation as an angle (`ROTATABLE_TOOLS`: the regular polygons, the two stars and the trapezoid), `ArrowLeft`/`ArrowRight` step through valid orientations instead of nudging 1 px; `↑`/`↓` still nudge, and any other element in the selection returns all four arrows to nudging. It sits **before** the `NUDGE` block in the keydown handler. Four decisions, each deliberate:

- **It costs those shapes their horizontal nudge**, and that was the user's explicit call when offered the alternatives (`Shift+←/→`, or only-when-a-single-shape). The mouse, `↑`/`↓` and the panel's X/Y fields all still move them.
- **`every`, not `some`**: with a rectangle or a text in the selection, what the arrows do would otherwise depend on what the group happens to contain.
- **`rect`/`roundedRect` are excluded** even though `ShapeRotation` handles them: there "rotating" is swapping `w`/`h`, which isn't worth losing their nudge for. So the set is `ROTATABLE_TOOLS`, not `ShapeRotation.isType`.
- **Auto-repeat is filtered** (`e.repeat`), like `NUDGE` and the F/Q/D/S toggles: holding the key would spin the shape and stack ~30 undo steps a second, evicting the 50-deep history. `preventDefault` runs *before* that check — `←`/`→` are also the canvas area's horizontal scroll, and a held key must not slide the canvas either. `e2e/rotate-keys.spec.js` guards exactly that (in `NARROW`, where the canvas overflows and there is scroll to lose; in `WIDE` it fits and the check would be vacuous).

### Coordinate handling

Zoom is applied as a CSS `transform: scale()` on the canvas wrapper; `getPos()` in app.js divides mouse coordinates by `state.zoom` so element coordinates are always in unscaled canvas space. A `transform` does **not** grow the layout box, so `.canvas-area__sizer` wraps the canvas and `applyZoom` sets its width/height to `CANVAS_W/H * zoom`; the wrapper uses `transform-origin: top left` plus `width: fit-content` (without it the wrapper stretches to the already-scaled sizer and the transform scales it a second time). Keep all three in sync or the zoomed-in canvas becomes partly unreachable by scroll (see `BUGS.md`). `fitZoomToViewport()` auto-picks the largest zoom (floored to a 10% step, never below 100%) that fits `.canvas-area`'s available size, run on init and on window resize; it backs off permanently once the user touches the zoom slider (`zoomManual` flag), so manual choices are never overridden. `ZOOM_MIN`/`ZOOM_MAX` (0.3–3) bound both `applyZoom` and the auto-fit, and **must be kept in sync with the `#zoom-slider` min/max in index.html**.

**Moving a selection is clamped to the canvas (`clampDelta`/`moveSelectionBy`, v2.12.1).** `onMouseDown` calls `setPointerCapture`, so a drag stays alive far outside the canvas and `getPos` happily returns coordinates well past `CANVAS_W`/`CANVAS_H` — nothing related element coordinates to the fixed 1200×800 canvas, so flinging something off the edge *lost* it: still counted in «Elementos» and still travelling inside exported JSON, but invisible and unreachable (a click can't land out there and a marquee can only be drawn over the canvas, so even select-all didn't bring it back). Every path that moves a selection now goes through `moveSelectionBy` — the drag, the arrow-key nudge and the X/Y fields of «Posición y tamaño» — keeping `KEEP_VISIBLE` (24) px of the box on canvas, or the whole object when it is smaller. Four properties to preserve, each with a guard:

- **The clamp applies to the selection's combined box, never piece by piece** — clamping each element separately would dismantle a building against the edge instead of stopping it as one thing.
- **It only limits movement that makes things worse.** An element already outside (a project saved before this version) must still be draggable back in, and moving a selection that contains one must not yank it to the edge and break its position relative to the rest.
- **`dragLast` stores the pointer's real position, not the clamped one**, so when the pointer comes back the object follows from the first pixel instead of having to re-cross the distance it overshot.
- **`applyGeometry` clamps before its no-op guard**, so a typed X of 9000 resyncs the field to where the element actually ended up rather than promising a position it doesn't have.

### «Limpiar todo» y los valores de fábrica

**`appDefaults()` (app.js) es la fuente ÚNICA de los ajustes de fábrica**, y la
usan las dos cosas que ponen el estado entero de golpe: el `state` inicial y el
botón «Limpiar todo». Un ajuste nuevo se resetea solo por estar ahí. Hasta la
v2.22.1 el botón mantenía **su propia lista escrita a mano**, y se había quedado
atrás en dieciséis ajustes (color, grosor, tamaño de letra, el relleno entero,
discontinuo, doble punta, cuadrícula, ajustar a la rejilla, clics acumulativos,
la letra del lienzo y los tres del estilo de texto). Cuatro cosas que conviene
no volver a separar:

- **Es una función, no un objeto.** `uiLabels` se muta en sitio
  (`state.uiLabels[tool] = …`), así que compartir la referencia haría que el
  botón devolviera lo último escrito en vez del valor de fábrica. Cualquier
  campo anidado que se añada hereda esa protección sin pensarlo.
- **Los ajustes que se persisten tienen que volver EN `state`, no solo en
  `localStorage`.** El botón borra la clave, pero si el valor sigue vivo en
  `state` el primer `savePrefs()` posterior —cambiar el color del fondo, sin ir
  más lejos— lo reescribe entero y reaparece en la recarga siguiente.
- **`syncAllControls()` es el punto único que vuelca `state` en los mandos**, y
  lo llaman el arranque y el botón. Los de semántica dual (color, grosor,
  relleno, tamaño de letra, discontinuo, doble punta) no hacen falta ahí:
  `redrawNow` los sincroniza en cada repintado y sin selección enseña justo
  esos defaults. Los que no tienen quien los sincronice, sí — y por eso el
  tamaño del borrador estrena `syncEraserControls()`: su mando solo lo escribían
  `applyEraserSize` y `openEraserSizeModal`, así que el estado se reseteaba y el
  deslizador seguía enseñando el tamaño anterior.
- **La herramienta vuelve al Lápiz con `silent`.** Aquí nadie ha pulsado una
  herramienta, así que abrirle sus ajustes encima del lienzo recién vaciado
  sería un modal que nadie pidió — el mismo motivo por el que las cuatro
  activaciones automáticas de Mover pasan ese flag.

Lo único que **no** vuelve a un valor fijo es el zoom, que re-ejecuta el
auto-ajuste (`zoomManual = false` + `fitZoomToViewport()`, la pareja que corre
`init()`): forzar el 100 % encogía el lienzo y dejaba el auto-ajuste apagado el
resto de la sesión (ver `BUGS.md`). Guardado por *«Limpiar todo» devuelve TODOS
los ajustes a los de fábrica, no solo unos cuantos*, que compara treinta mandos
contra un arranque limpio.

### Canvas background / grid color

`state.canvasBg` and `state.gridColor` (defaults `DEFAULT_CANVAS_BG`/`DEFAULT_GRID_COLOR` in app.js) are cosmetic prefs, not part of `state.elements` — they persist to their own `localStorage` key (`sketchwire.prefs`, via `savePrefs`/`restorePrefs`) separately from the autosave, and are not undo-tracked (same treatment as `state.zoom`/`showGrid`). `Renderer.drawGrid(ctx, w, h, color)` takes a single base color and varies only `globalAlpha` for the minor vs. major grid lines, rather than two hardcoded colors. "Limpiar todo" resets them and re-runs the zoom auto-fit (`zoomManual = false` + `fitZoomToViewport()` — the same pair `init()` runs), in addition to clearing elements: the button promises the app as freshly opened, and there the canvas fills the available space. Forcing 100% and setting `zoomManual` instead — the original behaviour — both shrank the canvas and disabled the auto-fit for the rest of the session (see `BUGS.md`).

**Since v2.31.0 the aspect is one click: `CANVAS_PRESETS` (config.js) and the row of swatches at the top of «Lienzo».** Each preset sets the three fields at once — paper, grid colour and grid on/off — because composing them by hand was three gestures, two of them inside the system's colour dialog, and the way *back* meant remembering two hex codes written nowhere in the interface: whoever turned the canvas white could not return. Five entries (Plano, Blanco, Milimetrado, Crema, Pizarra), `buildCanvasPresets`/`applyCanvasPreset`/`updateCanvasPresetActive` in app.js, mirroring the `buildColorGrid`/`applyColor`/`updateColorActive` trio. Six things to keep:

- **A preset never touches the ink.** It describes the paper; the drawing colour is another control. Accepted consequence: on «Pizarra» you must pick a light colour in the palette or the stroke is invisible. Making the preset swap `state.color` was rejected — a control that reaches across into another one is exactly what the panel stopped doing.
- **It does not enter undo** (no `saveUndo`), same as the two colour pickers it sits above: it is screen cosmetics, and it changes nothing that is exported or serialized into elements.
- **The first entry IS the factory state**, pinned against `DEFAULT_CANVAS_BG`/`DEFAULT_GRID_COLOR` and `appDefaults()`'s `showGrid` — same contract as `SKETCH_FONTS[0]` with `--font-sketch`. So «Limpiar todo» returns to it for free, through `appDefaults()` + `syncAllControls()`.
- **`showGrid` is persisted since this version** (`savePrefs`/`restorePrefs`, validated by type; a pre-2.31.0 prefs simply lacks it and falls back to on). Without that, the white-and-flat canvas came back with its grid lit on the next reload and the aspect no longer matched any swatch.
- **The swatch draws the grid, and that is load-bearing**: «Blanco» and «Milimetrado» share both colours and differ *only* by `showGrid`, so without the lines the row would show two identical white squares. Paper and grid colour reach the CSS as inline custom properties (`--preset-bg`/`--preset-grid`, the latter `transparent` when there is no grid) — which is why `tests/smoke.test.js`'s "every custom property is defined" guard now allows properties that app.js writes with `setProperty`, provided they are used with a fallback.
- **When nothing matches, nothing is marked.** Retouching a picker by hand leaves the row with no active swatch rather than claiming an aspect that isn't on screen; the grid colour is ignored in that comparison while the grid is off, since an invisible colour cannot decide which aspect is showing.

**Since v2.20.0 the defaults are a blueprint: `#686f92` paper with a `#fcfcfc` grid** (they were `#ffffff`/`#cdd3de`). Four consequences, each with a guard:

- **They are screen-only, and that is now load-bearing.** No export carries them: `_renderClean` composes its own `#ffffff` and passes no `showGrid`, the SVG writes `fill="white"` and the HTML `background: #fff` — and app.js only ever hands the exporters `{ overlapMode }`. While the default paper *was* white this held by coincidence; now a leak would be glaring. Guarded by *"ninguna exportación lleva el color del lienzo ni la cuadrícula"*, which exports an **empty** scene (so any stroke on the temp canvas can only be the grid) and passes hostile `background`/`showGrid`/`gridColor` options that must be ignored.
- **`Renderer.drawGrid`'s own default stays `#cdd3de` and must not follow.** It is the fallback when a caller passes no colour, and there the background to assume is white — `#fcfcfc` on white draws nothing. The app always passes `state.gridColor`, so the two never meet.
- **The paper colour is written twice** — the constant in app.js and the `value` attribute of `#canvas-bg-picker`/`#grid-color-picker` in index.html. The vm harness cannot see a divergence (it reads back the value app.js just assigned), so `tests/smoke.test.js` compares the two files directly.
- **`paintedPixels` (e2e/helpers.js) measures ink relative to the paper**, not below a fixed luminance. With the old `lum < 128` an *empty* canvas already counted 779 401 pixels — the slate paper itself — so drawing a rectangle moved the number by 2 051 and the helper had stopped measuring what its name promises. The threshold is 60 % of the paper's luminance, read from `#canvas-bg-picker`; the grid is always lighter than the paper, so it stays out under any combination.
