# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Pizarra is a canvas-based wireframing/sketching web app with a hand-drawn aesthetic. Vanilla HTML/JS with **zero runtime dependencies** — no bundler, no framework; `index.html` loads plain `<script>` tags and a plain stylesheet. Styles are authored in **SCSS (BEM)** under `src/scss/` and compiled by **Gulp 5 + dart-sass** into `css/styles.css`, which is **committed** so cloning and opening `index.html` keeps working with nothing installed (see "Styles" below). UI text is in Spanish.

The app was formerly called SketchWire, so that name survives in identifiers that must not change: the `localStorage` keys `sketchwire.autosave`/`sketchwire.prefs` and the clipboard marker `sketchwire/elements` in app.js. **Renaming those would orphan every user's saved canvas and preferences** — leave them alone.

## Running

Open `index.html` directly in a browser, or serve statically:

```bash
python3 -m http.server 8000   # then open http://localhost:8000
```

Style development needs `npm install` once, then: `npm run watch:css` (recompile on save), `npm run build:css` (one-shot), `npm run build` (compile + regenerate `dist/`, the publishable build: index.html and LICENSE verbatim, CSS compressed, JS minified — gitignored), `npm run lint:css` (stylelint). Tests use Node's built-in runner (no dependencies):

```bash
node --test tests/*.test.js          # full suite
node --test tests/exporter.test.js   # single file
```

**The app itself still has zero runtime dependencies** — `index.html` loads plain `<script>` tags and the already-compiled `css/styles.css`. `package.json`/`node_modules` exist only for development: the end-to-end suite and the style pipeline (Gulp/Sass/stylelint); never make the app require them at runtime.

Use the glob (`tests/*.test.js`), not the bare directory: `node --test tests/`
silently skips a file under Node 22.x's directory globbing, so a regression guard
could pass unnoticed by not running at all.

Tests load the global-scope scripts via `node:vm` with canvas/DOM stubs (see `tests/helpers/`). Two vm-realm gotchas: arrays/errors created inside the vm don't share host prototypes, so compare structurally (`[...arr]`, `err.name`) instead of `deepStrictEqual` against host literals or `instanceof`.

**`src/js/app.js` is testable too** (since v1.13.1) via `tests/helpers/load-app.js`, which runs the whole app under `node:vm`: `dom-stub.js` builds the element tree by parsing the real `index.html` (so ids, classes and nesting match the page), and the test drives real gestures — `selectTool`, `drag`, `click`, `key` — then reads the result with `elements()`. There is **no test hook in production code**: observability comes from the autosave, which serializes `state.elements` to localStorage. `flush()` drains the queued `requestAnimationFrame`/`setTimeout` callbacks so each gesture settles deterministically. Two things to know when writing these tests: pointer-move events must carry `buttons: 1` (app.js requires it to treat a move as a drag), and prefer asserting on element coordinates/counts rather than on canvas draw calls. **The harness does not simulate browser default actions** — it caught none of the two bugs found by opening the app in a real browser (a tool shortcut leaking into the modal it opened, and the eraser's reach feeling far too aggressive). It proves logic, not feel: still open the app for anything about focus, defaults or how a gesture reads. See `tests/app-interaction.test.js`. Prefer converting a "manual repro" BUGS.md entry into one of these tests over repeating the steps by hand.

### End-to-end suite (`e2e/`, Playwright)

```bash
npm run e2e:install     # una vez: descarga Chromium (~95 MB)
npm run test:e2e        # suite e2e
npm run test:all        # node:vm + e2e
```

It **complements** the `node:vm` harness, it does not replace it. The split is the point: `tests/` proves logic (coordinates, undo, export, geometry) in milliseconds; `e2e/` proves the things the vm harness cannot see *by construction* — layout, CSS, real focus and browser default actions. That's exactly the gap CLAUDE.md already warned about ("still open the app for anything about focus, defaults or how a gesture reads"), so most `e2e/` specs are BUGS.md entries that used to say *"verificación manual"*. **Decide where a new test goes by that rule**, not by convenience.

`playwright.config.js` serves the app with `python3 -m http.server` on port 8123 (no build, same as production) and runs Chromium only. Three things bite in this app specifically, all absorbed by `e2e/helpers.js` — use the helpers rather than driving the page directly:

- **Nothing is observable synchronously.** `redraw()` is coalesced through `requestAnimationFrame` and the autosave is debounced 500 ms, so a read right after a gesture returns the *previous* state. `settle()` (two rAFs) runs at the end of every gesture helper, and `elements()` then waits for the autosave to agree with the panel's «Elementos» counter. Without `settle()` that agreement is satisfied by the stale pair (0 === 0) and the wait returns instantly with the old scene — a silent false pass, not a failure.
- **The canvas is scaled and the scaling is animated.** `canvasPoint()` maps canvas coords to viewport coords through the canvas's own rendered box, so it absorbs zoom and scroll. But `.canvas-area__sizer` transitions `width`/`height` over 0.2 s: measuring mid-transition sends clicks to the wrong canvas coordinate and reports a half-sized scroll area. Always change zoom with `setZoom()`, which waits for the box to reach its final size.
- **Window size decides the initial zoom**, because of the auto-fit. Use the measured `WIDE` (1920×1200 → 120 %) and `NARROW` (1160×700 → 100 %) constants. `NARROW` is deliberately above 1100 px: below that the panel becomes a hidden drawer and its buttons can't be clicked without opening it first.

Observability follows the same rule as the vm harness: **no test hooks in production code** — the scene is read from the autosave, and everything else from the DOM the user sees.

`PLAN.md` holds the prioritized improvement roadmap (fases 1-3 completed, except §3.2 element-type registry, deliberately skipped as optional). `BUGS.md` is the regression registry: every bug fix gets a symptom/cause/fix entry there plus a **regression guard** — a test in `tests/` for code in one of the `node:vm`-loadable modules (config/sketchy/arc/renderer/exporter/templates), or documented manual repro steps if the fix lives in `app.js` (DOM-only, outside the test harness — see below). Add the entry as part of the fix, not as a follow-up.

## Styles (`src/scss/` → `css/styles.css`)

Since v1.25.0 the stylesheet is compiled: **`css/styles.css` is a generated artifact — edit `src/scss/` and run `npm run build:css`, never the CSS itself** (a guard in `tests/smoke.test.js` checks the banner and the runtime contracts). The artifact stays committed, at that exact path, because `tests/smoke.test.js` anchors `css/styles.css?v=…`, Playwright serves the repo root with no build step, and the README promises clone-and-open. `gulpfile.js` uses the modern `sass.compile()` API directly (no gulp-sass plugin), `style: 'expanded'`, no sourcemaps, no autoprefixer — the output is meant to be deterministic and reviewable. `src/` holds the app source: `src/scss/` (compiled), `src/js/` (loaded as-is — `index.html` points its `<script>` tags at `src/js/*.js`) and `src/img/` (every image in the repo). `index.html` itself stays at the repo root because the vm harness (`load-app.js`), Playwright and clone-and-open all anchor it there.

`npm run build` additionally assembles `dist/`, the publishable build (gitignored): LICENSE verbatim, index.html with its `src/js/` and `src/img/` paths flattened to `js/` and `img/` (the only HTML transformation anywhere), the same SCSS recompiled with `style: 'compressed'`, and each `src/js/*.js` minified with **terser** into `dist/js/` keeping its filename. `site.webmanifest` gets the same `src/img/` → `img/` rewrite, because its icon paths resolve relative to the manifest itself. Terser must never mangle top-level bindings — each `<script>` exposes globals (`TOOLS`, `Sketchy`, …) as top-level `const` that later scripts consume; the default `mangle: true` (without `toplevel`) is what keeps that safe. The `src/js/` files themselves are never transformed in the source tree.

## Images (`src/img/`)

**Every image in the repo lives in `src/img/`** — the icon set, `favicon.ico`, the topbar logo, the source PNG and the README screenshots. There is no `icons/` or `docs/` folder and nothing image-shaped at the repo root. `IMG_SKIP` in `gulpfile.js` is what keeps `dist/img/` down to the runtime pieces: it drops `icon-source-512.png` and anything named `screenshot-*`, which is why the README captures carry that prefix — rename them and they end up shipped.

The whole icon set is derived from `src/img/icon-source-512.png` with ImageMagick — that PNG is the only original, everything else is regenerable. `index.html` references them with **relative** paths (`src/img/…`, not `/src/img/…`) because the README promises clone-and-open over `file://`, where an absolute path resolves to the disk root. The small sizes (16/32/48, and thus the `.ico`) are cropped in ~7% before downscaling and lightly unsharpened: at 32px the source's generous padding left the drawing washed out. `src/img/logo-96.png` (the topbar's `<img class="topbar__logo-icon">`) comes from that same crop at 3× its 32px box. `src/img/icon-maskable-512.png` is the odd one — full-bleed paper background with the artwork at 80%, because Android crops a maskable icon into a circle and the squircle's corners would go with it; the rest keep transparent corners. `tests/smoke.test.js` guards that every icon referenced by the `<head>`, the manifest or the topbar exists and matches its declared `sizes` (a 404 here is silent — the browser just falls back to the default icon). The topbar logo is decorative (`alt=""`, the word «Pizarra» is right next to it) and carries no `border-radius`: the PNG already has its own rounded corners, and clipping it again eats into the drawing.

Rules that keep the compiled output correct — each one broke, or would have broken, something real:

- **`1rem` = 10px.** `html { font-size: 62.5% }` and every UI distance is written in rem (`body` restores the effective 16px with `1.6rem`). Media-query breakpoints stay in **px** on purpose, and so does everything JS sets on the canvas (canvas coordinates don't scale with browser font size; the UI chrome does). e2e asserts *computed* px (72/132), which rem resolves to exactly.
- **Custom properties must stay custom properties** in the output — never Sass `$vars` resolved at compile time: `--sidebar-w` is redefined at runtime inside a media query, and `src/js/config.js` reads `--font-sketch` at startup. The design-token *values* live as Sass vars in `src/scss/abstracts/_variables.scss` and `base/_tokens.scss` interpolates them into `:root` — that's the one place both layers meet.
- **Fonts have one source of truth: `src/scss/abstracts/_fonts.scss`** (`$font-ui`, `$font-sketch`). `_tokens.scss` emits them as custom properties via `meta.inspect()` — plain `#{}` interpolation strips the quotes each family needs. In the browser `SKETCHY_FONT` (config.js) reads `--font-sketch` from computed style, with the old literal as fallback for the `node:vm` harness (no `getComputedStyle` there) — the smoke guard asserts CSS and fallback agree. `FONT_FALLBACK` (exporter.js) derives from it stripping both quote kinds (double quotes would malform the SVG export's XML attributes).

**Since v2.13.0 the handwriting font is self-hosted and selectable, and the app requests no font over the network at all.** Five families live in `fonts/` as woff2 (SIL OFL 1.1, latin subset, licence in `fonts/LICENSE-handwriting-fonts.txt`): Architects Daughter — the default, unchanged — plus Caveat, Patrick Hand, Kalam and Indie Flower. **v2.14.0 added OpenDyslexic as a sixth option** — so the dyslexia-readable choice reaches the drawing and not just the chrome — and **v2.15.0 a seventh, Montserrat Alternates** (geometric). Neither is handwriting, so both end their stack in `sans-serif` rather than `cursive` (if the woff2 failed, another geometric beats a cursive), and the visible label became **«Letra del lienzo»**: it said «manuscrita» while they all were, and two of seven no longer are. Only OpenDyslexic carries `google: false`. The `<head>`'s two `preconnect`s and the Google Fonts `<link>` are gone, so the README's clone-and-open promise now holds offline and over `file://`; before, without a network the canvas silently fell back to the system cursive. Six things to keep in step:

- **`SKETCH_FONTS` (config.js) is the catalogue**, and every entry needs both an `@font-face` in `_font-faces.scss` and its `.woff2` on disk — a missing one doesn't throw, the canvas just draws with the system fallback. The first entry is the default and must say exactly what `$font-sketch`/`--font-sketch`/`SKETCHY_FONT` say. All of that is guarded in `tests/smoke.test.js`, including that `index.html` mentions neither googleapis nor gstatic.
- **`sketchFont()`, never `SKETCHY_FONT`, is what draws.** The constant is computed once at startup, so everything that writes on the canvas (renderer, previews, both exporters) goes through the function or a font change would leave old text behind. `exporter.js`'s `FONT_FALLBACK`/`FONT_CSS` became functions for the same reason.
- **`setSketchFont` also rewrites `--font-sketch`**, because the floating text editor is a real `<textarea>` that takes its family from that custom property — otherwise you would type in one hand and see another the moment you committed.
- **A `<canvas>` does not trigger a webfont download.** `ctx.font` with an unloaded family draws the fallback and never retries, and the only DOM node using the handwriting is that hidden textarea, so nothing requested it. `ensureSketchFontLoaded` asks `document.fonts.load` explicitly and repaints when it arrives — verified in a browser: choosing Kalam moves it from `unloaded` to `loaded` and the measured text width changes.
- **The picker exists twice** (`SKETCH_FONT_SELECTS`: the panel's «Lienzo» section and `#modal-text`, where you are looking while writing), both routed through the single `applySketchFont`. Options are built from the catalogue, never duplicated in the HTML, and each is labelled **in its own family** — in a list of names that is the only thing telling one handwriting from another.
- **Exports still fetch from Google Fonts, deliberately.** A `.svg` or `.html` export is a loose file that travels without the `fonts/` folder, so a relative path would break the moment it left; `FONT_URL()` builds the URL from the active family and offline the file falls back to the same stack. **`google: false` entries return `null`** and both exporters then omit the `<link>`/`@import` entirely — OpenDyslexic is not on Google Fonts, so the URL would have been a silent 404 inside every export. Any future self-made family needs that flag; a smoke guard pins the current list. The UI font is **OpenDyslexic** (chosen for dyslexia readability — a user accessibility choice, don't swap it), **self-hosted** in `fonts/`: four woff2 (Regular/Bold/Italic/BoldItalic) converted with fontTools from the user's official OTFs (classic Bitstream Vera-derived family; license file alongside, regenerated from the fonts' own name table). `@font-face` lives in `src/scss/base/_font-faces.scss` — weights 500/600 in the CSS resolve to 400/700 by CSS font-matching, and `dist/` gets `fonts/` copied verbatim. OpenDyslexic is wider than a typical sans: the sidebar buttons are sized so the longest catalogue word («Redondeado», ~58px at 0.9rem) fits on one line — 6.8rem button, no letter-spacing on the name, `min-height` so multi-line labels grow the button instead of overlapping the icon. Never reintroduce `overflow-wrap: anywhere` there (it splits words at arbitrary characters — «Rectán / gulo») nor a fixed button `height`; an e2e test in `responsive.spec.js` measures all three failure modes in both sidebar widths.
- **The `@use` order in `main.scss` is the cascade** — don't alphabetize. Each BEM block is one partial and carries its own media queries (base rule and its override travel together); `_scrollbar.scss` loads last because the original file ended with it. Order-dependent pairs: `.btn` → `.btn[hidden]`, `.panel` base → drawer media query, `.modal__shape-grid--three .modal__shape` (wins over the *later* `.modal__shape` by specificity — don't "fix" the order).
- **Vendor selectors never share a comma-separated group** (`::-webkit-slider-thumb` / `::-moz-range-thumb`): one unknown selector invalidates the whole group in both browsers. The shared body lives in the `range-thumb` mixin.
- **A comment between nested rules breaks nesting**: dart-sass traps it inside the parent's declaration block. That's why comment-dense partials (`_btn`, `_canvas-area`, `_modal`, `_panel-drawer`) use flat selectors and only comment-free stretches use `&__`/`&--`.
- Breakpoints are named in `src/scss/abstracts/_breakpoints.scss` (1201/1100/420/360) — the only place they may live; e2e and the docs below pin the sidebar one.
- stylelint is configured for the **legacy color notation on purpose** (`rgba(…)`, numeric alpha): the modern-notation autofix would rewrite every color and change the artifact's bytes. Don't "clean" that config without re-verifying the output.
- The v1.25.0 migration kept `.panel__select`'s `var(--text-main)` typo verbatim on purpose; v2.0.0 fixed it to `--text-primary`, and `tests/smoke.test.js` now asserts that **every custom property used in the compiled CSS is defined** — a wrong `var()` name fails nowhere by itself (SCSS, stylelint and the browser all stay silent).

## Architecture

Scripts are plain `<script>` tags loaded in dependency order in `index.html` (config → sketchy → arc → curve-path → shape-rotation → regular-polygon → trapezoid → eraser → building → garden → renderer → exporter → templates → app). There are no modules/imports — each file exposes a global (`TOOLS`, `Sketchy`, `ArcMath`, `CurvePath`, `ShapeRotation`, `RegularPolygon`, `Trapezoid`, `Eraser`, `Building`, `Garden`, `Renderer`, `Exporter`, `Templates`) via IIFE, and later scripts rely on earlier globals. If you add a file, add its `<script>` tag in the right position (and, for the test harness, in `ALL_FILES`/`KNOWN_GLOBALS` of `tests/helpers/load.js`).

The app is state-driven immediate-mode rendering: a single `state.elements` array of plain objects is the source of truth, and any change triggers a full canvas redraw (`redraw()` in app.js). Elements are serializable plain objects (this is what JSON export/import round-trips), so never store functions or DOM refs on them. They are also treated as immutable: operations replace the element object (`moveElement` returns a copy) rather than mutating it, which lets undo snapshots be shallow copies (`state.elements.slice()`) — preserve that discipline when adding features.

- `src/js/config.js` — global constants: `TOOLS` ids, `TOOL_GROUPS` (drives sidebar build), `COLORS`, `CANVAS_W/H` (1200×800), `UI_DEFAULTS` (fallback sizes for UI components placed with a tiny drag).
- `src/js/sketchy.js` — low-level "wobbly" hand-drawn primitives (line, rect, roundedRect, ellipse, arrow) using `Math.random()` jitter.
- `src/js/arc.js` — pure circular-arc math (`ArcMath`): fits a single cubic Bézier to an arc of a given sagitta over a chord (≤ 180°). A `curveArrow` with `arc: true` is a normal cubic whose controls were computed this way, so renderer/exporters/hit-test need no arc-specific code. The `TOOLS.ARC` sidebar tool ("Semicírculo") is creation-mode only — it is **not** an element type; it creates `curveArrow` elements that are always exact 180° semicircles (drag = diameter). Editing keeps the 180° invariant: `+/−` and the ctrl-handle drag change the radius via `resizeArc` (app.js), and endpoint drags preserve the shape through `transformControlsToChord`.
- `src/js/curve-path.js` — pure shared geometry for `curveArrow`, including chained curves. Historical single curves keep `x1/y1/cx/cy[/cx2/cy2]/x2/y2`; a chain also carries `segments`, an ordered, continuous array of quadratic/cubic Bézier objects, while top-level `x1/y1/x2/y2` mirror only the overall endpoints for connector anchoring. Use `CurvePath` for rendering, bounds, sampling, moving, scaling, reversing and endpoint/join editing so those mirrors never drift.
- `src/js/shape-rotation.js` — pure discrete rotation rules. `ShapeRotation.rotateElement` swaps a rectangle's `w/h` around its unchanged center for each 90° turn, and normalizes the `rotation` field of triangles/pentagons/hexagons after 90°/36°/30° turns. Unsupported types are returned unchanged.
- `src/js/regular-polygon.js` — pure geometry for `triangle`, `pentagon` and `hexagon`: side counts, vertices, center-radius creation and real-silhouette containment. These elements use the standard `x/y/w/h` shape schema but must keep `w === h`; app resize enforces the square and import validation rejects deformed polygons.
- `src/js/trapezoid.js` — pure geometry and quarter-turn rotation of the isosceles `trapezoid` element (standard `x/y/w/h` schema, free proportions).
- `src/js/building.js` — pure geometry (`Building`) for the **Edificios** section (see below). `Building.elements(tool, p1, p2, opts)` returns an array of plain **existing-type** elements (`rect`/`line`/`circle`/`curveArrow`), so renderer/exporter/`isValidElement`/bounds need no building-specific code. Covers balcones (railing + cantilevered slab in elevation, 8 types via `opts.balconyType`; `_railing` takes a `bar` callback so the forja can bow its bars with `ArcMath`, and the balcony is the only tool whose `DEFAULTS` entry carries `variantKey`/`byVariant`), plantas (rect/L/U/claustro), fachada in three vistas (flat/alzado/perfil via `opts.facadeShape`; multi-floor, windows + door, tiled roofs), tejados (dos aguas/un agua/plano/**cuatro aguas**/**mansarda** via `opts.roofShape`), and the Puerta types (door/arch/double/panel/garage + frame/archFrame/doubleFrame marcos) and Ventana types (window/arch/double/grid/round + frame/archFrame/roundFrame marcos). `_openings` **honours `opts.doorType`/`opts.windowType`** (facades draw the rich hole types via `_doorTool`/`_windowTool`, degrading to the basic hole below a size threshold), and `opts.floors`/`opts.bays`/`opts.roofPitch`/`opts.roofType` override the drag-derived plantas/vanos/pitch/roof (absent or `'auto'` = legacy behaviour). Door and window arches share one `_arched(b,o,{frameOnly,cross})`; the sill is `_sill`; the cornice is drawn only on the roofless facade (`_body(...,crown)`). The **perfil is a side view, not a second facade**: `_profile` passes `side=true` through `_body` to `_openings`, which forces `ground=false` so the lateral gets **no door** and an even bay rhythm on every floor (no central gap reserved for an entrance) — keep that flag if you touch `_openings`. Detail (mullions, sills, tiles, panels, slats, grid bars) uses a thinner `lineWidth` than the contour (`_lineT`/`_rectT`); arches are `ArcMath` `curveArrow`s with `arc:true, heads:'none'` and the óculo is a `circle` element. Elements come out **without `seed`** (app.js adds it via `withSeeds`); app.js also stamps a shared `buildingGroupId` on every piece of a multi-piece building.

- `src/js/eraser.js` — pure geometry (`Eraser`) for what an eraser stroke touches: `touches`/`doomedIndices`/`apply`, plus segment-segment distance with a crossing test. Everything that lives outside is injected via `deps` (`boundsOf`, `sampleCurve`, `polygonVertices`, `trapezoidVertices`) so the module stays DOM-free and testable; app.js supplies them in `eraserDeps()`. **Since v1.14.0 the eraser deletes elements instead of masking them** — the old `type:'eraser'` element was a `destination-out` mask fixed in canvas space, so moving the drawing slid it out from under the mask and the "erased" content came back (and still travelled inside exported JSON). The reach rule is **what you can see, not the bounding box**: for `OUTLINE_TYPES` shapes only the contour counts (box edges, sampled ellipse, or real polygon/trapezoid vertices) unless `el.fill` is set, in which case the interior is ink too — the interior of the **silhouette** (point-in-polygon over the same outline vertices), not of the bounding box: the bbox corner of a filled circle is ~15px away from any ink and must not erase it; text, images and UI components still use the box, because there the box *is* the drawing. Using the box for everything — the obvious "same as `hitTest`" choice — makes one sweep through the middle of a facade delete the whole wall. A generous box is right for *selecting* and far too aggressive for *erasing*. **Legacy `eraser` elements are still rendered, exported and validated** so older projects look unchanged, and `doomedIndices` skips them — deleting a mask would reveal exactly what it hides. Only the tool stopped creating them.
  **Since v1.22.0, `line`/`arrow`/`pencil` are recorded, not deleted, by `Eraser.erase(elements, pts, r, deps)`** (used by app.js instead of `doomedIndices`+filter): a touched line/arrow is resampled every `LINE_SAMPLE_STEP` (4px) and a touched pencil's own `points` are walked directly; `_survivingRuns` classifies each point as erased/kept and bisects the exact crossing at every transition, so what remains is whatever falls outside the circle, split into as many pieces as needed — this is what makes erasing through the middle of a line, or through where two strokes cross, only take the bit under the pointer instead of the whole element. An `arrow` piece only keeps its type (and head) if it contains the original tip (`x2,y2`) by reference — a run built from an interpolated crossing point never equals it — so a fragment cut away from the tip becomes a plain headless `line` rather than inventing a new arrowhead at the cut; a `heads:'both'` arrow keeps that flag only on a piece that still holds *both* original endpoints, which in practice means the split didn't really touch it. Every other type (shapes, text, images, components, `curveArrow`) still goes through whole-element delete — clipping a shape's contour or splitting a Bézier exactly was ruled out of scope. **Since v2.2.0 the split classifies with the same ink margin as `touches` (`r + lineWidth/2`)** — with bare `r` there was a band (between the axis and the stroke's edge) that "touched" without erasing anything visible yet still rebuilt the element; a graze that erases no sample now returns the element intact **by reference** (no phantom undo step, no silent de-anchoring), and a piece that keeps its original arrow endpoint keeps that endpoint's anchor (a piece demoted to `line` drops anchors — `resolveAnchors` ignores lines). The eraser's own size is `state.eraserSize`, edited by the panel's repurposed stroke slider (`#stroke-slider`, "Tamaño del borrador") and mirrored in `#modal-eraser` — `applyEraserSize()` is the single point that keeps both sliders, the preview canvas and `state.eraserSize` in sync, same pattern as Edificios' twin controls. **Selecting the Eraser tool opens `#modal-eraser` immediately**, same as Planta/Puerta/Balcón open their catalogue (`openEraserSizeModal()`, called from `selectTool`) — the panel's gear button (`#btn-eraser-size`, hidden unless erasing) reopens it later without leaving the tool. Unlike those catalogue modals, closing it does **not** revert to the tool active before: Eraser is already usable with its current size, there's nothing to "cancel" into. It is deliberately *not* added to `opensVariantModal`, for that same reason — same as Emoji.
- `src/js/garden.js` — pure geometry (`Garden`) for the **Jardín** section (see below), with plan and elevation renderers for vegetation. Same contract as `building.js`: `Garden.elements(tool, p1, p2, opts)` returns plain **existing-type** elements — `rect`/`line`/`circle`/`curveArrow`/`text` — with no `seed` and no DOM. `Garden.plantSize(tool,id,opts)` is the single botanical sizing function: adult height/spread/depth × stage factor × 50–150%, and click placement converts metres through 8–50 px/m. Detail uses `_fine(o)`, while `_chain`, `_blob` and `_rosette` carry organic plan silhouettes; elevation builders add trunks, branch architecture, layered crowns, flowers/fruit, ground lines and climbing supports. Natural mode uses per-species `foliage`/`accent` fills with transparency; ink mode stays monochrome. **The module must stay deterministic** — no `Math.random()`; irregularity comes from frozen tables and the hand-drawn wobble is added by `Sketchy` from `el.seed`. Labels can be common, botanical or dimensioned text; injected `measureText` may only move a label, never alter geometry.
- `src/js/renderer.js` — `Renderer.renderElement(ctx, el)` switches on `el.type` and draws each element type (shapes via Sketchy, plus composite UI components: button, input, imagePlaceholder, nav, card). Also grid and selection highlight.
- `src/js/exporter.js` — export to PNG/JPG (offscreen canvas), SVG and HTML (hand-built markup strings per element type), and JSON (project format); JSON import via file picker.
- `src/js/templates.js` — predefined element arrays (landing, dashboard, form).
- `src/js/app.js` — main controller IIFE: holds `state`, wires all DOM events, mouse handlers (two-canvas setup: `main-canvas` for committed elements, `overlay-canvas` for in-progress previews), hit-testing/drag for the select tool, undo/redo (deep-cloned snapshots of `state.elements`), text input overlay, modals.

One element type has no sidebar button: `image` (pasted via Ctrl/Cmd+V), whose `src` must be a base64 `data:image/png|jpeg` URL — enforced by `isValidElement` to keep injection out of SVG/HTML exports. Renderer keeps an image cache; `Renderer.setImageLoadCallback` is how app.js gets repaints when async loads finish.

The sidebar is responsive through CSS only: its default `--sidebar-w: 7.2rem`
(72px computed) and flex groups form one column up to 1200px. The
`@media (min-width: 1201px)` rule widens it to `13.2rem` (132px) and turns every
`.sidebar__group` into a two-column grid, with labels spanning both columns
(`src/scss/components/_sidebar.scss`). Keep that exact breakpoint aligned with the
documented desktop behaviour — e2e asserts the computed 72/132px on both sides.

One controlled exception to immutability discipline: `resolveAnchors()` in app.js runs at the start of `redrawNow` and materializes anchored arrow endpoints (`startAnchor`/`endAnchor` referencing an element `id`) back into the elements — always by replacing with copies, never with `saveUndo` (it's derived state: snapshots capture materialized coords and the post-undo redraw re-resolves). When the chord of a `curveArrow` changes, its control points are re-projected through the old-chord→new-chord similarity transform (`transformControlsToChord`) so the curve keeps its shape — the same helper runs while dragging an endpoint handle in `resizeTo`. Element `id`s are assigned lazily only when something anchors to them.

### Adding a new element type

Requires touching several files in sync: add the tool id to `TOOLS` and a sidebar entry in `TOOL_GROUPS` (config.js), a render case in `Renderer.renderElement`, creation logic in app.js `onMouseUp` (and `UI_DEFAULTS` if it's a UI component), bounds handling in `getElementBounds` (app.js) if it isn't x/y/w/h-shaped, and export cases in exporter.js for SVG and HTML (PNG/JPG reuse the Renderer automatically).

### Panel controls: dual semantics

Panel controls follow an Excalidraw-style dual semantic: **with a selection they edit the selected elements** (immutable copies + one undo step per gesture); **without a selection they set the creation default** (`state.lineWidth`, `state.doubleHead`, `state.fillShapes`, …). `redrawNow` is the single sync point that pushes the right value back into each control (single selection → element's value; no selection → default; multi-selection → left untouched). Any future panel control inherits this question — follow the same pattern (see the stroke slider, the "Doble punta"/"Rellenar formas" checkboxes and the fill color picker in `wireControls`). **Since v2.9.0 the stroke colour picker follows it too** — which meant nothing already drawn could ever be recoloured; `showColor()` updates the swatches/hex without touching `state.color`, so `redrawNow` can display the selection's colour without overwriting the creation default. **Since v2.10.0 the font-size slider was the last to join** (`applyFontSize`, same gesture-snapshot undo as `applyStrokeWidth`): with a `text` selected it resizes it live, without touching `state.fontSize`.

`#panel-sec-element` ("Posición y tamaño") is the one section that is pure element editing: X/Y/width/height plus the element's own text (`value` on a `text`, `label` on the UI components — `LABEL_FIELD`). It reads through `getElementBounds` and writes through `scaleElement` + `moveElement`, the same pair the handles and the drag use, so it works for **every** type (freehand strokes and multi-selections included) without a case per type and cannot drift from what dragging does. Four things it must keep:

- **It sits FIRST in the panel**, above «Trazo». It was added at the bottom and that alone made it useless: selecting something put the fields below Lienzo, Solapamiento and Zoom, off-screen on a normal window, and the feature read as "you can't edit anything". When a section only appears because something is selected, it is the most relevant thing on screen.
- **Typing a size must not permit what dragging a handle forbids.** A regular polygon needs `w === h` and `isValidElement` **rejects** deformed ones, so free width/height would produce a project that no longer imports; a group scales uniformly for the same reason (its pieces carry that invariant). `applyGeometry` mirrors `resizeTo`/`resizeGroupTo`: the side you just typed wins and the other follows.
- Scale before translate — the factor is relative to the *original* box.
- `syncGeometryControls` never overwrites the field that currently has focus, or typing "300" would be rewritten to "3" mid-keystroke.

Since v2.10.0 the X/Y/Ancho/Alto quartet also exists inside each of the four settings modals (`GEO_PREFIXES` = `el`, `stroke-modal`, `shape-modal`, `text-modal`, `ui-modal`): one `syncGeometryControls`/`applyGeometry(prefix)` body serves all five sets, so a measure typed in a modal obeys the exact same invariants as the panel. The modal blocks (`#*-modal-geo`) appear only with a selection, and their wrapper `<div>` is deliberately **classless** so the user-agent's `[hidden]` rule works without adding entries to the `_panel.scss` grouped rule. The wiring passes the prefix through a closure — passing `applyGeometry` directly as a handler would feed it the event as `prefix`.

Four hard-won rules inside `applyGeometry` (auditoría v2.10.1 — each has a BUGS.md entry and a guard; breaking any of them re-opens a real bug):

- **"Changed" is judged against what the field DISPLAYED** (`Math.round`), never against the exact box — otherwise every fractional box (any diagonal polygon drag; with the 120% auto-fit zoom, nearly everything) makes the untouched width "win" over the height the user just typed. When a field didn't change, the *exact* value is used, not the rounded one.
- **`Number('') === 0`**: an emptied (or garbage-typed) `type=number` field must count as "unchanged", or emptying Ancho collapses the element to 1px.
- **The no-op guard checks the *effect*** (`dx/dy/sx/sy`), not box equality: typing a height on a horizontal line (where `scaleElement` forces `sy = 1`) must not stack a phantom undo step, and the field must resync to the truth.
- **`geoFieldsFor` discards stale changes**: in a browser, clicking element B fires `mousedown` (selection changes) *before* the field's `blur`→`change`, so a width typed for A would land on B. The rAF resync always runs after the change, so the recorded selection identity catches it (e2e-guarded — the vm harness can't see this event order).

Reading and writing go through `selectionBounds()` — the combined box of ANY selection. `selectionGroupBounds()` stays group-only on purpose (it decides the single box *with handles*), but typing measures never needed the selection to be a building; multi-selections scale uniformly either way. And handles are drawn **only when the active tool is Mover** (`handlesOn` in `redrawNow`): with a kept selection and a creation tool, canvas gestures create — drawing scale handles there promised a resize that `onMouseDown` (whose handle hit-test lives in the SELECT branch) would never deliver.

### The panel is contextual (v2.9.0)

The panel's `<section>`s are shown or hidden by `syncPanelSections()`, called from `redrawNow` — the same single sync point. Sections: `#panel-sec-stroke` (always), `#panel-sec-fill` (a fillable tool **or** a fillable in the selection), `#panel-sec-text` (Texto/Emoji or a `text` selected), `#panel-sec-build` (`BUILDING_TOOLS`), `#panel-sec-garden` (`GARDEN_TOOLS`), `#panel-sec-canvas` and `#panel-sec-selection` (always). Two rows inside Trazo are contextual too: `#row-dash` and `#row-double-head`. Before this, drawing with the pencil still showed "Plantas", "Cubierta del alzado" and "Ancho del camino" — 28 controls, of which ~10 applied. Below 1100px the panel is a drawer, so every extra control is paid in scroll.

Three things this rests on, each of which has already broken something:

- **It keys on the tool AND the selection, never the tool alone.** Fill, stroke and text controls have dual semantics, so with a rectangle selected `#panel-sec-fill` must be there even if the active tool is the pencil — otherwise selecting a shape stops letting you edit it, which is worse than the long panel. Guarded by *"las secciones reaparecen con la selección, no solo con la herramienta"*.
- **`hidden` does not hide anything that declares `display`.** `.panel__section`, `.panel__check`, `.panel__field` and `.panel__gear` all do, and that beats the user-agent's `[hidden]{display:none}` — the same trap that made `.btn[hidden]` necessary. They share one grouped rule in `_panel.scss`; **add any new `.panel__*` you plan to hide from JS to that group.** It has bitten four times, including the ⚙ from the day it was written (visible with every tool, opening the eraser modal from the pencil). The vm harness cannot see it — `hidden` there is a JS property, not CSS — so `tests/smoke.test.js` asserts all four compiled rules and `e2e/panel.spec.js` asserts real visibility.
- **Nothing was renamed or deleted.** `dom-stub.js` fabricates an empty `<div>` for an unknown id, so a renamed control fails as a confusing value diff instead of a missing element; and the Edificios/Camino twins are pinned by three guards. The reorganization only moves nodes.

`#modal-stroke` and `#modal-shape` are the drawing and shape tools' own settings, twinned with the panel through `syncStrokeControls()` / `syncShapeControls()` and opened from `selectTool` like every other configurable tool — see the rule below. `#modal-shape` also owns the **rotation** of the shapes that store it as an angle (`ROTATABLE_TOOLS` = the regular polygons + trapezoid; rect/roundedRect serialize a quarter-turn into their `w`/`h` and `isValidElement` **rejects** a `rotation` on them). `state.shapeRotation` is the creation default, snapped to the active type's `ShapeRotation.step` — 36° is not a valid hexagon orientation, and a trapezoid off a quarter-turn fails import validation. `creationRotation()` is the single source for both the drag preview and the committed element, and editing a selection goes through `rotateTo()`, which applies whole `ShapeRotation.rotateElement` steps rather than writing the angle directly — the trapezoid also swaps `w`/`h` on each quarter, so a raw write would leave its box out of line with its silhouette. Both sync functions write **both** sides (panel and modal): the dual-semantics handlers were extracted into named `apply*` functions (`applyDash`, `applyDoubleHead`, `applyFill`, `applyFillTransparent`, `applyFillOpacity`, `applyFillColor`, `applyStrokeWidth`) so the two control sets share one body, the way `wireBuildPair` does for the Edificios twins.

### A tool's own settings must open from the tool, not only from the panel

A control that is reachable only from the side panel is, in practice, unreachable: the panel sits far from the sidebar where the user actually clicked, it can be a hidden drawer below 1100px width, and nothing about clicking a tool button hints that an unrelated-looking control changed meaning somewhere else on screen. **v1.22.0 shipped the eraser's size control as a small ⚙ button inside the panel's stroke-slider section — technically wired correctly, invisible in practice.** The user clicked the "Borrador" tool expecting the size modal to show up right there, the way every other configurable tool (Emoji, Planta, Puerta, Ventana, Tejado, Balcón, and the eight Jardín tools) already opens its own modal from `selectTool` the moment it's picked — and reported it as broken.

The fix, and the rule going forward: **if a tool has a setting worth surfacing, wire it into `selectTool(id)` so picking the tool opens it**, following the existing `if (id === TOOLS.X) $('modal-X').showModal();` pattern (see `openEraserSizeModal()`). A panel control (twin slider, gear button, whatever) can still exist as a faster way to *reopen* or *live-tweak* it without leaving the tool, exactly like the Eraser's `#btn-eraser-size` or Fachada's twin panel fields — but it must never be the *only* way in. Note one real difference from the catalogue tools: Emoji/Planta/Balcón etc. require a choice before the tool is usable, so cancelling their modal restores the previous tool (`opensVariantModal`, `state.toolBeforeModal`). The Eraser needs no such choice — it already erases at whatever size it has — so its modal is deliberately *not* registered in `opensVariantModal`, and closing it just leaves you on the Eraser, ready to draw (same reasoning as Emoji, which shares this trait).

**`#modal-stroke` and `#modal-shape` (v2.9.0) extend the same rule to the drawing and shape tools.** `STROKE_TOOLS` (Lápiz, Línea, Flecha, Flecha curva, Semicírculo) open the first from `selectTool`; `SHAPE_TOOLS` (the eight of Formas) open the second, which carries the whole **Relleno** block on top of the stroke — that panel section exists only for them. Both work exactly like the Eraser's size modal and, like it, are *not* in `opensVariantModal`: closing leaves you on the tool, ready to draw. Their live previews draw the real thing (a line vs an arrow; a pentagon vs a circle) with the current settings, so «Doble punta» is dimmed on a line and a filled pentagon looks filled before you drag. The ⚙ in the panel's «Trazo» heading is one button that opens whichever applies (`syncPanelSections` retargets it, and hides it for tools that have none). **`#modal-stroke` was built the other way round first — not opening on selection, only the ⚙ plus a re-entry click — on the reasoning that the pencil is the most-used tool and a modal on every change would be in the way. The user rejected that: the promise "picking a tool shows its settings" is the whole point of the rule, and an exception for the most-used tool is where it matters most.** Don't reintroduce the exception.

**`#modal-text` and `#modal-ui` (v2.10.0) complete the rule for the UI group** — Mover and «Select» (v2.11.0) are now the only tools with no settings modal (the guards' "tool that opens nothing" baseline uses Mover). Texto opens the first (font-size twin of `#font-slider`, colour, preview); Botón/Input/Imagen/Navbar/Tarjeta share the second (`UI_MODAL_TOOLS`), retitled per tool by `syncUiControls()`, whose preview draws the real component via `Renderer.renderElement` scaled to fit (the nav is 600×50). Its **Rótulo** field goes through `applyLabel` — the same body as the panel's `#el-label` — and is dual: with a selection it edits the element's `label`; without, it writes `state.uiLabels[tool]`, the creation default the UI branch of `onMouseUp` stamps on new components (empty = renderer default; `imagePlaceholder` has no label and its row hides). `uiLabels` persists in prefs (known keys, strings, trimmed to 120 chars — they end up in `label`, which travels in exported JSON). Neither modal is in `opensVariantModal`.

**Pulsar la herramienta del elemento seleccionado lo edita (v2.10.0).** `selectTool` used to clear the selection unconditionally, so the settings modals could only ever configure creation defaults. Now `MODAL_EDIT_TYPE` maps each settings-modal tool to the **exact** element type it edits (pencil/line/arrow/curveArrow — the Semicírculo maps to `curveArrow`, which is what it creates —, the eight shapes, `text`, the five UI types), and the selection survives when it contains at least one element of that type; the modal then opens showing the selection's values, and the existing dual semantics do the editing — geometry included. Exact-type on purpose: "press the tool of the selected element to edit it" fits in one sentence, and pressing Rectángulo with a circle selected deselects like it always did. Starting any creation gesture on the canvas (`onMouseDown`, right after the SELECT branch) drops the kept selection — otherwise the panel would keep editing the old selection while you draw something new. Catalogues, the Eraser and Emoji still clear.

**The two Edición tools never clear it at all (`SELECTION_TOOLS`, v2.12.0).** Mover and «Select» are the tools that work *on* the selection — one moves, resizes and duplicates it, the other builds it — so neither empties it when picked, in either direction. They aren't in `MODAL_EDIT_TYPE` (they have no settings modal), so they were falling into the unconditional `setSelection([])` inherited from pre-2.10.0, and that broke the natural division of labour the moment «Select» existed: frame several objects with «Select», press Mover to move them, and the drag moved only the one under the pointer because the selection was gone. Guarded by *"seleccionar varios con «Select» y pulsar Mover los mueve TODOS a la vez"* — plus its reverse and a third guard pinning that creation tools still clear, so the fix can't drift back into "never clear".

**The UI components' renderer defaults are Spanish since v2.10.0** («Botón», «Escribe aquí...», «Título», nav «Inicio/Nosotros/Contacto») — they were English in an app whose UI was always Spanish. They are duplicated in exporter.js (SVG and HTML branches) and pinned by `tests/sketchy-renderer.test.js` and `tests/exporter.test.js`: change them in both places or the exports lie.

Two consequences of nearly every tool now opening something:

- **Returning to the "previous tool" after cancelling a catalogue would chain a second modal** on top of the one just closed. `selectTool(id, { silent: true })` selects without opening, and `wireBuildModalCancel` uses it: a previous *catalogue* still falls back to `TOOLS.SELECT` (reopening it would put you back to picking a variant, which is not what cancelling asked for), but a previous tool that only opens *settings* is restored silently. Dumping every case on Mover would be the easy path and the worse one. Guarded by *"cancelar un catálogo recupera la herramienta sin encadenar modales"*.
- **`e2e/helpers.js`'s `selectTool()` closes the five settings modals** (`SETTINGS_MODALS`: eraser, stroke, shape, text, ui) after picking a tool, because a `<dialog showModal>` makes the canvas inert and every drawing spec would otherwise time out. Catalogues are deliberately *not* in that list — those specs need to pick a variant. Specs that assert the *opening* click the sidebar button directly instead (`e2e/panel.spec.js`).

### «Select» (solo selección, v2.11.0)

`TOOLS.PICK` («Select», grupo Edición, entre Mover y Borrador) es una herramienta de **solo selección**: el clic selecciona con exactamente la misma semántica que Mover (grupo completo vía `groupIndicesOf`, Alt aísla la pieza, doble clic desciende, Shift hace toggle vía el helper compartido `shiftToggleAt`, y «Los clics acumulan selección» añade/retira), y el arrastre dibuja **siempre** marquesina — incluso naciendo encima de un elemento, el gesto que con Mover lo movería y que era imposible de hacer en un lienzo denso. Nada se desplaza jamás con ella. Cuatro decisiones que hay que conservar:

- **El gesto entero se resuelve en el bloque de marquee de `onMouseUp`** (vía `state.pickDown`): hasta soltar no se sabe si fue clic o marco, así que el `mousedown` no toca la selección — un clic necesita la selección vieja intacta para poder acumular o retirar, y un marco la sustituye él mismo con `setSelection`. Con Mover ese camino no se pisa: su clic se resuelve en `mousedown` y su marquesina solo nace en el vacío.
- **No dibuja handles** — `handlesOn` en `redrawNow` sigue siendo `state.tool === TOOLS.SELECT` a propósito: un handle promete un resize que el hit-test de PICK nunca haría (regla v2.10.1: no dibujar promesas que el mousedown no cumple).
- **El doble clic desciende a la pieza pero NO abre editores** ni resetea curvaturas: es una herramienta que no modifica nada. La rama `picking` del handler dblclick corta antes de los editores de texto.
- **Sin atajo** (las 26 letras y los 10 dígitos están cogidos — misma situación que Balcón) y **sin modal de ajustes** (como Mover, no hay nada que ajustar). El cursor es `default` (`.canvas-area__canvas--pick`, CSS puro que el arnés vm no ve — guardado en `tests/smoke.test.js`). El orden exacto del grupo Edición (`select`, `pick`, `eraser`) y su condición de única herramienta sin tecla del grupo están fijados en `tests/config-templates.test.js`; el comportamiento, en `tests/app-interaction.test.js` y `e2e/select-tool.spec.js`.

### Emoji

`TOOLS.EMOJI` is creation-mode only, like `TOOLS.ARC` — **not an element type**. Picking the tool opens the `#modal-emoji` catalogue (built from `EMOJI_GROUPS` in config.js) — respecting `selectTool`'s `silent` flag, or cancelling a Building/Garden catalogue with Emoji as the previous tool would chain this one on top (auditoría v2.10.1) — and `placeEmoji()` stamps the chosen character as an ordinary `text` element centred on the click, at `state.emojiSize` — its own setting since v2.10.0 (the `#emoji-modal-size` slider in the catalogue, `EMOJI_MIN_SIZE`–`EMOJI_MAX_SIZE` = 32–96, persisted in prefs), no longer tied to `state.fontSize`: growing an emoji must not shrink the next text. With Emoji active and no selection, the panel's «Texto» section **retargets** to it (`#font-label` says «Emoji», the slider drives `state.emojiSize` through `applyEmojiSize`, min 32) — the eraser/stroke-slider pattern; before that retarget the section was a dead control for the Emoji, and pre-2.10.0 the slider *did* govern it. Both font sliders reach `EMOJI_MAX_SIZE` (96) so a selected big emoji doesn't overflow them. Because it is just a `text` element, rendering, hit-testing, resize, undo, autosave and all five export formats work with no emoji-specific code — keep it that way rather than introducing an `emoji` type. The catalogue is injected with `textContent`, never `innerHTML`.

### Edificios (sección)

The **Edificios** sidebar group draws a building's exterior. Like `TOOLS.ARC`/`TOOLS.EMOJI`, **every building tool is creation-mode only — none is an element type**; each drag produces plain `rect`/`line`/`circle`/`curveArrow` elements (via `src/js/building.js`), so render/export/undo/JSON/bounds work with no building-specific code. The one required sync point is `CREATION_ONLY_TOOLS` in exporter.js: it must include `...BUILDING_TOOLS` so `isValidElement` never accepts `type:'planta'`/`'puerta'`/… as a phantom element on JSON import. `paintOverlay` (app.js) draws the drag preview by calling `Building.elements` and stroking each `line`/`rect`/`circle`/`curveArrow` (helper `drawPiecesPreview`, which honours each piece's own `lineWidth`), so the preview always matches what is committed.

Every building tool opens a **shape-picker modal** on selection, mirroring the pattern (like `#modal-emoji`): **Planta** → `#modal-planta` (`PLANTA_SHAPES`, `state.plantaShape`), **Fachada** → `#modal-facade` (`FACADE_TYPES`, `state.facadeShape` = flat/gable/profile), **Tejado** → `#modal-roof` (`ROOF_TYPES`, `state.roofShape`), **Puerta** → `#modal-door` (`DOOR_TYPES`, `state.doorType`), **Ventana** → `#modal-window` (`WINDOW_TYPES`, `state.windowType`), **Balcón** → `#modal-balcony` (`BALCONY_TYPES`, `state.balconyType`), **Muro** → `#modal-wall` (`WALL_VIEWS`, `state.wallView`), **Verjas** → `#modal-fence` (`FENCE_VIEWS`, `state.fenceView`) and **Cancela** → `#modal-gate` (`GATE_VIEWS`, `state.gateView`). The first five are built by hand-written `build*Catalog`/`update*Active` pairs with inline-SVG icons (`plantaIcon`/`doorIcon`/`windowIcon`) — the arch uses an SVG path `A` command with **`sweep-flag=1`** to bulge up (y-down coords) — and their `update*Active` queries are scoped to their own catalogue (`$('planta-catalog').querySelectorAll(...)`) so the shared `.modal__shape` styling doesn't cross-toggle. **Balcón, Muro, Verjas and Cancela instead go through the generic `VARIANT_MODALS` table**, so their icons are the real geometry. Every catalogue is built with `createElement`/`createElementNS`/`textContent`, never `innerHTML`. The chosen state is passed into `Building.elements` as creation defaults; all nine tools persist their variant and applicable settings in prefs, validated against `BALCONY_TYPES`, `WALL_VIEWS`, `FORGE_TYPES`, `FENCE_VIEWS`, `GATE_TYPES` or `GATE_VIEWS`. Regression guards live in `tests/building.test.js`, `tests/app-interaction.test.js`, `e2e/fence.spec.js` and `e2e/gate.spec.js`.

**Balcón** draws a railing over a cantilevered slab in elevation, like Puerta and Ventana (8 types: barrotes/francés/forja/balaustrada/corrido/acristalado/terraza/mirador). Three things to know:

- **It is the only building tool whose default box depends on the variant**, because a mirador is tall and a balcón corrido is a strip, whereas a door measures the same whatever its type. `DEFAULTS` in building.js therefore gained a generic `variantKey`+`byVariant` resolution (the same idea garden.js uses for all its tools); only the balcony declares them. Guarded by *"el clic sin arrastrar da la caja propia de cada tipo de balcón"*.
- **The catalogue icon is drawn with a null drag on purpose** (`box: {x:0, y:0}` in `VARIANT_MODALS`), so `byVariant` picks each icon's box and the icon shows the type's natural proportion — which is what tells half the catalogue apart at that size. The garden entries keep their fixed 100×84 box.
- **It has no keyboard shortcut**, and neither do Muro, Verjas or Cancela: all 26 letters and 10 digits are taken, and `f`/`q`/`d`/`s` belong to curve-arrow actions checked before `TOOL_KEYS`. Pinned by *"el sidebar de Edificios y BUILDING_TOOLS son la misma lista"* in `tests/config-templates.test.js`, which also fixes the exact keyless list (`['balcon', 'muro', 'verja', 'cancela']`).

**Muro** draws a perimeter wall in either **plan view** (a footprint strip seen from above, like the sibling `#modal-plot` idea in Jardín) or **elevation view** (a face seen from the front, like Balcón). It combines a `VARIANT_MODALS` catalogue (2 entries, `WALL_VIEWS`, keyed by `wallView`) with settings orthogonal to that view: material (stone/concrete/**brick**), wall height (1/2 m), optional wrought-iron top railing with its own design and height, and one of **18 gate styles** plus «Sin puerta» and gate height. The precedent for this hybrid is **Camino** in Jardín (§ below), not a new pattern: `#modal-wall` gets a live thumbnail (`renderWallPreview`) and its own sync point (`syncWallControls`, called from `selectTool` right where `GARDEN_PATH` calls `syncPathControls`). **All settings stay enabled and visible in both views** — v2.3.1 fixed the opposite: dimming height and railing while the view was `plan` put them out of reach, because clicking a view commits and closes the modal. Treat that as the rule: in a hybrid catalogue+settings modal, a setting reachable only in the other variant is a dead end. Hence `_wallRailingPlan` (the handrail seen from above) and the plan footprint growing with declared height. **The height is the drawing's scale, not just its default box**: `_wallPxPerM` (`b.h` ÷ metres) drives course height, block width, concrete lifts and railing height, so «2 m» is visible at *any* drag size. Stone is irregular masonry from deterministic `_noise`; brick uses regular courses with alternating perpends; concrete stays visually plain apart from construction lifts. Because the default box depends on view and height, building.js derives `wallSizeKey` itself (`'plan1'`/`'plan2'`/`'h1'`/`'h2'`). The **entrance is a cancela, not a hole with bars**: two capped piers, leaves, defensive finials and a wall body split at the passage. The gate's own height is `o.wallGateHeight`, in metres on the `_wallPxPerM` scale (`#wall-gate-height`, clamped to `WALL_GATE_H_MIN/MAX`). `_wallGateRange` returns free span, pier width and the complete passage span that texture, railing and wall body must avoid.

The gate selector now contains **18 entries** from the shared `GATE_TYPES`: straight-bar `single`/`double`; nine concave styles (`concave`, `concaveSwan`, `concavePanel`, `concaveOrnate`, `concaveFan`, `concaveLyre`, `concaveDiamond`, `concaveRings`, `concavePalmette`); four monumental convex styles (`convexPanel`, `convexFan`, `convexMedallion`, `convexBlind`); and three urban portals (`solidTransom`, `openBars`, `openScrolls`). They remain ordinary `<option>`s in `#wall-gate-type`, because gate style is orthogonal to the plan/elevation catalogue. **The top railing's height and style are settings too** (`wallRailingHeight`/`wallRailingType`); the height is clamped to `WALL_RAIL_H_MIN/MAX`. The tool opens on `elevation` + `concave`; `wallDesignVersion` prevents historical default prefs (`plan` + `none`) from silently hiding that redesign.

**Verjas** and **Cancela** are autonomous siblings of Muro. Both use a hybrid modal: `FENCE_VIEWS`/`GATE_VIEWS` choose plan or elevation, while a `<select>`, a 0–350 cm slider and a live preview choose the model and physical height. `syncFenceControls`/`renderFencePreview` and `syncGateControls`/`renderGatePreview` are their single sync points. Verjas draws the 13 `FORGE_TYPES`; every design has a defensive finial and `_forgeFinial` gives each blade a distinct classical profile. Cancela draws all 18 `GATE_TYPES` without wall fabric by building its own opening and reusing `_wallGatePlan`/`_wallGateElevation`. Their independent prefs are `fenceView`/`fenceType`/`fenceHeightCm` and `gateView`/`gateType`/`gateHeightCm`; the exported module limits (`FENCE_H_MIN_CM/MAX`, `GATE_H_MIN_CM/MAX`) must match the HTML sliders and are pinned by `tests/smoke.test.js`.

`#modal-facade` is the one that carries more than a catalogue among the hand-written five, because Fachada is the only one of those with parameters. It holds a **live thumbnail** (`#facade-preview`) plus twins of the panel's four building fields (`#facade-floors`/`#facade-bays`/`#facade-roof-type`/`#facade-roof-pitch`), so a view can be chosen without hunting for the panel. Four rules keep it honest:

- **One opts builder.** `buildOpts()` is the single source for every `Building.elements` call — drag preview, commit, and thumbnail. Never inline a fresh opts object; a field added to one and not the others makes preview ≠ result.
- **Hole types belong here too.** `#facade-door-type`/`#facade-window-type` are filled by `fillVariantSelect()` from `DOOR_TYPES`/`WINDOW_TYPES` and write the same `state.doorType`/`windowType` as the Puerta/Ventana tool modals (calling their `update*Active` so both paths agree). Without them the facade flow could not reach the very types it draws — the Puerta/Ventana tools change the active tool.
- **One sync point.** `syncBuildControls()` pushes `state` into *both* control sets, refreshes the thumbnail and runs `updateFacadeFieldsEnabled()`. Every handler (panel *and* modal) calls it. Assigning `.value` fires no events, so the twins can't loop. The twin `<select>` options and slider range must stay identical — guarded by *"los controles gemelos de Edificios (panel y modal) ofrecen lo mismo"* in `smoke.test.js`.
- **The thumbnail reuses the real painter.** `renderFacadePreview(shape?)` calls `Building.elements` + `drawPiecesPreview` (the same pair the drag overlay uses) and fits the result by its own bounds — cornice, eaves and rasante fall outside the drag box. It paints `state.canvasBg` as paper first: the modal is dark and the drawing ink is not. Passing `shape` previews a view without selecting it (hover/focus).
- **Names promise nothing about the roof.** `FACADE_TYPES` entries carry a plain-language `name` plus the architect's term as `hint`; the Alzado icon draws the *active* `state.roofType` (`FACADE_ROOF_PTS`). Neither text may name a roof shape — `_gable` takes it from `state.roofType`, so "Alzado (2 aguas)" was a lie whenever hip/mansard was set. Guarded by *"el catálogo de Fachada no promete una cubierta concreta en el nombre"*.

`updateFacadeFieldsEnabled()` dims the settings the chosen view ignores (flat has no roof at all; profile always draws its own trapezoidal one, `_profile` never reads `roofType`). Clicking a view still commits and closes, as in the other four modals — only the parameters live-apply.

The **panel** has an "Edificios" section (`#build-floors`/`#build-bays`/`#build-roof-pitch`/`#build-roof-type` → `state.buildFloors`/`buildBays`/`roofPitch`/`roofType`) wired in `wireControls`. These are **creation defaults only** — building tools are creation-only, there is no "building" element to edit, so they do NOT follow the dual panel semantic (like the stroke-colour picker) and persist in prefs — as do the variants and settings of the nine building tools, so the whole section survives a reload or none of it does. Each of the four also exists as a twin inside `#modal-facade`; both sets are wired in pairs (`wireBuildPair`) against the same `state` and reconciled by `syncBuildControls()` (see above), so adding a fifth setting means adding it in **both** places or not at all.

Each building is created as a **group**: the `onMouseUp` building branch stamps a shared `buildingGroupId` (`newId()`) on every piece when a drag yields ≥2 elements. `groupIndicesOf(idx)` expands a hit to the whole group so a plain click selects the building as a unit (move/duplicate/delete already iterate `state.selection`); **double-click on a piece of the selected group descends to it** (the one-pointer way in, since v2.2.0 — the dblclick handler checks `selection.length > 1 && selection.includes(idx)` before falling through to the text editors), and **Alt+click** is the accelerator. The one-hand rule covers modifier+*click* chords too, not just modifier+drag: Alt+click as the *only* way in was an audit defect. Same pattern for disjoint multi-selection: the panel checkbox **«Los clics acumulan selección»** (`state.multiSelect`, not persisted — same as «Ajustar a cuadrícula») makes a click *add* the group and a **click without drag** on something already selected *remove* it (recorded as `state.pendingUnselect` in `onMouseDown` — also in the combined-frame branch, which captures those clicks — and consumed in `onMouseUp` only if `didDrag` stayed false, so dragging the selection keeps working); Shift+click stays as the accelerator.

Because a building is *always* a multi-selection, it interacts with the "drag the selection from anywhere inside its combined frame" convenience in `onMouseDown`: that frame covers the whole facade. **`hitTest` must run before that branch, and the branch must yield when the point lands on an element outside the selection** — otherwise anything drawn on top of a building becomes unreachable (click selects nothing new, drag moves the building, Delete deletes the building). Guarded by `tests/app-interaction.test.js`; the third test there pins the convenience itself, so don't "fix" a regression by removing it. `insertClones` reassigns a fresh `buildingGroupId` per cloned building (a copy is an independent group), and `selectionGroupBounds` draws one combined selection box. `isValidElement` (exporter.js) validates `buildingGroupId` as an `ID_RE` string so it survives the JSON round-trip.

Group **resize** works as a unit (v2.7.1). It was deliberately skipped when groups arrived, on the reasoning that resize could stay single-element — but once Edificios and Jardín made *most* of what you draw a group, that exception swallowed the feature: clicking anything you had just drawn gave a multi-selection, and multi-selections drew no handles, so in practice resizing had disappeared from the app. `selectionGroupBounds()` now draws its combined box **with** handles, and `resizeGroupTo` scales every piece through the same `scaleElement` used for one element. Three things to keep:

- **The handle hit-test must run before the combined-frame drag branch** in `onMouseDown`. The handles sit exactly on the corners of the frame you drag the group from, so with the other order grabbing a corner would move the group and there would be no way to scale it. Guarded by *"arrastrar por dentro del marco sigue moviendo el grupo, no escalándolo"*.
- **The group scale is UNIFORM**, unlike the free two-axis stretch a lone element allows. A group carries arbitrary pieces, and a free stretch would break invariants that belong to them: regular polygons require `w === h` and `isValidElement` **rejects** deformed ones on import, so a free scale could produce a project that no longer opens. Guarded by *"el resize de grupo conserva la proporción y no invalida las piezas"* — which also asserts the group actually grew, or it would pass vacuously by nothing happening at all.
- **`scaleElement` maps each element's own coordinates** (`mapX(el.x)`, `el.w * sx`) rather than snapping to the destination box. For a single element the two are identical, because `from` *is* that element's bounds; for a group member, assigning `to.x`/`to.w` directly would pile every piece onto the group's origin.

**Since v2.12.0 those handles belong to ANY multi-selection**, not only to a `buildingGroupId` group: `onMouseDown` and `redrawNow` take the box from `selectionBounds()` whenever `selection.length > 1`, and `resizeGroupTo` — already generic over `r.group`/`r.originals` — does the rest. Scaling "whatever is selected" never needed the selection to be a building, and typing measures had allowed it since v2.10.1, so the mouse was the odd one out. Two details that are deliberate: the scale stays **uniform** for the same invariant reason as groups (a hand-picked selection can contain regular polygons too), and a loose multi-selection keeps its **per-element highlights in addition to** the combined box — the box alone can't say *which* elements are selected, since it also covers gaps and neighbours. A building group still draws only the combined box: its pieces number in the dozens and it is manipulated as one thing.

**Panel controls show the selection's common value (v2.12.0).** The dual-semantics block in `redrawNow` used to sync only for a *single* selection, leaving every control stale with several — the panel showed the black and 2px of the creation defaults while three red 7px shapes were selected, even though touching a control did change all three. `commonOf(els, get)` returns the value all elements agree on, or `undefined` when they differ, and each control is computed over the elements it **affects** (arrows for «Doble punta», `FILLABLE_TYPES` for the fill block, texts for the font size) rather than over the whole selection. When there's no common value the control is left untouched: showing the first element's value would claim the others match it. Guarded by *"el panel enseña el valor común de la selección, y no lo inventa si discrepan"*.

### Jardín (sección)

The **Jardín** sidebar group has eight **creation-only** tools (`GARDEN_TOOLS`) covering 67 variants. Plot, decor and paths are plan-only; the 49 tree/shrub/flower/herb/climber species support plan and elevation. Every drag still produces plain existing-type elements via `src/js/garden.js`. `CREATION_ONLY_TOOLS` in exporter.js must include `...GARDEN_TOOLS`, or a tool id becomes a phantom element. Grouping **reuses `buildingGroupId`**. Plant groups also repeat a strict, versioned `gardenMeta` record on every piece (tool, variant, insertion points, original color/line width and all botanical controls): `moveElement` shifts those insertion points, cloning preserves them under a new group id, and exporter validation whitelists every field/range so imported metadata is safe to regenerate.

Four things differ from Edificios and are deliberate:

- **One generic catalogue builder, not one per tool.** `VARIANT_MODALS` is a table of `{tool, modal, root, cls, data, catalog, key, gen, opts, box, plant?}` entries — the eight garden ones plus Balcón, Muro, Verjas and Cancela — driving `buildVariantCatalog(cfg)` / `updateVariantActive(cfg)` and the `selectTool`/`setupModals` hooks. `plant:true` installs the shared preview/view/stage/scale/color/label controls. `gen`/`opts`/`box` let non-garden tools join; `opensVariantModal(tool)` is the one predicate both hooks use. New catalogues should be added through this table.
- **Icons are the real geometry, not hand-drawn SVG.** `variantIcon(cfg, variantId)` paints a `<canvas>` with `cfg.gen().elements` + `drawPiecesPreview`, fitted by real bounds. The 67 icons therefore cannot drift from creation geometry. Plant modals also use `renderPlantPreview` on a larger canvas and expose live botanical dimensions. A plant icon's box comes from `plantIconBox()`: the species' **botanical proportion**, scaled so the longer side is `ICON_MIN_SPAN` (64 px). It must not be the raw click-sized box — at 20 px/m a 0.25 m *Acis valentina* came out 5 px wide, where every `Math.max(1.2, …)` floor in the geometry (there to keep petals from vanishing) takes over, the details collide, and fitting-to-bounds blows that smudge up to fill the tile. Two species then shared one icon; the caléndula, the tomillo and the boca de dragón had carried that smudge since v2.7.0. Guarded by *"los iconos de plantas usan la caja botánica, no un rectángulo genérico"*.
- **`drawPiecesPreview` (ex-`drawBuildingPreview`) must handle every type a creation tool can emit.** What's missing doesn't throw — it just isn't drawn, and preview stops matching the result. It had a latent bug on exactly this: chained `curveArrow`s have no top-level `cx`/`cy`, so `quadraticCurveTo(undefined, …)` was a silent no-op. It now walks `CurvePath.segments` and delegates `text` to `Renderer.renderElement` rather than re-implementing font/anchor/line-height.
- **Shortcuts are `8 9 h x z`** — the only five plain keys that were left, so **Caminos, Aromáticas and Trepadoras have none** (`key` is optional in `TOOL_GROUPS`), and any further garden tool arrives keyless too. `f`, `q`, `d` and `s` are already taken by curve-arrow actions that are checked *before* `TOOL_KEYS` and only when a `curveArrow` is selected; since every garden piece contains curves, reusing one would fail intermittently and silently. Pinned by `RESERVED_PLAIN_KEYS` in `tests/config-templates.test.js`, which also pins the *exact* keyless list, so a tool can neither lose its key in a refactor nor gain one that collides.
- **Two pitfalls in the `LOBES` tables** (`_blob`'s radius multipliers): a table that alternates high/low over few points has low-order symmetry and reads as a polygon — 8 points alternating gave a rhombus, not a clump. Over many points the same alternation is a *feature*: `carob` uses 14 for a scalloped crown. And two variants of the same tool must not differ only in their table, or they become indistinguishable at icon size (that was "Frondoso" vs "Olivo"); give them different structure instead. Guarded by *"dentro de un catálogo, dos variantes nunca se dibujan igual"* in `tests/garden.test.js`, whose signature is the element-type multiset **plus the overall aspect ratio** — proportion is a legitimate way to differ (Rectangular vs Cuadrada carry the exact same pieces), so a new variant must change one or the other.
- **Caminos is its own tool, and its two axes are four variants — not two panel checkboxes.** The camino comes in serpenteante/recto × liso/empedrado. They live as four catalogue entries because in this section the variant is what picks the default box and names the label; a checkbox would have neither. And they got their own sidebar button (`TOOLS.GARDEN_PATH` / `PATH_TYPES` / `#modal-path`) rather than staying in Decoración, where four near-identical strips filled half the catalogue and buried the rest. Guarded by *"los caminos viven en su propia herramienta, no en Decoración"*. `_pathTool` derives both axes from the explicit `PATH_VARIANTS` table (never by sniffing the id string) and computes the wave **once**, in `_at`, because the cobbles have to ride the exact same curve as the edges — a second copy of that sine is a guarantee they eventually drift apart. **By default, the drag is read as a box, and both the route and the thickness come out of it**: the long side is the route, the short side the thickness — so moving the mouse perpendicular while dragging fattens the path. That is the *only* way to get both from one gesture without a modifier key or a second step, and it is why a plain drag comes out horizontal or vertical. An any-angle version shipped briefly in 1.19.0 and was reverted in 1.21.0 because it took over the drag vector itself and, with it, the mouse-driven thickness the user preferred. **v1.23.0 reintroduced free angles as an opt-in, and v1.24.0 made that opt-in reachable with one hand.** The primary control is a **sticky setting**, `state.pathAnyAngle` — a checkbox that exists twice (`#path-any-angle` in the Camino catalogue, `#check-path-any-angle` in the panel), persisted in prefs. **A held modifier could not be the only way in: Shift+drag needs two hands, and the user this was built for has the use of one.** Treat that as a standing constraint, not a one-off fix — any future gesture whose only form is modifier+drag is a defect. `state.pathFreeAngle` (the Shift transient, mirroring `state.curveFlip`'s three touch points — `onMouseDown`, `onMouseMove`, and the drag-commit tail) survives as an *optional* accelerator, and `gardenOpts()` ORs the two. `elements()` picks `_pathAxisFree` over `_pathAxis` when `o.freeAngle` is set — same signature, same consumers (`_pathTool`/`_pathBox` don't change at all) — but `ux`/`uy` come straight from the raw drag vector and the width comes *exclusively* from `o.pathWidth`, exactly like a box-mode click or straight drag, because there is no short side left to read one from. **Unlike `curveFlip`, the angle flags are threaded into `gardenOpts()`** — the catalogue icons read it too, to keep the one-opts-builder discipline — so the Shift transient must be reset to `false` explicitly at the end of every `GARDEN_PATH` commit (the shared `onMouseUp` tail) rather than left for the next `mousedown` to clear; `curveFlip` never needs that because nothing icon-related reads it. The sticky flag can't be reset that way (it's meant to persist), so the Camino row of `VARIANT_MODALS` carries its own `opts: () => ({ ...gardenOpts(), freeAngle: false })`: **the icons are there to tell the four *trazados* apart (serpenteante/recto × liso/empedrado), not to show the angle**, and at 56 px a diagonal drawn at the panel's width — up to 120 px over a 95 px route — is a blob, the same reasoning that gave the row its fixed `box` in v1.20.0. What *does* show the live angle and width is `renderPathPreview()`, the `#path-preview` thumbnail beside them, built on the `renderFacadePreview` pattern (real geometry through `drawPiecesPreview`, fitted by real bounds, `state.canvasBg` as paper, reusing the `.modal__preview`/`.modal__build` CSS so the ≤420 px stacking comes for free). Its sample drag is deliberately **short-side-free** — dead straight, or a clean diagonal when the setting is on — because that is exactly the case where the width comes from the slider in *both* modes, so the thumbnail can never promise a thickness the drag then overrides. `syncPathControls()` is the single sync point for both twin pairs plus the thumbnail, same contract as `syncBuildControls()`. Finally, `drawPathAngle()` rotulates the live angle beside the pointer during the drag (protractor convention: 0° right, positive up, hence the negated `atan2` — canvas y grows downward). It is **overlay-only** — cleared with the rest of `paintOverlay` every frame, never an element, never in undo/autosave/export — and deliberately silent in box mode, where the path can only come out at 0° or 90° and the number would be noise. The cobble-flattening ratio (`rx`/`ry` in `_pathTool`) is a continuous function of `ax.ux`/`ax.uy` rather than a horizontal/vertical `if`, so a diagonal path never hits a visible seam at 45° — it reduces to the old fixed 0.82 ratio at the two angles box mode can ever produce, and to an almost-round stone on the diagonal. When the short side is under `MIN_SPAN` (a click, or a dead-straight drag) the width falls back to `o.pathWidth`, the panel setting — that is the setting's whole job. The drag-derived width is deliberately *not* clamped: there the user sees exactly what they draw. `elements()` still branches for `GARDEN_PATH` before the generic box, because its default is a *length*, not a size, and because `_pathBox(ax)` gives the label a box measured on the drawn band rather than on the drag. There is **one geometry, not one per orientation**: everything is computed in path coordinates (`u` = fraction travelled, `v` = offset from the axis) and `_p(u, v)` rotates it onto the canvas. **`v` is measured along the same direction `_wave` takes as its normal**, so `_at` applies unchanged either way and no stray sign can creep in between the edges and the cobbles — a bug that would be invisible in the horizontal case, which is why the guards check both. **The paving grows in rows, not in stone size** (`PATH_ROWS`/`PATH_ROW_H`/`PATH_SPREAD`): with two fixed rows a 90 px path was paved with half-metre boulders and read as a row of balloons. `PATH_STONES` caps the total, since `PATH_COLS` only bounds one row. Cobble size follows the path's *width*, like real paving, so the count grows with its length; `PATH_COLS` is only a flood guard, and past it the empedrado thins out rather than stopping half-way.

The **panel** keeps the global label switch and Camino's angle/width controls. Botanical defaults live in each plant modal and persist globally (`plantView`, `plantStage`, `plantScalePct`, `plantPxPerM`, `plantColorMode`, `gardenLabelMode`). A complete plant-group selection exposes `#btn-edit-garden`; `editSelectedGarden()` restores its metadata, and choosing a species calls `regenerateGardenGroup()` to replace the group at the stored insertion points with one undo snapshot. Cancel must clear `editGardenGroupId` without touching the original. Labels remain ordinary `text` elements inside the group.

### Shape fill

Only `FILLABLE_TYPES` (rect, roundedRect, circle, triangle, pentagon, hexagon) take a fill; UI components carry their own as part of their design. Four fields control it: `fill` (boolean, on/off), the optional `fillColor` (hex), the optional `fillTransparent` (boolean), and the optional `fillOpacity` (number from 0 to 1, defaulting to 0.4 when absent). They are deliberately independent — the "Rellenar formas" checkbox toggles `fill` only and never touches the others, so emptying and refilling a shape recovers the same color, mode and opacity. "Relleno translúcido" and the opacity slider have the standard dual panel semantics: with a selection they update selected fillable shapes, using one undo step per slider gesture; without a selection they set creation defaults. Solid mode is represented by the absence of `fillTransparent`, preserving backward compatibility.

`Renderer.fillStyle(el)` is the single place that resolves these fields. Transparent mode converts `fillOpacity` to an 8-bit hex alpha and applies it to `fillColor || color`; otherwise it uses `fillColor || color + '20'`. A translucent shape without `fillOpacity` must remain at the legacy 40% (`0x66`). Therefore **a shape without `fillColor` keeps the classic translucent stroke tint**, and older projects render identically — preserve both fallbacks. SVG and HTML exports mirror this resolution. `isValidElement` validates `fillTransparent` as a boolean, `fillOpacity` as a finite number in `[0, 1]`, and `fillColor` as hex because they affect serialized/exported output.

### Shape overlap mode

`state.overlapMode` is a global scene setting with two valid values: `normal` (default and backward-compatible) and `hidden-dashed`. `Renderer.renderElements(ctx, elements, mode)` must be used for whole-scene rendering so it can compare geometric shapes by z-order. In hidden mode it samples the real outlines of rect, roundedRect, circle/ellipse, triangle, pentagon and hexagon shapes, assigns every covered segment to the highest later shape containing it, draws visible segments solid, and defers hidden segments until after that covering shape's fill. Only hidden segments use `[4 * lineWidth, 4 * lineWidth]`; the upper outline stays solid.

The setting is persisted in prefs, autosave and exported JSON (`settings.overlapMode`). `Exporter.importJSON()` keeps its array return API and exposes the imported mode as the non-enumerable `elements.overlapMode` property. PNG/JPG call the coordinated renderer; SVG and hidden-mode HTML use the same overlap plan. Old autosaves (bare element arrays) and JSON without settings resolve to `normal`.

### Coordinate handling

Zoom is applied as a CSS `transform: scale()` on the canvas wrapper; `getPos()` in app.js divides mouse coordinates by `state.zoom` so element coordinates are always in unscaled canvas space. A `transform` does **not** grow the layout box, so `.canvas-area__sizer` wraps the canvas and `applyZoom` sets its width/height to `CANVAS_W/H * zoom`; the wrapper uses `transform-origin: top left` plus `width: fit-content` (without it the wrapper stretches to the already-scaled sizer and the transform scales it a second time). Keep all three in sync or the zoomed-in canvas becomes partly unreachable by scroll (see `BUGS.md`). `fitZoomToViewport()` auto-picks the largest zoom (floored to a 10% step, never below 100%) that fits `.canvas-area`'s available size, run on init and on window resize; it backs off permanently once the user touches the zoom slider (`zoomManual` flag), so manual choices are never overridden. `ZOOM_MIN`/`ZOOM_MAX` (0.3–3) bound both `applyZoom` and the auto-fit, and **must be kept in sync with the `#zoom-slider` min/max in index.html**.

**Moving a selection is clamped to the canvas (`clampDelta`/`moveSelectionBy`, v2.12.1).** `onMouseDown` calls `setPointerCapture`, so a drag stays alive far outside the canvas and `getPos` happily returns coordinates well past `CANVAS_W`/`CANVAS_H` — nothing related element coordinates to the fixed 1200×800 canvas, so flinging something off the edge *lost* it: still counted in «Elementos» and still travelling inside exported JSON, but invisible and unreachable (a click can't land out there and a marquee can only be drawn over the canvas, so even select-all didn't bring it back). Every path that moves a selection now goes through `moveSelectionBy` — the drag, the arrow-key nudge and the X/Y fields of «Posición y tamaño» — keeping `KEEP_VISIBLE` (24) px of the box on canvas, or the whole object when it is smaller. Four properties to preserve, each with a guard:

- **The clamp applies to the selection's combined box, never piece by piece** — clamping each element separately would dismantle a building against the edge instead of stopping it as one thing.
- **It only limits movement that makes things worse.** An element already outside (a project saved before this version) must still be draggable back in, and moving a selection that contains one must not yank it to the edge and break its position relative to the rest.
- **`dragLast` stores the pointer's real position, not the clamped one**, so when the pointer comes back the object follows from the first pixel instead of having to re-cross the distance it overshot.
- **`applyGeometry` clamps before its no-op guard**, so a typed X of 9000 resyncs the field to where the element actually ended up rather than promising a position it doesn't have.

### Canvas background / grid color

`state.canvasBg` and `state.gridColor` (defaults `DEFAULT_CANVAS_BG`/`DEFAULT_GRID_COLOR` in app.js) are cosmetic prefs, not part of `state.elements` — they persist to their own `localStorage` key (`sketchwire.prefs`, via `savePrefs`/`restorePrefs`) separately from the autosave, and are not undo-tracked (same treatment as `state.zoom`/`showGrid`). `Renderer.drawGrid(ctx, w, h, color)` takes a single base color and varies only `globalAlpha` for the minor vs. major grid lines, rather than two hardcoded colors. "Limpiar todo" resets both to their defaults, clears the prefs key and re-runs the zoom auto-fit (`zoomManual = false` + `fitZoomToViewport()` — the same pair `init()` runs), in addition to clearing elements: the button promises the app as freshly opened, and there the canvas fills the available space. Forcing 100% and setting `zoomManual` instead — the original behaviour — both shrank the canvas and disabled the auto-fit for the rest of the session (see `BUGS.md`).
