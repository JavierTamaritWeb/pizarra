### A tool's own settings must open from the tool, not only from the panel

A control that is reachable only from the side panel is, in practice, unreachable: the panel sits far from the sidebar where the user actually clicked, it can be a hidden drawer below 1100px width, and nothing about clicking a tool button hints that an unrelated-looking control changed meaning somewhere else on screen. **v1.22.0 shipped the eraser's size control as a small ⚙ button inside the panel's stroke-slider section — technically wired correctly, invisible in practice.** The user clicked the "Borrador" tool expecting the size modal to show up right there, the way every other configurable tool (Emoji, Planta, Puerta, Ventana, Tejado, Balcón, and the eight Jardín tools) already opens its own modal from `selectTool` the moment it's picked — and reported it as broken.

The fix, and the rule going forward: **if a tool has a setting worth surfacing, wire it into `selectTool(id)` so picking the tool opens it**, following the existing `if (id === TOOLS.X) $('modal-X').showModal();` pattern (see `openEraserSizeModal()`). A panel control (twin slider, gear button, whatever) can still exist as a faster way to *reopen* or *live-tweak* it without leaving the tool, exactly like Fachada's twin panel fields — but it must never be the *only* way in, **and it must not change meaning with the active tool**: the panel's stroke slider did (it became the eraser's size, retitled and re-ranged) and that is why v2.21.0 removed it outright rather than moving it. Note one real difference from the catalogue tools: Emoji/Planta/Balcón etc. require a choice before the tool is usable, so cancelling their modal restores the previous tool (`opensVariantModal`, `state.toolBeforeModal`). The Eraser needs no such choice — it already erases at whatever size it has — so its modal is deliberately *not* registered in `opensVariantModal`, and closing it just leaves you on the Eraser, ready to draw (same reasoning as Emoji, which shares this trait).

**`#modal-stroke` and `#modal-shape` (v2.9.0) extend the same rule to the drawing and shape tools.** `STROKE_TOOLS` (Lápiz, Línea, Flecha, Flecha curva, Semicírculo) open the first from `selectTool`; `SHAPE_TOOLS` (the ten of Formas) open the second, which carries the whole **Relleno** block on top of the stroke — that panel section exists only for them. Both work exactly like the Eraser's size modal and, like it, are *not* in `opensVariantModal`: closing leaves you on the tool, ready to draw. Their live previews draw the real thing (a line vs an arrow; a pentagon vs a circle) with the current settings, so «Doble punta» is dimmed on a line and a filled pentagon looks filled before you drag. **Since v2.21.0 a panel ⚙ belongs to its section and always opens the settings of *that* section** — `#btn-element-settings`, `#btn-fill-settings`, `#btn-text-settings`, `#btn-build-settings`, `#btn-garden-settings`, `#btn-selection-settings`. Before that there was a single one, **in the «Trazo» heading**, that `syncPanelSections` **retargeted to five different modals** by `state.tool` and showed or hid with a six-branch condition: the same button, in the same place, opened five different dialogs and there was no way to tell which without pressing it. **«Trazo» is now the one section with settings and no ⚙, deliberately** — it was that button's house, and giving it one back is reopening the problem. Its three destinations are reached where they belong: pressing the tool in the sidebar (the primary way, which also works with the panel closed or drawered) and, with something selected, `#btn-element-settings`. «Lienzo» has none either, for the simpler reason that no modal holds its controls. What survives of the context-dependence is deliberately small and never changes a destination: «Texto» has two (`#modal-emoji` when the Emoji is active and nothing is selected, since that is where the slider's twin lives), and only `#btn-element-settings` still gets a `hidden` — it follows the **type of what is selected** (`TYPE_SETTINGS_MODAL`, the inverse of `MODAL_EDIT_TYPE`) and `settingsModalForSelection()` returns `null` when the types disagree, same rule as `commonOf`: don't invent a value they don't share. Everything else inherits its section's visibility. All of them call `open*Modal()` directly, so opening settings from the panel can never change tool or empty the selection; **«Edificios» and «Jardín» are the one exception and go through `selectTool` on purpose**, because a catalogue is rebuilt when it opens (its icons are painted with the live geometry, colour and stroke) and that rebuild lives inside `selectTool`. Two consequences worth remembering: `renderStrokePreview`/`renderShapePreview` now read the selected element's type before the tool's (those modals can be opened with any tool active, so a selected pentagon was previewing as a rectangle), and the guard that matters most is the textual one in `tests/smoke.test.js` — `dom-stub.js` fabricates an empty `<div>` for an unknown id, so a gear wired in app.js but missing from `index.html` passes every vm test and simply isn't there in the browser; that same guard pins which two sections must stay ⚙-less. **`#modal-stroke` was built the other way round first — not opening on selection, only the ⚙ plus a re-entry click — on the reasoning that the pencil is the most-used tool and a modal on every change would be in the way. The user rejected that: the promise "picking a tool shows its settings" is the whole point of the rule, and an exception for the most-used tool is where it matters most.** Don't reintroduce the exception.

**`#modal-text` and `#modal-ui` (v2.10.0) complete the rule for the UI group** — Mover, «Select» (v2.11.0) and **Marco** (v3.12.0) are the only tools with no settings modal (the guards' "tool that opens nothing" baseline uses Mover). The frame has none because it has no creation setting of its own: its colour and stroke come from the shared defaults and its label is edited per-frame in «Posición y tamaño», so a modal would be an empty promise — the rule is *if a tool has settings, picking it opens them*, not *every tool opens a dialog*. Texto opens the first (font-size twin of `#font-slider`, colour, preview); Botón/Input/Imagen/Navbar/Tarjeta share the second (`UI_MODAL_TOOLS`), retitled per tool by `syncUiControls()`, whose preview draws the real component via `Renderer.renderElement` scaled to fit (the nav is 600×50). Its **Rótulo** field goes through `applyLabel` — the same body as the panel's `#el-label` — and is dual: with a selection it edits the element's `label`; without, it writes `state.uiLabels[tool]`, the creation default the UI branch of `onMouseUp` stamps on new components (empty = renderer default; `imagePlaceholder` has no label and its row hides). `uiLabels` persists in prefs (known keys, strings, trimmed to 120 chars — they end up in `label`, which travels in exported JSON). Neither modal is in `opensVariantModal`.

**Pulsar la herramienta del elemento seleccionado lo edita (v2.10.0).** `selectTool` used to clear the selection unconditionally, so the settings modals could only ever configure creation defaults. Now `MODAL_EDIT_TYPE` maps each settings-modal tool to the **exact** element type it edits (pencil/line/arrow/curveArrow — the Semicírculo maps to `curveArrow`, which is what it creates —, the ten shapes, `text`, the five UI types), and the selection survives when it contains at least one element of that type; the modal then opens showing the selection's values, and the existing dual semantics do the editing — geometry included. Exact-type on purpose: "press the tool of the selected element to edit it" fits in one sentence, and pressing Rectángulo with a circle selected deselects like it always did. Starting any creation gesture on the canvas (`onMouseDown`, right after the SELECT branch) drops the kept selection — otherwise the panel would keep editing the old selection while you draw something new. Catalogues, the Eraser and Emoji still clear.

**The two Edición tools never clear it at all (`SELECTION_TOOLS`, v2.12.0).** Mover and «Select» are the tools that work *on* the selection — one moves, resizes and duplicates it, the other builds it — so neither empties it when picked, in either direction. They aren't in `MODAL_EDIT_TYPE` (they have no settings modal), so they were falling into the unconditional `setSelection([])` inherited from pre-2.10.0, and that broke the natural division of labour the moment «Select» existed: frame several objects with «Select», press Mover to move them, and the drag moved only the one under the pointer because the selection was gone. Guarded by *"seleccionar varios con «Select» y pulsar Mover los mueve TODOS a la vez"* — plus its reverse and a third guard pinning that creation tools still clear, so the fix can't drift back into "never clear".

**The UI components' renderer defaults are Spanish since v2.10.0** («Botón», «Escribe aquí...», «Título», nav «Inicio/Nosotros/Contacto») — they were English in an app whose UI was always Spanish. They are duplicated in exporter.js (SVG and HTML branches) and pinned by `tests/sketchy-renderer.test.js` and `tests/exporter.test.js`: change them in both places or the exports lie.

Two consequences of nearly every tool now opening something:

- **Returning to the "previous tool" after cancelling a catalogue would chain a second modal** on top of the one just closed. `selectTool(id, { silent: true })` selects without opening, and `wireBuildModalCancel` uses it: a previous *catalogue* still falls back to `TOOLS.SELECT` (reopening it would put you back to picking a variant, which is not what cancelling asked for), but a previous tool that only opens *settings* is restored silently. Dumping every case on Mover would be the easy path and the worse one. Guarded by *"cancelar un catálogo recupera la herramienta sin encadenar modales"*.
- **`e2e/helpers.js`'s `selectTool()` closes the five settings modals** (`SETTINGS_MODALS`: eraser, stroke, shape, text, ui) after picking a tool, because a `<dialog showModal>` makes the canvas inert and every drawing spec would otherwise time out. Catalogues are deliberately *not* in that list — those specs need to pick a variant. Specs that assert the *opening* click the sidebar button directly instead (`e2e/panel.spec.js`).
